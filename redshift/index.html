Start here · the class, minus the noise

A sales file lands. What happens next?

A business team wants to know revenue, cost and profit by region and by country. The data arrives as a CSV in S3. A file isn't something analysts can query, and at gigabyte or petabyte scale you can't even open it. So you, the data engineer, build a pipeline that turns that file into clean warehouse tables, runs on its own when the file arrives, and never creates duplicates.

The class covered one complete pipeline. Strip away the logistics and these ideas are what's left:

The ideas from class, cleaned up

Pattern

Source → process → load → orchestrate

Every pipeline has this shape. The services can change: Glue becomes EMR, Step Functions becomes Airflow, Redshift becomes Snowflake. The pattern stays the same.

Lake vs warehouse

S3 holds anything; Redshift holds tables

A lake stores any format (CSV, JSON, video) with no enforced structure. A warehouse needs a defined schema of typed columns, and that is what makes it fast to query.

Medallion

Bronze → silver → gold

Raw as received → cleansed and typed (Parquet) → aggregated for business use. The lab keeps bronze and silver in S3 and gold in Redshift. The lab guide calls this "Pattern 2".

Orchestration

Dependencies and failure handling

Job 1 must succeed before jobs 2 and 3 run, and a failure stops the chain. Step Functions owns the order, parallel branches and catches.

Event vs schedule

Run when data arrives

A 10 PM cron job fails if the file is late. An event trigger runs only after the file exists, so a late file doesn't break it.

Upsert

Update else insert

Re-running the same file still leaves 899 rows. Matching rows are replaced, not appended. This is idempotency, and interviewers love it.

Serverless

Pay for use, not for servers

Like Google Drive, you use the service without renting machines. Start on Redshift Serverless, and move to provisioned only when a steady workload makes it cheaper.

Environments

Dev → QA → Prod with IaC

Engineers build manually in dev. DevOps then scripts it (setup.sh in the lab, CloudFormation or CDK in real life) and promotes the same code to higher accounts.

Questions students asked, answered properly

How does the data get into S3 in the first place?

Most of the time (roughly 70–80% in practice) the source team pushes files into a bucket and prefix you give them, in a format you agree on. You can also pull data yourself: Glue JDBC reads from a database, AWS DMS or zero-ETL for change data capture, AppFlow for SaaS. You own the landing contract: the bucket, the prefix, the format and the trigger.

Three CSV files arrive. Does the pipeline run three times?

Yes. Each ObjectCreated event invokes Lambda once. To run once per batch, ask the source to finish with a zero-byte marker file (_SUCCESS or batch.done), filter the S3 notification on that suffix, and have the Glue job read the whole prefix. Other options: batch events through SQS or EventBridge, or move to a schedule when arrival times are reliable.

A 5 GB file is uploading in parts. Will the event fire too early?

No. S3 emits ObjectCreated:CompleteMultipartUpload only after the object is fully written and visible. Readers never see a half-written object.

Why three tables from one CSV?

Each table serves a different question, so each has a different grain. target_sales is one row per order, by_region is one row per region, and by_country_item is one row per country and item type. Pre-aggregated tables make dashboards fast and cheap. Inside Redshift you could also build them as materialized views (Level 6).

Who configures CloudWatch logs?

Nobody needs to. Lambda, Glue and Step Functions send logs to CloudWatch by default (Step Functions logging levels are configurable). In Redshift you also query SYS_* system views and can turn on audit logging (Level 9).

L1
Level 1 · Foundations

Why a warehouse exists at all

Amazon's order database is built to save one order in milliseconds. Ask it "total profit by region for the last five years" and it has to read every column of every order row by row, while customers are still checking out. A warehouse is a second copy of the data, laid out for the opposite job: reading a few columns across billions of rows.

What Amazon Redshift actually is

Redshift is a fully managed, massively parallel processing (MPP), columnar data warehouse. It speaks PostgreSQL-flavoured SQL (it began as a fork of ParAccel on PostgreSQL 8.0.2) and connects over JDBC/ODBC or the HTTP-based Data API. Your lab setup script used the Data API to create tables with aws redshift-data execute-statement. Three ideas explain almost all of its speed:

  1. MPP: data is split across many slices, each scanning its share at the same time.
  2. Columnar storage: a query reads only the columns it needs, and similar values compress very well.
  3. Skipping: zone maps (min/max per block) let it skip blocks that can't match a filter.

Level 2 · Architecture

Leader, compute nodes, slices, and where data really lives

Picture a restaurant. The leader node is the head chef: it reads the order (your SQL), writes the recipe (query plan), and hands each line cook a piece of the work. The compute nodes are the stations, and each slice is one cook with their own share of the ingredients. The pantry is Redshift Managed Storage on S3, with a fast local fridge (SSD cache) at every station.

How a query travels

The plan is broken into streams → segments → steps. A stream is a set of segments that run together. A segment is compiled code that each slice runs. Steps are individual operations such as scan, hash, aggregate or join. When you read EXPLAIN output (Level 6), you're reading this plan.

Leader-node-only gotchas

Some functions run only on the leader, such as certain catalog queries and CURRENT_SCHEMA()-style system functions. Mixing them with user-table queries throws errors. Also, the leader is a single point of coordination. Huge result sets returned to a client (SELECT * on a billion rows) bottleneck there. Use UNLOAD to S3 instead.

L3
Level 3 · Storage internals

Columnar blocks, compression and zone maps

Your query is SELECT region, SUM(total_profit) FROM target_sales GROUP BY region. The table has 14 columns. A row store reads all 14. Redshift reads 2. The data it does read is compressed 3–10×, and whole blocks are skipped when a filter rules them out. That's most of the performance story, before any tuning.

Blocks and compression encodings

Each column is stored in immutable 1 MB blocks. Because a block holds one data type with often-repeated values, compression works extremely well, and less I/O means faster queries. With ENCODE AUTO (the default), Redshift picks and changes encodings for you.

Zone maps: skip blocks you don't need

Deletes, updates and VACUUM

Blocks are immutable. An UPDATE is really a delete plus an insert. A DELETE only marks rows as deleted, so they still take space and get scanned until removed. New rows land in an unsorted region at the end. Two background jobs clean up:

  • VACUUM reclaims space from deleted rows (DELETE ONLY) and re-sorts (SORT ONLY, FULL, REINDEX for interleaved). Redshift runs automatic vacuum delete and automatic table sort in quiet periods.
  • ANALYZE refreshes the statistics the optimizer uses. Auto analyze runs in the background. COPY into an empty table also updates stats (STATUPDATE).
Connect to the lab

Each upsert run deletes matching UUIDs from target_sales and inserts fresh rows. Over months of daily runs, that leaves ghost rows and unsorted data. Auto vacuum usually keeps up. After a huge backfill, run VACUUM FULL target_sales TO 99 PERCENT; ANALYZE target_sales; yourself, and check svv_table_info.unsorted and stats_off.

L4
Level 4 · Physical design

Distribution, sort keys, data types and the star schema

To join sales to country, matching rows must sit on the same slice. If they don't, Redshift ships data across the network mid-query, which is the single biggest cause of slow joins. Distribution decides which slice a row lives on. The sort key decides what order rows sit in on that slice. Together they decide whether a query flies or crawls.

StyleUse whenWatch out
KEYLarge fact table and its largest dimension joined on the same column. Distribute both on that column so the join is local.Skew: a column with few or uneven values (country, NULL-heavy, "unknown") overloads one slice. Pick high-cardinality, evenly spread keys such as customer_id.
ALLSmall, slowly changing dimensions (under a few million rows) joined everywhereEvery load writes to every node, and storage multiplies by the node count
EVENTables with no dominant join, or staging tablesJoins on it always need redistribution
AUTOYour default, especially on ServerlessOverride only with evidence from EXPLAIN or system views
-- Detect skew: rows on the busiest slice vs the quietest
SELECT "table", diststyle, skew_rows, unsorted, stats_off, tbl_rows
FROM svv_table_info ORDER BY skew_rows DESC;

Sort keys

  • Compound (default when you list columns): sorted by col1, then col2. Great for filters on the leading column (dates). Useless if you filter only on col2.
  • Interleaved: equal weight to each column. Rarely worth it today: slow to vacuum (REINDEX) and bad with ever-increasing columns like dates.
  • AUTO (default): Redshift watches your query patterns and chooses one. This is Automatic Table Optimization (ATO).

Good sort key candidates: columns in range filters (order_date), columns frequently in WHERE, or the join column, because sorted data on both sides allows a merge join, the fastest join type.

Data types: small, exact, correct

  • Use the narrowest type: SMALLINT before INTEGER before BIGINT.
  • Size VARCHAR realistically. Redshift allocates memory for the declared width during queries, so VARCHAR(65535) everywhere wastes RAM. Lengths are in bytes, so multi-byte UTF-8 needs headroom.
  • Store dates as DATE or TIMESTAMP, never VARCHAR. You get proper zone maps, date functions and AZ64 compression.
  • Money: DECIMAL(p,s), not FLOAT.
  • Semi-structured JSON: the SUPER type, queried with PartiQL dot notation (payload.customer.city).
  • Surrogate keys: BIGINT IDENTITY(1,1). Values are unique but not gap-free or ordered across slices.
Constraints are not enforced

PRIMARY KEY, FOREIGN KEY and UNIQUE are informational only. The optimizer uses them for planning, but Redshift will happily store duplicates. Only NOT NULL is enforced. That's exactly why the lab needs an upsert: the database won't stop the duplicates. If you declare a PK, make sure it's true, or you'll get wrong query results.

Modeling: from flat file to star schema

Star

Denormalized dimensions

One join per dimension. Simple for BI tools, and the Redshift default choice.

Snowflake schema

Normalized dimensions

Country → region as separate tables. Saves space, but adds joins, so it's usually avoided in Redshift.

SCD type 1

Overwrite

Keep only the latest value. The lab's upsert is SCD1 at row level.

SCD type 2

Keep history

Close the old row (valid_to, is_current=false) and insert a new one. Done with MERGE plus an INSERT.

COPY, upserts, MERGE, streaming and zero-ETL

In the lab, Glue "wrote to Redshift". Under the hood, Glue's Redshift connector wrote temporary files to s3://…/tmp/ and issued a COPY. That's the core lesson of this level: bulk data enters Redshift through COPY, in parallel, from S3. Row-by-row INSERT is the slow path.

Upsert patterns: making loads idempotent

-- Pattern B, the modern answer for the lab's upsert
BEGIN;
MERGE INTO public.target_sales USING public.stage_sales s
ON target_sales.uuid = s.uuid
WHEN MATCHED THEN UPDATE SET
  units_sold = s.units_sold, total_revenue = s.total_revenue,
  total_cost = s.total_cost, total_profit = s.total_profit, order_date = s.order_date
WHEN NOT MATCHED THEN INSERT VALUES
  (s.uuid, s.country, s.item_type, s.sales_channel, s.order_priority, s.order_date, s.region,
   s.ship_date, s.units_sold, s.unit_price, s.unit_cost, s.total_revenue, s.total_cost, s.total_profit);
END;

-- Dedup inside the batch first: MERGE fails when one target row matches 2 source rows
CREATE TEMP TABLE stage_dedup AS
SELECT * FROM (
  SELECT s.*, ROW_NUMBER() OVER (PARTITION BY uuid ORDER BY load_ts DESC) AS rn
  FROM stage_sales s) WHERE rn = 1;   -- then MERGE … USING stage_dedup
Interview line: why not TRUNCATE + INSERT for the main table?

"Full reloads rewrite the whole table every run, so cost grows with history, and readers see an empty table if anything fails between statements. An upsert only touches changed keys, runs in one transaction, and gives the same result if the same file is replayed. That's idempotency. For small aggregates, a full recompute inside a transaction is simpler and correct."

Also know
  • ALTER TABLE APPEND moves blocks from a staging table into a target instantly (no copy) when the schemas match. Good for append-only facts.
  • Temp stage tables (CREATE TEMP TABLE … (LIKE target)) avoid stage collisions when two pipeline runs overlap.
  • Deep copy (CREATE TABLE new AS SELECT …, then swap) re-sorts a badly fragmented table faster than VACUUM.

Level 6 · Tuning

Reading EXPLAIN, materialized views and the tuning checklist

A dashboard that took 2 seconds now takes 40. You don't guess. You run EXPLAIN, look for the expensive step (usually a redistribution or a full scan), check the system views for skew and stale stats, then fix the cause: a key, a sort, a stat, or a precomputed result.

The redistribution labels in EXPLAIN

EXPLAIN
SELECT c.region, SUM(f.total_profit)
FROM fact_sales f JOIN dim_country c ON f.country = c.country
WHERE f.order_date >= '2016-01-01'
GROUP BY 1;
-- XN HashAggregate ...
--   XN Hash Join DS_DIST_ALL_NONE (cost=...)        <- good: dim_country is ALL
--     XN Seq Scan on fact_sales f  Filter: (order_date >= '2016-01-01')

Join algorithms: merge join (both sides sorted and distributed on the join key, fastest), hash join (most common), and nested loop (usually a missing join condition or a cross join, so investigate it).

Precompute: materialized views

The lab's aggregate tables are hand-built materialized results. Redshift can maintain them for you:

CREATE MATERIALIZED VIEW mv_sales_by_region
AUTO REFRESH YES AS
SELECT region, SUM(total_revenue) AS revenue, SUM(total_profit) AS profit,
       SUM(units_sold) AS units, COUNT(*) AS orders
FROM public.target_sales GROUP BY region;

REFRESH MATERIALIZED VIEW mv_sales_by_region;   -- incremental when possible
  • Incremental refresh applies only changes for supported query shapes (SUM, COUNT, joins). Others recompute fully.
  • Automatic query rewrite: queries against the base table can be answered from the MV automatically.
  • AutoMV: Redshift may create and drop MVs on its own based on your workload.
  • Cascading MVs (an MV on an MV) and MVs on external (Spectrum) and Iceberg tables are supported. Iceberg MVs arrived in 2026.
Lab upgrade idea

Glue jobs 2 and 3 (which read Redshift over JDBC, aggregate in Spark and write back) could be two materialized views. Fewer moving parts, no Spark cluster, refreshed right after the load. This is the ELT mindset: push transformations into the warehouse when they're pure SQL.

Other speed features

Result cache

Free repeat answers

Identical query, unchanged data, same user rights: served from the leader in milliseconds. Turn it off when benchmarking: SET enable_result_cache_for_session TO off;

SQA

Short query acceleration

Predicts short queries and runs them in a fast lane so dashboards don't wait behind ETL.

Approximate

APPROXIMATE COUNT(DISTINCT)

HyperLogLog, about 2% error, much faster on huge cardinalities. HLL sketches can be stored and combined.

Late binding

WITH NO SCHEMA BINDING

Views that don't lock underlying tables, so you can drop and recreate tables during loads. Required for views over Spectrum.

The tuning checklist, in order

  1. Is it queueing or executing? (queue_time vs execution_time.) Queueing means a workload or scaling problem (Level 7).
  2. Are stats fresh? stats_off above 10 means ANALYZE.
  3. Is the table mostly unsorted or full of deleted rows? Run VACUUM or a deep copy.
  4. Any DS_BCAST_INNER or DS_DIST_BOTH on big tables? Fix distribution.
  5. Are range filters on the sort key? Do you filter on wrapped columns like DATE(ts)? Filter the raw column instead.
  6. Spilling to disk? Look for is_diskbased in the query details. Use narrower VARCHARs, fewer columns, more memory per slot, or more RPUs.
  7. Selecting more than you need? Avoid SELECT *; columnar rewards narrow queries.
  8. Same heavy aggregate every few minutes? Materialized view.

Level 7 · Concurrency

Workload management, concurrency scaling and resizing

At 9 AM, 200 analysts open dashboards while a nightly ETL job is still loading. Without rules, a single monster query can starve everyone. Workload management (WLM) is the bouncer: it decides who gets in, how much memory they get, and when to call in extra clusters.

Auto WLM

Recommended

Redshift sets concurrency and memory per query dynamically. You set priorities (HIGHEST … LOWEST) per queue.

Manual WLM

Full control

Up to 8 queues, fixed slots and memory %. Only for very specific needs; it's easy to get wrong.

QMR

Query monitoring rules

Predicates like query_execution_time > 600, scan_row_count or spill trigger log, hop (move queue) or abort.

Concurrency scaling

Burst for reads (and writes)

Adds transient clusters when queries queue. Provisioned clusters earn about 1 free hour of credit per day of use, then pay per second. Set a usage limit.

Transactions and isolation

Redshift is ACID. Provisioned clusters historically default to SERIALIZABLE isolation. Serverless and newer databases default to SNAPSHOT isolation, which allows more concurrency. Under serializable, two concurrent writers to the same table can fail with ERROR: 1023 Serializable isolation violation. The fixes are to serialize the writers (one pipeline at a time, or an explicit LOCK table at the start of the transaction), retry with backoff, or switch the database to snapshot isolation.

Connect to the lab

If two files land a minute apart, two Step Functions executions run Glue job 1 at the same time, and both truncate and load stage_sales. That's a race. Fixes: a per-run temp stage table, Step Functions concurrency control (a Lambda check for running executions, or an SQS FIFO in front), or a batch marker file so there's only one run.

Spectrum, Iceberg, federated query, data sharing and ML

Your warehouse holds two years of hot data. Ten years of history sits in S3 as Parquet, finance wants to join against live Aurora data, and a sister team in another AWS account needs read access. You don't copy anything. You query it where it lives.

  • Cut scanned bytes: columnar formats (Parquet), compression, partitions on common filters, and fewer, larger files (128 MB–1 GB).

Apache Iceberg in Redshift (2025–2026)

Iceberg is an open table format that adds ACID transactions, schema evolution, hidden partitioning and time travel to files on S3. Redshift has moved from read-only to a full Iceberg engine:

  • Writes (INSERT and more) to Iceberg tables through the auto-mounted Glue Data Catalog, with Lake Formation permissions respected.
  • ALTER TABLE for Iceberg schema, partition and property changes (May 2026).
  • Iceberg v3 support with deletion vectors, row lineage and default column values (August 2026).
  • Iceberg materialized views stored in S3 or S3 table buckets, readable by other engines (October 2026).
  • Automatic resolution of non-conflicting concurrent writes (rolled out September 2026).
Interview line

"For shared, multi-engine data I'd keep the gold tables as Iceberg in S3 Tables or the Glue Catalog, so Spark, Athena and Redshift all read one copy. Redshift-local tables stay for the hottest, most concurrent BI workloads, where its storage engine is fastest."

System design with Redshift at the center

How to answer any design question: the 6-step frame

  1. Clarify requirements: data volume and velocity, freshness SLA, number of users and queries, retention, compliance (PII), budget.
  2. Ingestion per source: files → S3 + COPY; OLTP → zero-ETL or DMS; events → streaming; SaaS → AppFlow or zero-ETL.
  3. Storage layers: bronze, silver and gold. Decide what lives in S3/Iceberg and what lives in Redshift (hot, concurrent).
  4. Modeling: star schema, grain, SCD strategy, distribution and sort keys for the top queries.
  5. Orchestration and reliability: event or schedule, dependencies, idempotent loads, retries, DLQs, data-quality gates, backfills.
  6. Operate: security, monitoring, cost controls, CI/CD, DR. Then name the trade-offs you accepted.

Reliability patterns every senior answer includes

Idempotency

Safe to replay

Stage + MERGE or DELETE/INSERT keyed on a business key, with a manifest of processed files. Re-running yesterday gives the same result.

Completeness

Marker files

_SUCCESS or .done triggers a single run per batch (from class). Add row-count and checksum validation against a control file.

Data quality

Gate before gold

Glue Data Quality rules (completeness, uniqueness, ranges). Bad rows go to quarantine, and the pipeline fails loudly.

Late data

Reprocess windows

Upsert by key and recompute affected partitions or aggregates for the last N days, not just today.

Schema drift

Detect, don't explode

Catalog or crawler compares schemas. New columns land in SUPER or are added with ALTER TABLE. Breaking changes alert the source team.

Failures

Retry, catch, alert

Step Functions Retry with backoff on Glue throttling, Catch → SNS alert, DLQ on Lambda, and a runbook for backfills.

Small files

Compact first

Thousands of tiny files slow COPY and Spectrum. Compact to 128 MB–1 GB Parquet in the silver layer.

Isolation

Separate ETL from BI

Two workgroups on one dataset through data sharing (multi-warehouse writes), so heavy loads never slow dashboards.

Stored procedures: logic that lives in the warehouse

CREATE OR REPLACE PROCEDURE etl.upsert_sales(p_batch VARCHAR)
AS $$
DECLARE
  v_rows INT;
BEGIN
  MERGE INTO public.target_sales USING public.stage_sales s
    ON target_sales.uuid = s.uuid
  WHEN MATCHED THEN UPDATE SET units_sold = s.units_sold, total_profit = s.total_profit
  WHEN NOT MATCHED THEN INSERT VALUES (s.uuid, s.country, s.item_type, s.sales_channel,
    s.order_priority, s.order_date, s.region, s.ship_date, s.units_sold, s.unit_price,
    s.unit_cost, s.total_revenue, s.total_cost, s.total_profit);
  GET DIAGNOSTICS v_rows := ROW_COUNT;
  INSERT INTO etl.load_audit VALUES (p_batch, v_rows, GETDATE());
  RAISE INFO 'batch % merged % rows', p_batch, v_rows;
EXCEPTION WHEN OTHERS THEN
  RAISE EXCEPTION 'upsert failed for batch %: %', p_batch, SQLERRM;
END;
$$ LANGUAGE plpgsql;

CALL etl.upsert_sales('2026-10-24');
  • Language is PL/pgSQL: variables, IF/LOOP, cursors, dynamic SQL with EXECUTE, RAISE, exception blocks.
  • Procedures can COMMIT/ROLLBACK inside when called outside an explicit transaction block. The NONATOMIC option makes each statement commit on its own, which suits long ETL steps.
  • SECURITY DEFINER lets users run a procedure with the owner's rights without being granted access to the underlying tables. This is a common security pattern.
  • Schedule them with Query Editor v2 scheduled queries (EventBridge Scheduler + Data API under the hood), or call them from Step Functions or Airflow.
  • UDFs: SQL UDFs (scalar, inline) and Lambda UDFs (any language, external calls). Python UDFs are past end of support.

Interview question bank

Fundamentals
What makes Redshift fast compared to a normal database?

MPP across slices, columnar storage (read only the needed columns), heavy compression, zone maps that skip blocks, compiled query code, result caching, and RMS with local SSD caching. Most speed comes from reading less data and doing it in parallel.

Explain leader node vs compute node vs slice.

The leader parses, optimizes, compiles and coordinates, and does final aggregation; it stores no user table data. Compute nodes execute the plan. Each node is divided into slices with their own share of CPU, memory and data, and the slice is the unit of parallelism.

What is RA3 managed storage and why does it matter?

RA3 (and RG) nodes keep the durable copy of data in S3-backed Redshift Managed Storage and cache hot blocks on local SSD. Compute and storage scale and bill independently. It also enables data sharing, multi-AZ and fast resizes.

Namespace vs workgroup in Serverless?

The namespace is storage and metadata: databases, users, snapshots, encryption. The workgroup is compute and networking: RPUs, limits, VPC and endpoint. You pay RPU-seconds only while queries run, plus storage.

Are primary keys enforced in Redshift?

No. PK, FK and UNIQUE are informational and only used by the optimizer. Only NOT NULL is enforced. You prevent duplicates yourself through staging and upsert/MERGE logic, plus dedup checks.

Design and tuning
How do you choose a distribution style?

Start with AUTO. For a large fact joined to a large dimension, distribute both on the join key (KEY) for colocated joins. Small, slowly changing dimensions get ALL. Tables with no clear join pattern get EVEN. Avoid low-cardinality or skewed keys, and check skew_rows in svv_table_info.

Compound vs interleaved sort key?

Compound sorts by the columns in order. It's best when queries filter on the leading column (usually date) and supports merge joins. Interleaved weights columns equally for varied filter combinations, but vacuum (REINDEX) is expensive and it handles ever-increasing columns badly. Today the default answer is compound or AUTO.

A query got slow overnight. How do you troubleshoot?

Check sys_query_history for queue vs execution time. Run EXPLAIN and look for DS_BCAST or DS_DIST_BOTH and nested loops. Check svv_table_info for stats_off, unsorted % and skew. Check for disk spill. Then fix the cause: ANALYZE or VACUUM, keys, rewriting filters on sort-key columns, WLM priorities or more RPUs, or a materialized view.

Why are deletes and updates expensive, and what is VACUUM?

Blocks are immutable. A delete only marks rows, and an update is a delete plus an insert into the unsorted region. VACUUM reclaims deleted space and re-sorts. Auto vacuum runs in the background. After big changes, run VACUUM and ANALYZE, or do a deep copy.

What does the result cache do and when is it bypassed?

It returns stored results for identical queries when the underlying data hasn't changed and the user has access. It's bypassed when data changes, for queries with non-deterministic functions such as GETDATE() or RANDOM(), and when it's disabled for the session.

When would you use a materialized view instead of an aggregate table?

When the aggregate is pure SQL over Redshift data. Redshift maintains it (incrementally when possible), can auto-refresh it, and can rewrite queries to use it automatically. A hand-built table makes sense when the logic is complex or needs external processing.

Loading and pipelines
Why COPY instead of INSERT? How do you make COPY fast?

COPY loads in parallel on every slice directly from S3. Single-row INSERTs go through the leader one at a time. For speed: split input into equal compressed files (1 MB–1 GB) in a count that's a multiple of slices, use columnar formats, use a manifest, and turn off COMPUPDATE/STATUPDATE for staging loads.

Explain your upsert strategy and why it's idempotent.

Load the batch into a staging table, deduplicate on the business key, then in one transaction either DELETE matching keys from the target and INSERT from stage, or MERGE. Replaying the same file produces the same final state: 899 rows stay 899, and the homework file correctly gives 909.

Multiple files arrive for one batch. How do you avoid N pipeline runs?

The source writes a marker file (.done or _SUCCESS) last. The S3 notification filters on that suffix, and the job processes the whole prefix or manifest. Alternatives: SQS or EventBridge batching with a short window, or scheduled runs with a completeness check.

How would you load near-real-time data into Redshift?

Streaming ingestion: an external schema on Kinesis or MSK plus an auto-refresh materialized view, for seconds of latency. For OLTP sources, zero-ETL integrations. Firehose to S3 then COPY when minute-level latency is fine.

How do you handle schema changes from the source?

Agree on a contract with the source team. Detect drift in the catalog or in Glue. Land additive changes safely: new nullable columns via ALTER TABLE, or a SUPER column for semi-structured payloads. Fail fast and alert on breaking changes. Version the silver layer, where Iceberg schema evolution helps.

Two pipeline runs overlap and one fails with a serializable isolation error. Why, and what do you do?

Concurrent transactions read and wrote overlapping tables in a way that can't be serialized. Serialize the writers (one execution at a time, or LOCK the table at the start of the transaction), use per-run temp staging, retry with backoff, or use SNAPSHOT isolation.

Platform and architecture
Redshift Spectrum vs Athena vs loading the data?

Load hot, frequently joined data into Redshift. Use Spectrum to join S3 data with Redshift tables from one SQL endpoint. Use Athena for standalone ad-hoc lake queries with no warehouse involved. All three can share the Glue Data Catalog.

What is data sharing and when do you use it?

Live, zero-copy access to Redshift data across clusters, workgroups, accounts and regions. Uses: isolating ETL from BI compute, hub-and-spoke or data-mesh designs, giving business units their own compute and cost, and monetizing data through Data Exchange. Consumers can now also write.

Serverless or provisioned? Defend your choice.

Serverless for new, spiky or dev workloads: no capacity planning, and you pay only while queries run. Provisioned RA3/RG with reserved nodes when the load is steady 24×7 and predictable, so the commitment is cheaper and you get fine WLM control. AWS's guidance, and the class's, is to start serverless and re-evaluate once usage is understood.

How do you secure a Redshift warehouse holding PII?

Private VPC with no public access, KMS encryption, TLS. IAM or SSO identities with RBAC roles. RLS for row restrictions, dynamic masking or column grants for PII, Lake Formation for lake data, Secrets Manager for credentials, and audit logging plus CloudTrail for evidence.

How do you control Redshift cost?

Serverless usage limits and max RPU; the right base RPU; reservations; pausing dev clusters; MVs and the result cache to avoid recomputation; offloading cold data to S3/Iceberg; Spectrum and concurrency-scaling limits; monitoring sys_serverless_usage; tearing down unused environments.

What changed in Redshift recently that I should mention?

Graviton RG instances (2026), DC2 deprecation, Iceberg writes, ALTER and v3 support, Iceberg materialized views, AI-driven Serverless scaling with price-performance targets, a 4-RPU minimum base, multi-warehouse writes, zero-ETL expansion, and Python UDFs reaching end of support (use Lambda or SQL UDFs).

COPY and UNLOAD deep dive
Walk me through what happens when you run COPY from S3.

The leader lists the S3 objects (or reads the manifest) and assigns files to slices. Each slice downloads, decompresses, parses and encodes its files in parallel, then writes column blocks. Distribution decides which slice finally stores each row. The load is one transaction: it either commits fully or rolls back, and errors go to sys_load_error_detail. On an empty table, COPY can also choose encodings (COMPUPDATE) and update stats (STATUPDATE).

Your COPY of one 20 GB CSV takes 40 minutes. How do you speed it up?

A single uncompressed file means one slice does the parsing. Split it into many equal, compressed files (count a multiple of the slice count, 1 MB–1 GB each), or better, convert to Parquet in the silver layer. Load into a staging table with COMPUPDATE and STATUPDATE off, check the bucket is in the same region, and make sure the target's sort key isn't forcing a huge re-sort.

How do you make sure COPY loads exactly the right files, once?

Use a manifest listing the exact keys with mandatory: true, and record loaded manifests in an audit table. Alternatives: COPY JOB auto-copy (tracks loaded files itself), or moving processed files to an archive/ prefix. Combine with an upsert so a replay is still harmless.

COPY failed with "Invalid digit" on row 1. What happened?

The header row was read as data. Add IGNOREHEADER 1. If it's a mid-file value like "N/A", use NULL AS 'N/A' or clean the data upstream. Always confirm the line and column in sys_load_error_detail before changing options.

Why UNLOAD instead of SELECT to export 500 million rows?

SELECT sends every row through the leader to one client, which makes it slow and memory-heavy. UNLOAD has all slices write files to S3 in parallel, in Parquet with partitions if you like, encrypted with KMS. Downstream engines (Athena, Spark, Spectrum) read them directly.

Can COPY do an upsert by itself?

No. COPY only appends. Upsert is a pattern: COPY into staging, then DELETE+INSERT or MERGE into the target in one transaction. That's exactly what the lab's preactions and postactions do.

Sort keys and distribution scenarios
Most queries filter on order_date and join on customer_id. Design the keys.

DISTKEY(customer_id) on the fact and the customer dimension, so the join is colocated (DS_DIST_NONE). SORTKEY(order_date) on the fact for zone-map pruning on date filters. Check customer_id isn't skewed (no giant "guest" customer). If it is, consider AUTO or EVEN plus a smaller dimension as ALL.

You chose DISTKEY(country) and one slice is 10× bigger. Why, and what now?

Low cardinality and an uneven value distribution: a few countries dominate, so hashing puts their rows on the same slice. That slice becomes the bottleneck for every query. Switch to a high-cardinality key (order_id or customer_id) or AUTO with ALTER TABLE … ALTER DISTSTYLE, then confirm with skew_rows.

Why does filtering on DATE(order_ts) ignore my sort key?

Wrapping the column in a function hides its raw min/max from zone-map pruning. Filter the raw column with a range instead: order_ts >= '2026-10-01' AND order_ts < '2026-10-02'.

Why can a compound sort key on (region, order_date) be useless for a date-only filter?

Compound sorting is hierarchical. Data is ordered by region first, so dates are scattered across every region's block range and the date min/max per block is wide. Put the most common filter column first, usually the date.

When does ALL distribution hurt?

When the table is large or changes often. Every insert or update is written to every node, storage multiplies by the node count, and loads slow down. Keep ALL for small, slowly changing dimensions.

What's a merge join and how do you get one?

The fastest join: both tables are distributed and sorted on the join column, so slices stream through both in order with no hash table. It needs matching DISTKEY and SORTKEY on the join column and mostly sorted (vacuumed) data.

Data API and connectivity
What is the Redshift Data API and why would you use it?

An HTTPS API (through the AWS SDK or CLI) for running SQL without drivers or persistent connections. It's asynchronous (ExecuteStatement → DescribeStatement → GetStatementResult) and authenticates with IAM temporary credentials, Secrets Manager or Identity Center, so there are no passwords in code. It's ideal for Lambda, Step Functions, scripts and CI/CD; less suited to BI tools or huge result sets.

Data API vs JDBC: when do you pick each?

Data API: serverless and event-driven callers, short-lived functions, no VPC networking for the caller, async long queries. JDBC/ODBC: BI tools, dbt, interactive sessions, streaming large results, and anything needing session features continuously (though the Data API now offers session reuse).

How do you run several statements atomically via the Data API?

BatchExecuteStatement. Statements run in order, and the default ExecutionMode=TRANSACTION commits all or rolls back all. AUTO_COMMIT commits each one individually.

Name the Data API limits.

Query up to 24 hours; results retained 24 hours; result size up to 500 MB (gzipped); statement up to 200 KB; 500 active queries per cluster or workgroup; sessions kept alive up to 24 hours, one query at a time per session; client token valid 8 hours.

How do you avoid a Lambda waiting on a long Redshift query?

Submit with the Data API and return immediately. Then either let Step Functions poll DescribeStatement in a Wait/Choice loop, or set WithEvent=true so EventBridge fires on completion and triggers the next step.

Can you parameterize a table name in a Data API call?

No. Named parameters (:name) replace values only, never identifiers such as table or column names, which also protects against SQL injection. For dynamic identifiers, validate against an allow-list in code, or use a stored procedure with EXECUTE and QUOTE_IDENT.

SQL, objects and admin
CTAS vs CREATE TABLE LIKE vs SELECT INTO?

CTAS creates and fills a table from a query, but doesn't copy constraints, IDENTITY, defaults or the PK, so state your dist and sort keys. LIKE copies the structure (columns, NOT NULL, dist and sort keys) with no data, which is perfect for staging tables. SELECT INTO is CTAS in different syntax.

Why does TRUNCATE inside my transaction break the rollback?

TRUNCATE commits the current transaction implicitly. If you need all-or-nothing behavior (readers must never see an empty table), use DELETE FROM inside BEGIN…COMMIT instead. It's slower but transactional, and VACUUM reclaims the space later.

A new table was created and analysts can't see it. Why?

Grants apply to existing objects. A new table needs its own grant, or set ALTER DEFAULT PRIVILEGES IN SCHEMA … GRANT SELECT ON TABLES TO ROLE analyst so future tables inherit access. Also check USAGE on the schema.

Redshift has no indexes. How does it find rows fast?

Zone maps (min/max per 1 MB block) plus sort keys let it skip blocks, and MPP scans the rest in parallel. Distribution keys colocate joins. Materialized views and the result cache avoid recomputation.

Stored procedure vs UDF vs materialized view?

A procedure runs multi-step logic and DML (ETL, MERGE, audit), called with CALL. A UDF is a scalar function used inside queries (SQL or Lambda; Python UDFs are past end of support). A materialized view stores a query's result for fast reads, with refresh.

Which system views would you check first, and why SYS_?

sys_query_history (what ran and how long), svv_table_info (skew, unsorted, stats), sys_load_error_detail (load failures), svv_transactions/stv_locks (blocking). SYS_ views work on both Serverless and provisioned; STL and STV are provisioned-era views.

Scenario and troubleshooting
A dashboard query hangs and nothing seems to run. What do you check?

Locks. Query svv_transactions or stv_locks for a session holding a lock, often an idle transaction someone never committed or a long ETL job. Decide whether to wait or PG_TERMINATE_BACKEND(pid). Prevent it with statement timeouts, short transactions, and splitting ETL and BI onto separate workgroups.

Duplicates appeared in the fact table even though order_id is the PRIMARY KEY. How?

PKs aren't enforced. Likely causes: a replayed file with plain INSERT, two overlapping runs, or a source batch that contained duplicates. Fix the data with ROW_NUMBER dedup into a new table and swap. Prevent it with stage dedup, MERGE or DELETE+INSERT, single-run orchestration, and a uniqueness check in data quality.

Glue can't connect to Redshift: "Communications link failure". What's wrong?

Networking. Glue runs ENIs in the connection's subnet and needs a security group with a self-referencing inbound rule, a route to S3 (gateway endpoint or NAT) for its temp dir, and the right port or endpoint. The lab's setup step 6 did exactly this.

Your Serverless bill doubled last week. How do you investigate?

sys_serverless_usage for when RPUs spiked, joined to sys_query_history for which queries and users ran then. Look for runaway ad-hoc scans, a new job, a raised base RPU, or MVs refreshing too often. Then set max RPU-hours usage limits, max capacity and query limits.

You must backfill 3 years of data without hurting daytime dashboards. Plan?

Generate partitioned Parquet in S3 and COPY in chunks (per month) into staging, then MERGE or APPEND into the target. Run it off-hours or on a separate ETL workgroup over a data share. Run VACUUM and ANALYZE after, monitor queue time, and make each chunk idempotent so failures can be retried.

How do you migrate an on-prem Teradata warehouse to Redshift?

Assess with AWS SCT (or DMS Schema Conversion), convert DDL and procedures, and map PI → DISTKEY and PPI → SORTKEY. Export history to S3 and COPY it, then run DMS CDC (or extracts) in parallel. Validate counts and checksums, run both systems side by side, then cut over BI tools. Retire BTEQ scripts in favor of procedures or dbt.
