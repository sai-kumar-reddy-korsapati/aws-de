Why containers exist

A container packages your code together with everything it needs to run: the Python version, the libraries, system packages and config. The same package runs the same way on your laptop, in CI, on EC2, on Fargate or in Lambda. It kills "works on my machine".

Shipping containers changed world trade because every port, crane, truck and ship handles the same box. Nobody cares if it holds bananas or laptops. Docker images are that standard box for software: ECS, Lambda, EKS, AgentCore and Batch all accept the same OCI image.

The problem it solves for data engineers

  • Your Glue job works, but a local PySpark test fails because your laptop has Java 21 and Spark wants 17.
  • A pandas script needs pyarrow, which needs a C library that the Lambda zip limit (250 MB unzipped) cannot hold.
  • Airflow, Postgres, MinIO and a mock API must run together locally for a test. Installing each by hand takes a day.
  • A dbt or Great Expectations run must use exactly the same versions in CI and production.

Common misconception

A container is not a lightweight VM. There is no guest OS booting. The ubuntu image only contains Ubuntu's userland files (bash, apt, libc); the kernel is always the host's.

"A VM virtualises hardware and runs its own kernel; a container is a normal Linux process isolated with namespaces and limited with cgroups, sharing the host kernel. That's why containers start fast and are small, but the isolation is weaker, which is why AWS runs each Fargate task and Lambda function inside its own Firecracker microVM."

  • Container = your app + its dependencies, packaged as an image, run as an isolated process.
  • Containers share the host kernel; VMs bring their own.
  • The same OCI image runs on ECS, EKS, Lambda, Batch, AgentCore and your laptop.

How a container really works

Linux has three features that, combined, make a container: namespaces decide what a process can see, cgroups decide how much it can use, and a layered filesystem gives it its own root directory. Docker just automates setting these up.

Namespaces: what the process sees

pid
The container has its own process tree. Your app is PID 1 inside it.
net
Own network interfaces, IP, routing table and ports. Two containers can both listen on 8080.
mnt
Own view of mounted filesystems, so / is the image, not the host.
uts
Own hostname.
ipc
Own shared memory and message queues.
user
Maps root inside the container to an unprivileged user outside (rootless mode).

cgroups: what the process can use

Control groups cap CPU, memory, PIDs and I/O. When you set --memory 512m and your pandas script loads a 2 GB CSV, the kernel's OOM killer ends the process and Docker reports exit code 137. On ECS the same thing shows as OutOfMemoryError: Container killed due to memory usage.

Union filesystem: layers

An image is a stack of read-only layers. When a container starts, Docker adds one thin writable layer on top (overlayfs). Writes go there; deleting the container deletes that layer. This is why containers are ephemeral: anything not in a volume or sent to S3 is gone.

Prove it is just a processTerminal
$ docker run -d --name sleeper alpine sleep 600
$ docker exec sleeper ps
Output
PID   USER     TIME  COMMAND
    1 root      0:00 sleep 600
    7 root      0:00 ps

Inside, sleep is PID 1. On the Linux host (or inside Docker Desktop's VM) the same process has an ordinary PID like 48213 and shows up in ps aux. That is the pid namespace at work.

Why PID 1 matters

PID 1 receives the stop signal. docker stop and ECS send SIGTERM, wait (10 s in Docker, 30 s by default in ECS, set with stopTimeout), then send SIGKILL. If your entrypoint is a shell script that does not exec your app, the shell gets SIGTERM, ignores it, and your Python job is killed mid-write. Fix: use the exec form CMD ["python","job.py"], end scripts with exec python job.py, or add --init / tini.

"Namespaces isolate what a process sees, cgroups limit what it uses, and overlayfs gives it a layered root filesystem with a thin writable layer. I also make sure my app runs as PID 1 via exec-form CMD so it gets SIGTERM and can finish its current batch before Fargate kills it."

  • Namespaces = visibility; cgroups = limits; overlayfs = layered root filesystem.
  • Exit 137 = killed by SIGKILL, usually out of memory.
  • Container writable layer is thrown away; persist to volumes, S3 or a database.
  • Your process should be PID 1 (exec form) so it handles SIGTERM.

Images, OCI and the runtime stack

An image is a read-only template (layers + config). A container is a running instance of an image. The OCI (Open Container Initiative) standards make images and runtimes interchangeable, which is why an image built by Docker runs on ECS, EKS, Lambda or Podman.

Image is the class, container is the object. Or: image is the recipe card, container is the dish you cooked from it. You can cook many dishes from one card.

Image commands: pull, tag, push, save

Images live in your local store and in registries. You pull them down, tag them with names that point to a registry, and push them up.

Image names decoded

123456789012.dkr.ecr.us-east-1.amazonaws.com/data/sales-etl:1.4.0 = registry (ECR host) / repository (data/sales-etl) : tag (1.4.0). With no registry, Docker assumes Docker Hub (docker.io/library/python). With no tag, it assumes latest, which is just a default tag name, not "the newest".

save/load vs export/import

save/load move an image with all layers and metadata. export/import flatten a container's filesystem and lose history, CMD and ENV. Interviewers ask this.

  • registry/repository:tag. No registry = Docker Hub; no tag = latest.
  • latest is just a name. Never deploy latest to production.
  • tag adds a name (no copy); push uploads only missing layers.

Exec form vs shell form

Exec form (use this)

CMD ["python","job.py"]

Your process is PID 1 and receives SIGTERM directly. No shell variable expansion.

Shell form

CMD python job.py

Runs /bin/sh -c "python job.py". The shell is PID 1 and does not forward SIGTERM, so ECS waits 30 s then SIGKILLs your job.

Entrypoint script that still handles signalsentrypoint.sh
#!/bin/sh
set -e
# fetch config, run migrations, etc.
echo "starting with RUN_DATE=${RUN_DATE:-today}"
exec python -m src.job "$@"     # exec replaces the shell, so python becomes PID 1
Handle SIGTERM in Python so a Fargate Spot interruption doesn't corrupt outputjob.py
import signal, sys, logging
stop = False
def on_term(signum, frame):
    global stop
    logging.warning("SIGTERM received, finishing current batch")
    stop = True
signal.signal(signal.SIGTERM, on_term)

for batch in batches():
    if stop:
        checkpoint(); sys.exit(0)
    process(batch)

Fargate Spot gives a 2-minute warning, delivered as SIGTERM to your task (plus an ECS event). Set stopTimeout up to 120 s on Fargate so you have time to checkpoint.

"ENTRYPOINT is the fixed executable, CMD is the overridable default arguments. I use exec form for both so my app is PID 1 and gets SIGTERM; in ECS the task definition's command overrides CMD and entryPoint overrides ENTRYPOINT."

  • ENTRYPOINT = program, CMD = default args. Run args / ECS command replace CMD.
  • Exec form (JSON array) so signals reach your app.
  • Scripts end with exec "$@"-style handoff.

Layer caching and instruction order

BuildKit reuses a layer if the instruction and its inputs haven't changed. Once one layer changes, every layer after it is rebuilt. So put things that rarely change (OS packages, dependencies) at the top and things that change on every commit (your code) at the bottom.

Bad vs good orderDockerfile
FROM python:3.13-slim
WORKDIR /app
COPY . .                                  # any file change busts the cache
RUN pip install -r requirements.txt       # reinstalled on every commit

Cache rules worth knowing

  • RUN apt-get update alone is cached forever, so a later apt-get install may use stale lists. Always apt-get update && apt-get install -y … && rm -rf /var/lib/apt/lists/* in one RUN.
  • --no-cache rebuilds everything; --pull fetches a newer base image.
  • In CI, runners start empty. Use a remote cache: --cache-to type=registry,ref=…:cache,mode=max --cache-from type=registry,ref=…:cache (ECR supports this) or type=gha in GitHub Actions.
  • A cache miss rebuilds that layer and all layers after it.
  • Order: base → OS packages → dependency manifests → install → code.
  • Use registry or GHA cache in CI.

Multi-stage builds and small images

A multi-stage build uses one stage with compilers and build tools to produce artefacts, then copies only the results into a clean, small final stage. Smaller images pull faster (faster Fargate starts and Lambda cold starts), cost less in ECR and have fewer CVEs.

Production Python image with uv, multi-stage, non-rootDockerfile
# syntax=docker/dockerfile:1
ARG PY=3.13

# ---------- build stage ----------
FROM python:${PY}-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:0.9 /uv /usr/local/bin/uv
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy UV_PYTHON_DOWNLOADS=never
WORKDIR /app
# install deps only (cached until the lockfile changes); cache mount keeps uv's download cache between builds
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --frozen --no-install-project --no-dev
COPY src/ ./src/
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv uv sync --frozen --no-dev

# ---------- runtime stage ----------
FROM python:${PY}-slim AS runtime
RUN groupadd -g 1000 app && useradd -u 1000 -g app -m app
WORKDIR /app
COPY --from=builder --chown=app:app /app /app
ENV PATH="/app/.venv/bin:$PATH" PYTHONUNBUFFERED=1
USER app
ENTRYPOINT ["python", "-m", "src.job"]

The localhost trap

  • Inside a container, localhost is the container itself, not your laptop.
  • To reach a service on your laptop from a container: host.docker.internal (Desktop; on Linux add --add-host=host.docker.internal:host-gateway).
  • A server inside a container must bind 0.0.0.0, not 127.0.0.1, or published ports and load balancers can't reach it. AgentCore Runtime explicitly requires host 0.0.0.0.
  • -p 8080:80 binds on all host interfaces; -p 127.0.0.1:8080:80 keeps it private to your machine.
On AWS: awsvpc mode

On Fargate (and recommended on EC2) every task gets its own ENI with a private IP in your subnet and its own security group. Containers in the same task share that ENI and talk over localhost (sidecar pattern). Port mapping is 1:1: containerPort = hostPort. Different tasks find each other through a load balancer, Service Connect or Cloud Map DNS.

  • User-defined networks give DNS by container name; the default bridge doesn't.
  • localhost in a container = that container. Bind servers to 0.0.0.0.
  • awsvpc: one ENI + SG per task; containers in a task share localhost.

Tagging strategy and digests

A tag is a pointer you choose; a digest is the content hash. Good tags tell you what code is running; digests guarantee it never changes underneath you.

Tag styleExampleUse
Git SHAsales-etl:3f9a1c2Every CI build. Traceable to a commit.
SemVersales-etl:1.4.0Releases. Immutable.
Environmentsales-etl:prodAvoid as the deploy reference (moves silently). OK as a human pointer.
latestsales-etl:latestNever in task definitions. You can't tell what's running or roll back.

ECS resolves a tag to a digest when a deployment starts and pins tasks to it (version consistency), so all tasks in a deployment run identical bits even if the tag later moves. Lambda also stores the digest at deploy time; pushing a new image to the same tag does not update the function until you call update-function-code.

"I tag every build with the git SHA and releases with SemVer in an immutable ECR repo, and deploy by explicit tag or digest. Never latest, so rollback is just pointing the service back at the previous task definition revision."

ECS building blocks

Amazon ECS (Elastic Container Service) is AWS's own container orchestrator. You describe what to run in a task definition, and ECS runs it as tasks on capacity (Fargate or EC2) inside a cluster. A service keeps N tasks running forever; a standalone task runs once and exits.

A logical grouping of capacity and workloads (e.g., data-prod). Free; you pay for what runs in it.
Task definition
JSON blueprint: one or more containers + CPU/memory + roles + networking. Each change creates a new revision (family:revision).
Task
A running instance of a task definition. All its containers share the network (ENI) and are scheduled together. Equivalent of a Kubernetes pod.
Service
Keeps desiredCount tasks running, replaces failures, registers with load balancers, does rolling or blue/green deployments, and auto scales.
Capacity provider
Where tasks run: FARGATE, FARGATE_SPOT, an EC2 Auto Scaling group, or Managed Instances. A strategy can mix them (e.g., base 1 on FARGATE, rest 3:1 on FARGATE_SPOT).

On EC2 instances, the ECS agent talks to the control plane. Fargate hides it.

Fields people get wrong

  • cpu/memory: on Fargate, set at task level and must be a valid combination (e.g., 2048 CPU units = 2 vCPU allows 4–16 GB).
  • essential: if an essential container exits, the whole task stops. Sidecars that may exit should be false.
  • dependsOn: start order between containers (START, COMPLETE, SUCCESS, HEALTHY), e.g., run a migration container to SUCCESS before the app.
  • secrets are injected as env vars at start. Rotating a secret needs a new deployment/task to pick it up.
  • healthCheck: the Dockerfile HEALTHCHECK is ignored; define it here (requires a shell/binary such as curl in the image).
  • Task definition = docker run flags in JSON + roles + networking.
  • Override command/environment per run with --overrides.
  • Revisions are immutable; deploy by revision.

Task role vs task execution role

This is the single most asked ECS interview question. The execution role is used by ECS itself to start your task. The task role is used by your code while it runs.

Task execution role

Assumed by the ECS agent / Fargate before your container starts.

  • Pull the image from ECR
  • Create log streams and write to CloudWatch Logs
  • Fetch values for secrets from Secrets Manager / SSM (and KMS decrypt)

Usually AmazonECSTaskExecutionRolePolicy + secret read permissions.

Task role

Assumed by your application through the container credentials endpoint (AWS_CONTAINER_CREDENTIALS_RELATIVE_URI), which boto3 finds automatically.

  • Read s3://raw/…, write s3://curated/…
  • Start a Glue job, query Athena, put to SQS, call Bedrock

Least-privilege, per workload.

The execution role is the stage crew: they set up the stage, bring in the props (image) and switch on the microphones (logs, secrets). The task role is the actor's own badge for what they may do during the performance.

Classic failures
  • CannotPullContainerError ... not authorized or ResourceInitializationError: unable to pull secrets → fix the execution role (or network route to ECR/Secrets Manager).
  • AccessDenied from boto3 inside your logs → fix the task role.

"The execution role is for ECS to launch the task: pull from ECR, push logs, resolve secrets. The task role is what the application's AWS SDK uses at runtime, like reading S3 or starting a Glue job. If the task never starts it's usually the execution role or networking; if the app gets AccessDenied it's the task role."

  • Execution role = start the task (ECR, logs, secrets). Task role = app permissions.
  • Never put access keys in env vars; the SDK gets task-role credentials automatically.

EC2 capacity and Managed Instances

Sometimes Fargate isn't enough: you need a GPU, 400 GB of RAM, local NVMe, or you run so many small tasks that packing them onto big instances is cheaper. ECS gives you two EC2 options: self-managed (your Auto Scaling group) and ECS Managed Instances (AWS runs the EC2 fleet for you).

Self-managed EC2 capacity

  • Launch instances from the ECS-optimized AMI (Bottlerocket or Amazon Linux 2023) in an Auto Scaling group with the cluster name in user data.
  • Attach the ASG through a capacity provider with managed scaling (target capacity, e.g. 90%) so ECS adds instances when tasks are pending, and managed termination protection so it doesn't kill busy instances.
  • Placement strategies: binpack (cost), spread (availability across AZs), random. Constraints: distinctInstance, attribute expressions (e.g., instance type = g5.*).
  • Network modes: awsvpc (recommended; enable ENI trunking for density), bridge with dynamic host ports, host.
  • You own AMI updates, patching, draining (DRAINING state) and right-sizing.
  • Daemon scheduling strategy: one task per instance (log/metrics agents).

ECS Managed Instances (since Sept 2025)

  • You give instance requirements (vCPU/memory ranges, GPU, families) or let ECS choose. ECS launches, places multiple tasks per instance, and terminates idle instances.
  • AWS patches by replacing instances on a regular cycle (respecting your maintenance settings), running Bottlerocket.
  • Pricing: EC2 instance price + a management fee; works with Savings Plans/Reserved pricing for the EC2 part.
  • Supports GPUs, Trainium/Inferentia, instance store. Best of both: EC2 choice, Fargate-like operations.

Express Mode is the fastest way to put a containerised web app or API on AWS. You give it an image, a port, a health-check path and two IAM roles; ECS creates a Fargate service, an Application Load Balancer with HTTPS and an AWS-provided URL, auto scaling, security groups and networking, all as normal resources in your account. ECS networking, load balancing and Service Connect

In awsvpc mode, each task is a first-class member of your VPC with its own IP and security group. Traffic reaches tasks through a load balancer (from users) or Service Connect (from other services).

Load balancers

  • ALB (HTTP/HTTPS, path/host routing) or NLB (TCP/UDP, static IPs). Target group target type must be ip for awsvpc/Fargate.
  • Task SG allows the container port only from the ALB's security group.
  • healthCheckGracePeriodSeconds on the service stops slow-starting apps being killed during warm-up.
  • Deregistration delay (default 300 s) — lower it (30–60 s) for faster deployments of stateless APIs.

Service-to-service

  • Service Connect: ECS injects an Envoy-based proxy; services call each other by short names (http://orders:8080) with retries, outlier detection and per-call metrics. Uses a Cloud Map namespace. Recommended default.
  • Service discovery (Cloud Map DNS): A/SRV records per task, no proxy.
  • VPC Lattice: cross-VPC/cross-account service networking with auth policies.
  • One ENI + SG per task; target type ip.
  • Private subnets + NAT or endpoints (ECR API, ECR DKR, S3 gateway, Logs, Secrets).
  • Service Connect for service-to-service calls.

ECS cost optimisation

Container bills come from compute size × time, plus NAT data processing, load balancers and logs. Most savings come from right-sizing, ARM, Spot and not paying NAT for ECR pulls.

  1. Right-size: run docker stats locally and check Container Insights; most tasks are over-provisioned 2–4x on memory.
  2. Graviton (ARM64): ~20% cheaper on Fargate; build multi-arch.
  3. Fargate Spot for retryable batch and workers (~70% off). Capacity provider strategy: base on FARGATE, weight on FARGATE_SPOT.
  4. Compute Savings Plans cover Fargate and Lambda.
  5. VPC endpoints for ECR/S3/Logs instead of NAT gateway data charges on every image pull; S3 gateway endpoint is free.
  6. Smaller images = shorter pull time = less billed time for short tasks.
  7. Scale to zero queue workers; schedule dev services off at night.
  8. Log retention: set CloudWatch retention (e.g., 30 days) and avoid DEBUG in prod.
  9. Share ALBs across services with host/path rules (Express Mode does this).
  • Right-size, ARM, Spot, Savings Plans.
  • Endpoints instead of NAT for pulls; set log retention.

import json, urllib.parse, boto3, pyarrow.parquet as pq, io
s3 = boto3.client("s3")          # created once per execution environment (reused on warm starts)
REQUIRED = {"order_id", "order_ts", "amount"}

def lambda_handler(event, context):
    rec = event["Records"][0]["s3"]
    bucket, key = rec["bucket"]["name"], urllib.parse.unquote_plus(rec["object"]["key"])
    body = s3.get_object(Bucket=bucket, Key=key)["Body"].read()
    cols = set(pq.read_schema(io.BytesIO(body)).names)
    missing = REQUIRED - cols
    if missing:
        s3.copy_object(Bucket=bucket, Key=f"quarantine/{key}", CopySource={"Bucket": bucket, "Key": key})
        return {"status": "rejected", "missing": sorted(missing)}
    return {"status": "ok", "columns": len(cols)}

Container security checklist

Container security has four layers: what's in the image, how it runs, what it can reach, and who can change it. Healthcare and pharma clients audit all four.

1. The image

  • Minimal, pinned base (python:3.13-slim, distroless or Chainguard); rebuild weekly to pick up patches.
  • Multi-stage: no compilers, git, curl or tests in the runtime image.
  • Scan in CI (Docker Scout, Trivy, Grype) and in ECR (Inspector enhanced scanning). Fail the build on CRITICAL with a fix available.
  • No secrets in layers. Check with docker history --no-trunc; use secret mounts.
  • Generate an SBOM and provenance (--sbom=true --provenance=mode=max); sign images (Notation with AWS Signer, or cosign) and verify at deploy.

2. The runtime

  • Run as non-root (USER 1000).
  • Read-only root filesystem + a writable /tmp volume.
  • Drop Linux capabilities (--cap-drop ALL; ECS linuxParameters.capabilities.drop), no --privileged.
  • Never mount /var/run/docker.sock into a container.
  • Set memory limits and PID limits so one bad job can't starve the host.
  • Prefer Fargate/Lambda (microVM per task) for untrusted or multi-tenant code.

3. The network and IAM

  • Tasks in private subnets; SGs allow only what's needed (ALB SG → task port).
  • One task role per workload, scoped to exact buckets/prefixes, KMS keys and actions.
  • Secrets from Secrets Manager/SSM via the secrets block.
  • VPC endpoints with endpoint policies; ECR repository policies restricted to your org.

4. The supply chain

  • Immutable tags; deploy by digest from CI only (no laptop pushes to prod repos).
  • GitHub Actions with OIDC to AWS (no long-lived keys); pin actions by SHA.
  • Pull-through cache instead of pulling directly from public registries in prod.
  • GuardDuty Runtime Monitoring for ECS/EKS detects suspicious container behaviour.

Project 1: Scheduled Fargate ETL job

Goal: a containerised Python job (Polars/pandas) that reads yesterday's raw files from S3, cleans them and writes partitioned Parquet to the curated bucket, every night at 02:00, with alerts on failure. This is the most common container workload in data engineering.

import argparse, datetime as dt, logging, os, sys, json
import polars as pl

logging.basicConfig(level=os.getenv("LOG_LEVEL", "INFO"), format='{"level":"%(levelname)s","msg":"%(message)s"}')
RAW, CURATED = os.environ["RAW_BUCKET"], os.environ["TARGET_BUCKET"]

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--run-date", default="yesterday")
    a = ap.parse_args()
    d = (dt.date.today() - dt.timedelta(days=1)) if a.run_date == "yesterday" else dt.date.fromisoformat(a.run_date)
    src = f"s3://{RAW}/sales/dt={d}/*.csv"
    df = (pl.scan_csv(src)
            .filter(pl.col("amount") > 0)
            .with_columns(pl.col("order_ts").str.to_datetime(), pl.lit(str(d)).alias("dt"))
            .unique(subset=["order_id"]))
    out = f"s3://{CURATED}/sales/dt={d}/part-0.parquet"     # overwrite = idempotent rerun
    df.sink_parquet(out)
    logging.info(json.dumps({"run_date": str(d), "output": out}))

if __name__ == "__main__":
    try:
        main()
    except Exception:
        logging.exception("job failed"); sys.exit(1)

Common errors and fixes

Most container incidents come from a short list of errors. Recognise the message, know the three likely causes, check them in order.

exec /usr/local/bin/python: exec format error

Image architecture doesn't match the host: arm64 image (built on an M-series Mac) running on x86 Fargate, or vice versa. Fix: --platform linux/amd64, a multi-arch build, or set runtimePlatform.cpuArchitecture to match. For AgentCore it must be arm64.

CannotPullContainerError: ... i/o timeout / failed to resolve ref
  • No route to ECR: private subnet without NAT or without ecr.api + ecr.dkr + S3 gateway endpoints; or public subnet with assignPublicIp=DISABLED.
  • Endpoint security group doesn't allow 443 from the task SG.
  • Tag doesn't exist (typo, lifecycle policy expired it).
CannotPullContainerError: ... 403 Forbidden / not authorized

Execution role missing ECR permissions, repo policy denies cross-account access, or KMS key policy doesn't allow decrypting a KMS-encrypted repo.

ResourceInitializationError: unable to pull secrets or registry auth

Execution role lacks secretsmanager:GetSecretValue/ssm:GetParameters/kms:Decrypt, wrong secret ARN or JSON key, or no network route to Secrets Manager/SSM endpoints.

OutOfMemoryError: Container killed due to memory usage (exit 137)

Raise task memory or fix the code: stream/chunk instead of loading whole files (Polars lazy scan_*, pandas chunksize, pyarrow datasets), drop unused columns early, avoid copying DataFrames. Use docker stats locally to measure peak usage.

Essential container in task exited

The generic "the main container stopped" reason. Look at the container's exitCode and CloudWatch logs. If logs are empty, the process died before logging: wrong entrypoint, missing env var at import time, or permissions on a read-only filesystem.

Tasks keep cycling: failed ELB health checks
  • App binds 127.0.0.1 instead of 0.0.0.0.
  • Health check path wrong or returns 3xx/401.
  • Task SG doesn't allow the ALB SG on the container port.
  • Slow start: increase healthCheckGracePeriodSeconds.
service was unable to place a task because no container instance met all of its requirements

EC2 capacity: not enough CPU/memory/ports/ENIs on instances, or placement constraints too strict. Use a capacity provider with managed scaling, enable ENI trunking, or move to Fargate/Managed Instances.

Read-only file system errors

readonlyRootFilesystem is on and the app writes to its own directory or ~/.cache. Mount a volume at /tmp and set HOME, MPLCONFIGDIR, XDG_CACHE_HOME etc. to it.

ModuleNotFoundError only in the container

Dependency in your local venv but not in requirements/lockfile; venv not on PATH in the runtime stage; or a .dockerignore excluded a source folder. Run docker run --rm -it --entrypoint sh img and look.

Docker Hub toomanyrequests: You have reached your pull rate limit

CI pulls anonymously from Docker Hub. Use ECR pull-through cache or ECR Public mirrors (public.ecr.aws/docker/library/python), or authenticate.

Build is slow / reinstalls everything every time

Wrong instruction order, COPY . . before dependency install, no .dockerignore, or CI without a remote cache. See the caching lesson.

Lambda: Runtime.InvalidEntrypoint or Runtime.ExitError

Custom base image without awslambdaric, wrong CMD handler string, image built for the wrong architecture, or the code writes outside /tmp.

  • Architecture mismatch → exec format error.
  • Pull errors → network route or execution role.
  • Health-check cycling → 0.0.0.0, path, SGs, grace period.

2. High-level design

3. Deep dives

  • Contract: each team provides an image and a job.yaml (cpu, memory, timeout, schedule, trigger, IAM permissions requested). A platform pipeline turns it into a Batch job definition, a job role and a schedule via CDK/Terraform.

  • Step Functions vs MWAA: SFN for event-driven, per-execution state; Airflow for complex DAG dependencies and backfills.

Design: real-time ingestion API with workers

Prompt: "Partners POST up to 5,000 events/second. Store them durably, process them into the lake within 5 minutes, and survive spikes of 10x."

  1. Ingest: API Gateway (auth, throttling) → either direct service integration to Kinesis Data Streams / SQS, or an ECS Fargate API behind an ALB that validates and writes to Kinesis. Keep the front door thin and stateless; scale on requests per target.
  2. Buffer: Kinesis (ordering per partition key, replay) or SQS (simpler, per-message). The buffer absorbs 10x spikes so workers scale calmly.
  3. Process: ECS service workers (or Lambda with batch windows) consuming the stream, writing micro-batches to S3/Iceberg every minute; or Firehose straight to S3/Iceberg tables if no custom logic.
  4. Scale: workers on backlog/iterator age; API on CPU/requests; Spot for workers, On-Demand base for the API.
  5. Durability: acknowledge the client only after the buffer write succeeds; DLQ for poison messages; idempotent writes keyed on event ID.
  6. Ops: alarms on iterator age > 2 min, 5xx rate, DLQ depth; blue/green deploys for the API with circuit breaker.

"I separate the stateless front door from processing with a durable buffer. The API tier on Fargate scales on request count, Kinesis absorbs spikes, and a worker service scales on iterator age and writes micro-batches to Iceberg. Every hop is idempotent on event ID, so retries are safe."

  • Thin API → durable buffer → scalable workers → lake.
  • Scale each tier on its own signal; idempotency everywhere.

Design questions: quick answers

How do you reduce Fargate task start time for a job that runs every 5 minutes?

Smaller image (slim, multi-stage), ECR in the same Region with VPC endpoints, SOCI index for lazy loading large images, avoid heavy init at startup. If still too slow, keep a long-running service polling a queue instead of a task per run, or use Lambda.

How do you run the same job in dev, test and prod?

One image promoted by digest across accounts (ECR replication or cross-account pull); environment config via env vars/SSM per account; IaC parameterised per environment.

How do containers in ECS get AWS credentials?

The task role. ECS exposes a credentials endpoint (169.254.170.2 + AWS_CONTAINER_CREDENTIALS_RELATIVE_URI); SDKs fetch and refresh temporary credentials automatically.

Multi-Region DR for a containerised service?

ECR cross-Region replication, IaC deployable to both Regions, data replicated (S3 CRR, Aurora Global), Route 53 failover/latency routing, warm standby with min tasks in the secondary Region.

How would you migrate a cron job on an EC2 box to containers?

Containerise the script with pinned deps, externalise config/secrets, make it idempotent and log to stdout, push to ECR, run as a Fargate RunTask from EventBridge Scheduler with alerts; run both in parallel for a few days comparing outputs; then retire the box.

Sidecar use cases in ECS?

FireLens log router, ADOT collector for metrics/traces, Envoy (Service Connect), a proxy for a vendor API, or an init container (dependsOn SUCCESS) that downloads reference data before the main container starts.

Question bank: Docker fundamentals

Open each question, answer out loud first, then compare.

What is the difference between an image and a container?

An image is an immutable, layered template (filesystem layers + config). A container is a running (or stopped) instance of an image with its own writable layer, namespaces and cgroup limits. Many containers can run from one image.

Container vs virtual machine?

A VM virtualises hardware and runs its own kernel; a container is an isolated process sharing the host kernel, isolated by namespaces and limited by cgroups. Containers are smaller and start faster; VMs give stronger isolation. Fargate and Lambda combine both by running containers in Firecracker microVMs.

Explain image layers and caching.

Each RUN/COPY/ADD creates a read-only layer identified by a content hash. On rebuild, BuildKit reuses layers whose instruction and inputs are unchanged; after the first changed layer, everything below is rebuilt. So order instructions from least to most frequently changing: base, OS packages, dependency manifest + install, then code.

CMD vs ENTRYPOINT?

ENTRYPOINT is the executable; CMD supplies default arguments (or the command when no ENTRYPOINT). Arguments to docker run or ECS command replace CMD; --entrypoint / ECS entryPoint replace ENTRYPOINT. Use exec form so the app is PID 1 and receives SIGTERM.

COPY vs ADD?

COPY copies files from the build context. ADD also extracts local tar archives and can fetch URLs. Prefer COPY for clarity and security; use ADD only for tar extraction or checksum-verified downloads.

ARG vs ENV?

ARG exists only during the build (set with --build-arg) and isn't in the runtime environment, though values can appear in image history. ENV persists into the image and running containers. Neither is safe for secrets: use BuildKit secret mounts at build and Secrets Manager at runtime.

How do you make an image smaller?

Slim base, multi-stage builds, combine RUN steps and clean package caches in the same layer, --no-cache-dir, a strict .dockerignore, no test/notebook/data files, and analyse with docker history or dive.

What is a multi-stage build?

A Dockerfile with several FROM stages. Early stages compile or install with full toolchains; the final stage copies only the artefacts (e.g., a venv) into a minimal base. Result: small, secure runtime images without build tools.

Volumes vs bind mounts?

Named volumes are managed by Docker and portable, ideal for database data. Bind mounts map a specific host path, ideal for live code editing and local config. tmpfs keeps data in memory. In AWS, persist to S3/EFS/databases because tasks are ephemeral.

How do containers talk to each other?

On a user-defined bridge network (Compose creates one) containers resolve each other by service/container name. Outside access needs published ports. In ECS awsvpc, containers in a task share localhost; across tasks use a load balancer, Service Connect or Cloud Map.

What does exit code 137 mean?

SIGKILL (128 + 9), usually the OOM killer because the container exceeded its memory limit, or the container didn't stop within the timeout after SIGTERM. Check OOMKilled in docker inspect or the ECS stopped reason.

Why should a container run one process / why log to stdout?

One main process per container keeps lifecycle, scaling and health simple; the orchestrator restarts or replaces it as a unit. Logging to stdout/stderr lets the platform (awslogs, FireLens, Lambda) collect logs without agents or files inside the container.

What is the containerd / runc relationship?

containerd manages images and container lifecycles; runc is the low-level OCI runtime that creates namespaces and cgroups and starts the process. Docker's daemon sits on top of containerd; ECS, Fargate and Kubernetes talk to containerd directly.

How do you build images for Graviton from an Intel CI runner?

docker buildx build --platform linux/arm64 (QEMU emulation) or, faster, use native arm64 runners; push a multi-arch index with both platforms so the same tag works everywhere.

What's in a .dockerignore and why does it matter?

It excludes files from the build context: .git, venvs, data, notebooks, tests, .env and credentials. Benefits: faster builds, better caching, smaller images and no leaked secrets.

Question bank: AWS containers

Task role vs task execution role?

Execution role: used by ECS/Fargate to start the task — pull from ECR, write CloudWatch logs, resolve secrets. Task role: used by the application at runtime through the credentials endpoint for S3, Glue, Athena, Bedrock and so on.

ECS vs EKS?

ECS is AWS-native, simpler, with a free control plane and deep integration. EKS is managed Kubernetes: portable, huge ecosystem (Helm, operators), more complexity and a control-plane fee. Choose EKS if the organisation is standardised on Kubernetes or needs its ecosystem; otherwise ECS.

Fargate vs EC2 launch type?

Fargate: serverless, per-task microVM, no instance management, max 16 vCPU/120 GB, no GPUs or privileged mode. EC2: you choose instances (GPUs, large memory), can bin-pack for cost, but you manage AMIs, patching and scaling — unless you use ECS Managed Instances, where AWS manages the EC2 fleet.

Lambda vs Fargate for a data job?

Lambda for event-driven work under 15 minutes and 10 GB memory with spiky concurrency; Fargate for long-running or heavier single-node work, custom runtimes and steady workers. Same image can serve both with different entrypoints.

How do you run a scheduled container job on AWS?

EventBridge Scheduler targeting ECS RunTask (Fargate), or Step Functions with ecs:runTask.sync when part of a pipeline, or MWAA's EcsRunTaskOperator. Alert on task STOPPED with non-zero exit via EventBridge.

Tasks in a private subnet can't pull images. Why?

No route to ECR: they need a NAT gateway or VPC interface endpoints for ecr.api and ecr.dkr plus an S3 gateway endpoint (layers live in S3), and logs for CloudWatch. Also check endpoint SGs allow 443 and the execution role has ECR permissions.

How are secrets provided to ECS tasks?

The secrets section references Secrets Manager or SSM Parameter Store ARNs; the execution role fetches them at start and injects env vars. For rotation during long tasks, fetch at runtime with the SDK and cache.

Explain an ECS rolling deployment and the circuit breaker.

ECS starts new tasks up to maximumPercent, waits for health checks, then stops old ones while keeping minimumHealthyPercent. The deployment circuit breaker detects tasks that fail to reach steady state and, with rollback enabled, returns to the last good revision.

How do you scale an ECS service processing SQS messages?

Application Auto Scaling with target tracking on backlog per task (visible messages ÷ running tasks) or step scaling on queue depth; min can be 0. Workers use long polling, idempotent processing, a visibility timeout longer than processing time, and a DLQ.

What is Fargate Spot and when would you use it?

Spare Fargate capacity at up to ~70% discount, interruptible with a 2-minute SIGTERM warning. Use for fault-tolerant batch jobs and queue workers with checkpointing/idempotency; mix with On-Demand via capacity provider strategy.

What is ECS Express Mode?

A simplified way (Nov 2025) to deploy a containerised web app: give an image, port and two roles; ECS creates a Fargate service, ALB with HTTPS URL, auto scaling and networking in your account at no extra charge. AWS's recommended replacement for App Runner.

What does AgentCore Runtime require from a container?

ARM64 image in ECR, listening on 0.0.0.0:8080 with POST /invocations and GET /ping (optionally /ws). Each session runs in an isolated microVM.

How does a Lambda container image differ from a regular image?

It must implement the Lambda Runtime API (AWS base images include the runtime interface client), max 10 GB, stored in ECR, filesystem read-only except /tmp, and it's invoked per event with a 15-minute limit. Test locally with the Runtime Interface Emulator.

How do you debug a running Fargate task?

ECS Exec (aws ecs execute-command) via SSM, after enabling execute-command on the service and granting ssmmessages permissions to the task role; plus CloudWatch logs, stopped reasons, service events and Container Insights.

When would you use AWS Batch instead of ECS directly?

When you have large numbers of jobs needing queues, priorities, fair share across teams, array jobs, automatic retries based on exit codes, and compute that scales to zero, including GPU or Spot fleets.

Scenario questions

"Your nightly Fargate job started failing with exit code 137 after the data doubled. What do you do?"

Confirm OOM in stopped reason/Container Insights. Short term: raise task memory (next valid size) and rerun the failed date (idempotent). Long term: make the job stream data (Polars lazy, chunked reads, column pruning), partition the work into parallel tasks or Batch array jobs, or move the transform to Glue/EMR if it's becoming distributed-scale. Add a memory alarm at 80%.

"A deployment works on your laptop but tasks fail with exec format error."

Architecture mismatch from building on Apple Silicon. Build with --platform matching runtimePlatform, or produce a multi-arch image in CI on native runners; prefer ARM64 Fargate for cost.

"CI builds take 15 minutes. Speed them up."

Reorder Dockerfile for caching, add .dockerignore, use cache mounts for pip/uv, enable a registry or GHA cache, build on native architecture instead of QEMU, use slim bases, run tests in parallel stages with --target.

"Costs for container workloads jumped 3x this month."

"An ECS API service keeps restarting every couple of minutes."
