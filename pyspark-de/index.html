Foundations

What Spark is and why it wins

Spark is a distributed compute engine: it splits data into partitions, ships your code to many machines, runs it in parallel and keeps intermediate data in memory instead of writing to disk between every step like MapReduce did.

The four things to say in one breath

  • In-memory, DAG-based execution. Spark plans the whole pipeline as a directed acyclic graph and only writes to disk at shuffle boundaries.
  • Lazy evaluation. Transformations build a plan; nothing runs until an action. That lets the optimizer reorder, prune and push filters down.
  • One engine, many workloads. Batch (DataFrame/SQL), streaming (Structured Streaming), ML (MLlib), graph.
  • Fault tolerance through lineage. A lost partition is recomputed from its parent partitions rather than replicated.

PySpark specifically

PySpark is the Python API. Your Python code runs on the driver and talks to the JVM through Py4J. DataFrame operations are translated into JVM plans, so they run at JVM speed. Only Python UDFs and RDD lambdas actually run Python on executors (in separate Python worker processes), which is why they are slower.

Interview: Why is Spark faster than MapReduce?

MapReduce writes every map and reduce output to HDFS and launches a new JVM per task. Spark keeps intermediate results in memory, reuses executor JVMs for the whole application, pipelines narrow transformations into a single stage, and optimizes the whole DAG (Catalyst + whole-stage code generation). Disk is only touched for shuffle files, spills and explicit persistence.

Interview: Is PySpark slower than Scala Spark?

For DataFrame/SQL code, no meaningful difference: both compile to the same physical plan in the JVM. The gap appears with Python UDFs and RDD operations, where rows must be serialized to Python workers and back. Pandas UDFs (Arrow) close most of that gap; built-in functions close all of it.

Foundations

Architecture: driver, executors, cluster manager

Driver
Runs your main, builds the logical plan, splits it into jobs → stages → tasks, schedules tasks, tracks block locations and receives results from actions like collect(). One per application. If the driver dies, the application dies.
Executor
A JVM process on a worker node. Has a fixed number of cores (task slots) and heap. Runs tasks, caches data, writes shuffle files. Lives for the application’s lifetime (unless dynamic allocation removes it).
Cluster manager
Allocates containers: YARN on EMR on EC2, a managed equivalent on Glue and EMR Serverless, Kubernetes on EMR on EKS.
SparkSession
Entry point since 2.0. Wraps SparkContext, SQLContext and HiveContext. In Glue you get it from GlueContext.spark_session.
Task
One unit of work on one partition. Number of tasks in a stage = number of partitions.
Core / slot
One task runs on one core. Parallelism = executors × cores per executor.

Interview: What happens when you run spark-submit?
  1. The driver starts (locally in client mode, in a container in cluster mode) and creates the SparkSession.
  2. The driver asks the cluster manager for executors; containers launch and register with the driver.
  3. Your code builds a logical plan lazily. On an action, Catalyst optimizes it into a physical plan.
  4. The DAGScheduler cuts the plan into stages at shuffle boundaries; the TaskScheduler sends one task per partition to free executor cores, preferring data locality.
  5. Executors run tasks, write shuffle output, report back. Next stage reads shuffle output. Results return to the driver or are written to storage.
  6. On spark.stop() or exit, executors are released.
Interview: Can one executor run tasks from two different applications?

No. Executors belong to one application. Two applications share a cluster only through the cluster manager. Inside one application, multiple jobs can run concurrently (from different threads) and share executors, scheduled by FIFO or FAIR scheduling.

Transformations, actions, lazy evaluation

A transformation returns a new DataFrame and only adds a node to the plan. An action asks for a result, which forces Spark to optimize and execute the plan.

Nothing runs until line 5pyspark
df = spark.read.parquet("s3://lake/orders/")         # reads only metadata/schema
big = df.filter("amount > 100")                       # plan node
slim = big.select("order_id", "customer_id", "amount") # plan node

agg.write.mode("overwrite").parquet("s3://out/")       # ACTION: job(s) run now

Because Spark sees the whole chain before running, the filter and column list are pushed into the Parquet scan: only 3 columns and only row groups that may contain amount > 100 are read.

Trap

Every action re-executes the lineage from the source unless something is cached. Calling df.count() for logging and then df.write reads S3 twice. In Glue jobs this is the most common hidden 2× cost.

Exceptions to “fully lazy”

spark.read with schema inference (inferSchema=True on CSV, or JSON without a schema) triggers a small job to sample data. .cache() is lazy, but the first action fills it.

Interview: Benefits of lazy evaluation?

Whole-plan optimization (predicate pushdown, column pruning, filter reordering, join reordering, constant folding), pipelining of narrow operations into one stage so data passes through once, and avoiding computation of results nobody uses.

Foundations

Narrow vs wide, jobs, stages, tasks

Narrow: each output partition depends on one input partition (filter, select, withColumn, map, union, coalesce). No data movement; Spark chains them in one stage.

Wide: an output partition needs rows from many input partitions (groupBy, join (non-broadcast), distinct, orderBy, repartition, window with partitionBy). This requires a shuffle and creates a stage boundary.

Applicationhas manyJobsone per action*Stagessplit at shufflesTasksone per partition

* An action can create more than one job (schema inference, broadcast collection, AQE re-planning, sortBy range sampling). Do not assume 1:1 in the UI.

Count the stagespyspark
orders = spark.read.parquet("s3://lake/orders/")        # 120 files -> ~120 partitions
cust   = spark.read.parquet("s3://lake/customers/")     # large, not broadcastable

res = (orders.filter("status = 'SHIPPED'")
       .join(cust, "customer_id")                       # shuffle both sides
       .groupBy("country").agg(F.sum("amount"))         # shuffle again
       .orderBy("country"))                             # range shuffle
res.write.parquet("s3://out/by_country/")

Stages: scan+filter orders, scan customers, join (reduce side of both) + partial agg, final agg, sort. Roughly 5 stages (plus a sampling job for the range partitioner). With AQE, some may be skipped or merged at runtime.

Interview: What decides the number of tasks?

The number of partitions in that stage. For file scans: total bytes ÷ spark.sql.files.maxPartitionBytes (128 MB default), adjusted by openCostInBytes and the cluster’s default parallelism. After a shuffle: spark.sql.shuffle.partitions (200 default), which AQE may coalesce. After repartition(n): n.

Interview: What is a “skipped stage” in the UI?

A stage whose shuffle output already exists from an earlier job in the same application, so Spark reuses those shuffle files instead of recomputing. Common when you run two actions on the same DataFrame that shares a shuffle.

RDD operations still asked about

reduceByKey vs groupByKey
reduceByKey combines values on the map side before the shuffle, so far less data moves. groupByKey ships every value and can OOM on hot keys.
map vs flatMap
map: 1 → 1. flatMap: 1 → 0..n, flattened.
mapPartitions
Function called once per partition with an iterator. Use it to open one DB connection per partition instead of per row.
aggregateByKey / combineByKey
General map-side combine with separate within-partition and across-partition functions.

Converting a DataFrame to RDD drops Catalyst optimization and serializes rows. Avoid in hot paths.
Interview: When would you still use an RDD?

Rarely: custom partitioning logic (partitionBy with a custom function), processing unstructured binary data, fine control over per-partition side effects, or maintaining old code. In interviews say “DataFrame first; RDD only when the DataFrame API cannot express it, and then mapPartitions to amortize setup cost.”

Partitions: the unit of parallelism

A partition is a chunk of rows processed by one task. Too few partitions waste cores and create huge tasks that spill or OOM. Too many create scheduling overhead and tiny output files.

Rule of thumb

Target 100–200 MB per partition for processing, and 2–4× the total core count as a minimum number of partitions. Output files: 128 MB–1 GB each.

Interview: Where do the initial partitions come from when reading S3?

For splittable formats (Parquet, ORC, uncompressed or bzip2 CSV) Spark packs files into partitions up to spark.sql.files.maxPartitionBytes (128 MB), counting each file as at least openCostInBytes (4 MB). Large Parquet files are split at row-group boundaries. Gzip CSV/JSON is not splittable: one file = one task, so a single 20 GB .gz file is read by one core.

Interview: How do you handle schema evolution in Parquet on S3?

Additive changes (new nullable columns) work with mergeSchema=true on read or by reading through a catalog table that has the superset schema. Type changes and renames break Parquet readers. The robust answer is a table format: Iceberg tracks columns by ID, so add/rename/drop/widen (int→long, float→double) are metadata-only operations. Interview: Is monotonically_increasing_id() a safe surrogate key?

It is unique and increasing within one run, but not consecutive (the partition ID lives in the upper bits) and not stable across runs because partitioning changes. For consecutive numbers use row_number() over a window (which pulls everything into one partition if unpartitioned) or zipWithIndex on the RDD. For stable keys use a hash of the natural key: sha2(concat_ws('||', k1, k2), 256).

Interview: How does Spark execute groupBy().sum()?

Two HashAggregate steps. Stage 1: partial_sum per input partition (map-side combine). Exchange: hash partition by the group keys. Stage 2: final sum merges the partials. If the hash map for a task does not fit memory, Spark falls back to sort-based aggregation and spills. In the plan you see HashAggregate(keys=[country], functions=[partial_sum(amount)]) then Exchange hashpartitioning(country, 200) then HashAggregate(keys=[country], functions=[sum(amount)]).

All join typespyspark

Ambiguous columns

Joining with an expression keeps both key columns, and selecting "id" afterwards fails with AMBIGUOUS_REFERENCE. Join on a column name/list, or alias both sides: o.alias("o").join(c.alias("c"), F.col("o.cust_id") == F.col("c.id")).select("o.*", "c.name").

Pitfalls that show up in production

  • Duplicate keys on the “dimension” side multiply rows. Always check c.groupBy("customer_id").count().filter("count > 1") before trusting a join.
  • Null keys never match in equi-joins. In left joins they create a hot partition of nulls with no partner (a skew source). Filter or salt them.
  • Type mismatch (string vs bigint) makes Spark cast and can break pushdown and broadcast decisions.
  • Filtering the right table in WHERE after a left join turns it into an inner join. Filter before joining or put the condition in the join.
Join hintspyspark
o.join(F.broadcast(c), "customer_id")            # force broadcast hash join
o.join(c.hint("merge"), "customer_id")           # sort merge join
o.join(c.hint("shuffle_hash"), "customer_id")    # shuffle hash join
spark.sql("SELECT /*+ BROADCAST(c) */ * FROM o JOIN c USING (customer_id)")

Strategy internals (BHJ vs SMJ vs SHJ, thresholds, what you see in plans) are in Join strategies.

Interview: left_semi vs inner join followed by select?

Semi join returns each left row at most once even if the right side has duplicates, and it never brings right columns. An inner join duplicates left rows for each match. Semi is also cheaper: it can stop after the first match. Equivalent SQL: WHERE EXISTS / IN. Anti join = NOT EXISTS, and unlike NOT IN it is not broken by NULLs on the right.

from pyspark.sql.types import StructType, ArrayType

def flatten(df, sep="_"):
    """Expand structs into columns and explode arrays until nothing nested remains."""
    while True:
        nested = [(f.name, f.dataType) for f in df.schema.fields
                  if isinstance(f.dataType, (StructType, ArrayType))]
        if not nested:
            return df
        name, dtype = nested[0]
        if isinstance(dtype, StructType):
            cols = [F.col(f"`{name}`.`{c.name}`").alias(f"{name}{sep}{c.name}") for c in dtype.fields]
            df = df.select([F.col(f"`{c}`") for c in df.columns if c != name] + cols)
        else:
            df = df.withColumn(name, F.explode_outer(F.col(f"`{name}`")))

Mention the trade-off: exploding several independent arrays multiplies rows (a cartesian product per record). In real pipelines, explode each array into its own child table keyed by the parent id.

Interview: Why are Python UDFs slow, concretely?

(1) Rows are serialized from Tungsten format, pickled, sent over a socket to a Python worker, unpickled, processed, and sent back. (2) Catalyst cannot see inside, so filters on UDF output cannot be pushed down and whole-stage codegen breaks around it (you see BatchEvalPython or ArrowEvalPython in the plan). (3) Extra memory for the Python process. Also: UDFs may be evaluated more than once per row, so they must be deterministic or marked .asNondeterministic().

Interview: Give an example where Catalyst changes your code’s order

df.join(dim, "id").filter(df.country == "IN"): Catalyst pushes the filter below the join so only Indian rows are joined, and further into the Parquet scan as PushedFilters: [EqualTo(country,IN)]. If country is a partition column it becomes PartitionFilters and whole S3 prefixes are skipped. It also prunes columns: if you only select 3 of 80 columns, only 3 are read from Parquet.

Interview: What breaks predicate pushdown?
  • Filtering on the output of a Python UDF.
  • Casting the column (CAST(dt AS DATE) = ... on a string partition column can still prune in newer versions, but functions like substring(dt,1,7) on the column usually stop file-level pushdown).
  • Non-deterministic expressions.
  • Reading via df.rdd.
  • Formats without stats (CSV, JSON) can push filters into parsing but cannot skip data blocks.
  • A cache() between the scan and the filter (the filter applies to cached data, not the source).

Interview: You see BroadcastNestedLoopJoin in a plan. What do you do?

Shuffle internals

A shuffle redistributes rows so all rows with the same key land in the same partition. It is the most expensive thing Spark does: CPU for serialization and compression, local disk for shuffle files, and network to fetch them.

What happens physically

  1. Map side (shuffle write): each task computes the target partition for every row (hash of key mod N), buffers and sorts records by partition id, spills to disk when memory fills, and finally writes one data file + one index file per map task (sort-based shuffle).
  2. The driver’s MapOutputTracker records where each map output lives.
  3. Reduce side (shuffle read): each reduce task fetches its block from every map output over the network (up to spark.reducer.maxSizeInFlight, 48 MB, at a time), merges, and continues.
Shuffle Write (UI)
Bytes written by map tasks. Big = expensive stage boundary.
Shuffle Read
Bytes fetched by reduce tasks. Uneven read per task = skew.
Spill (memory)
Size of data in memory form that had to be spilled.
Spill (disk)
Size on disk after serialization. Any spill = tasks short of execution memory.
Fetch wait time
Time reducers waited for shuffle blocks: network or slow/dead executors.
External shuffle service

With dynamic allocation, executors can be removed while their shuffle files are still needed. The external shuffle service (a process on each node, enabled on EMR) serves those files after the executor is gone. Spark 3 can instead track shuffle files (spark.dynamicAllocation.shuffleTracking.enabled) or decommission executors gracefully, migrating blocks. Losing shuffle files causes FetchFailedException and stage retries.

Choosing spark.sql.shuffle.partitions

Size each shuffle partition to roughly 100–200 MB. If the largest shuffle stage writes 300 GB: 300,000 MB ÷ 200 MB ≈ 1,500 partitions. With AQE on, set the initial number high (e.g. via spark.sql.adaptive.coalescePartitions.initialPartitionNum) and let AQE merge small partitions down to advisoryPartitionSizeInBytes (64 MB default).

Interview: How do you reduce shuffle?
  • Filter and project before wide operations (Catalyst does much of this, but not across UDFs or caches).
  • Broadcast small tables.
  • Pre-aggregate before joining (aggregate fact to the join grain first).
  • Reuse partitioning: once data is hash-partitioned by key, later joins/aggregations on the same key with the same partition count skip the Exchange.
  • Bucketing for tables joined repeatedly on the same key.
  • Avoid unnecessary repartition, distinct and orderBy (sorting the final output is rarely needed).
  • Use approx_count_distinct instead of exact distinct counts where allowed.

AQE limits
  • Skew handling only covers sort-merge (and shuffled hash) joins, not skew inside groupBy or windows. Those still need salting or two-phase aggregation.
  • It cannot help the first stage (file scan) because there is no shuffle yet.
  • It cannot fix a skew where one key is bigger than the whole executor can process in reasonable time on the non-skewed side constraints (e.g. the outer side of a left join can be split, the inner build side cannot in some join types).
  • It does not apply to streaming queries.
Interview: AQE is on, but the job still has one slow task. Why?

Possible reasons: the skew is in an aggregation or window (not a join); the skewed partition is below the 256 MB threshold but tasks are slow because of expensive per-row work; the skew is in the scan stage (one huge non-splittable gzip file); the join type does not allow splitting that side; or the configured factor/threshold do not match the data. Check the SQL tab: if the SortMergeJoin node does not show “skewed partitions”, AQE did not act. Then salt manually or broadcast.

SQL tab: the operator graph

Each box is a physical operator with metrics. Useful ones:

  • Scan parquet: number of files read, size of files read, partitions read, metadata time. Thousands of files of a few KB = small-file problem.
  • Filter / Project: number of output rows. A filter that keeps 99% of rows is not helping.
  • Join: output rows. If output rows ≫ input rows, the join key is duplicated (row explosion).

  • AQEShuffleRead: number of partitions after coalescing, number of skewed partitions split.

  • GC time shown in red (over 10% of task time).

  • “Dead” executors list growing (OOM kills, spot interruptions on EMR).

Interview: A stage shows “Retry 1” and FetchFailedException. What happened?

Spark marks the map output lost, re-runs the parent stage for the missing partitions, then retries the reduce stage. Optimization

Partitioning, file sizes and the small-file problem

Choosing a partition column for the lake

  • Partition by what queries filter on most, usually a date (dt, event_date).
  • Low-to-medium cardinality: each partition should hold at least ~1 GB / a few hundred MB of data. Never partition by customer_id or timestamps.
  • Avoid deep nesting (year/month/day/hour/country): S3 listing time and tiny files explode.
  • For Iceberg use transforms (days(ts), bucket(16, id)) so queries filter on the raw column and still prune (hidden partitioning).

Why small files hurt

  • Each file = an S3 GET + LIST overhead + footer read; driver planning time grows with file count.
  • Each file opened adds openCostInBytes to planning, and tasks are dominated by open latency.
  • Athena and Redshift Spectrum get slow and expensive too.

How small files are created

Files written = (number of write tasks) × (partition values each task holds). 400 shuffle partitions writing a table partitioned by 30 dates can create 12,000 files per run.

Controlling output filespyspark
# 1. cluster rows of the same partition value into the same task
df.repartition("dt").write.partitionBy("dt").parquet(out)            # 1 file per dt (can be huge)

# 2. spread big days over N files each
df.repartition(F.col("dt"), (F.rand() * 8).cast("int")) \
  .write.partitionBy("dt").parquet(out)                             # ~8 files per dt

# 3. cap file size by rows
df.write.option("maxRecordsPerFile", 2_000_000).partitionBy("dt").parquet(out)

# 4. let AQE size the final shuffle partitions (writes after a shuffle)
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "256m")

# 5. Iceberg: rely on write distribution + compaction
spark.sql("ALTER TABLE glue_catalog.db.orders SET TBLPROPERTIES ('write.distribution-mode'='hash')")
spark.sql("CALL glue_catalog.system.rewrite_data_files(table => 'db.orders', options => map('target-file-size-bytes','536870912'))")
Reading many small files on Glue

DynamicFrames support grouping: connection_options={"groupFiles": "inPartition", "groupSize": "134217728"} packs small files into ~128 MB read tasks. With DataFrames, raise spark.sql.files.maxPartitionBytes and lower spark.sql.files.openCostInBytes, then compact the source.

Interview: Your S3 table has 2 million 50 KB files. Fix it.

Short term: compaction job that reads each partition and rewrites it with repartition to files of 256 MB–1 GB, swapping atomically (write to a new prefix, then repoint the Glue table/partition locations, or use Iceberg rewrite_data_files which commits atomically). Long term: fix the writer (repartition by partition column before write, fewer shuffle partitions or AQE coalescing, micro-batch interval for streaming), and migrate to Iceberg with scheduled compaction and snapshot expiry. For Kinesis Firehose sources, increase buffer size/interval.

Optimization

Data skew: detect and fix

Skew = a few keys hold a disproportionate share of rows, so a few tasks do most of the work. Symptoms: stage stuck at 199/200 tasks; Max task duration ≫ Median; one executor spilling or OOMing; same task ID failing repeatedly.

Find the hot keyspyspark
(df.groupBy("customer_id").count()
   .orderBy(F.desc("count")).show(20, truncate=False))
# frequent culprits: NULL, '', 'UNKNOWN', -1, a default merchant, a bot user_id, one giant tenant

Fixes, cheapest first

  1. Filter junk keys (nulls, placeholders) or handle them separately and union back.
  2. Broadcast the other side if it fits: no shuffle, no skew.
  3. AQE skew join (on by default): check the SQL tab shows skewed partitions being split; tune skewedPartitionFactor / skewedPartitionThresholdInBytes lower if needed.
  4. Salting for joins AQE cannot handle.
  5. Two-phase aggregation for skewed groupBy.
  6. Isolate hot keys: process the top N keys with a broadcast join and the rest normally.
Salted joinpyspark
N = 16   # salt buckets; pick from the skew ratio

# big, skewed side: random salt per row
facts_s = facts.withColumn("salt", (F.rand(seed=42) * N).cast("int"))

# other side: replicate each row N times, once per salt value
dim_s = dim.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(N)])))

joined = facts_s.join(dim_s, ["customer_id", "salt"]).drop("salt")

The hot key’s rows are spread over 16 partitions; the dimension grows 16×, so salt only when that side is moderate. Refinement: salt only hot keys (when(col.isin(hot_keys), rand*N).otherwise(0)) and replicate only those dimension rows.

Two-phase (salted) aggregationpyspark
N = 32
partial = (events.withColumn("salt", (F.rand() * N).cast("int"))
                 .groupBy("page_id", "salt")
                 .agg(F.sum("views").alias("v"), F.count("*").alias("c")))
final = partial.groupBy("page_id").agg(F.sum("v").alias("views"), F.sum("c").alias("events"))
# works for sum/count/min/max; for avg carry sum and count; distinct counts need HLL sketches
Interview: Skew in a window function partitioned by user_id. Options?

AQE does not split window partitions. Options: (1) remove bot/test users or null IDs; (2) add a second partition key that the logic allows (e.g. user_id, session_date if the window never crosses days); (3) handle the few hot users separately with a different algorithm; (4) for running totals, compute per (user, day) aggregates first, then window over the much smaller daily table and join back; (5) increase executor memory so the large partition at least spills instead of failing.

Optimization

Caching and persistence

Cache only what is reusedpyspark
from pyspark import StorageLevel

clean = raw.filter(...).withColumn(...)          # expensive lineage
clean.persist(StorageLevel.MEMORY_AND_DISK)      # df.cache() == MEMORY_AND_DISK for DataFrames
clean.count()                                    # materialize (optional, makes timing clear)

clean.filter("country = 'IN'").write.parquet(a)  # reads cache
clean.groupBy("dt").count().write.parquet(b)     # reads cache
clean.unpersist()                                # free executor memory

MEMORY_ONLYPartitions that do not fit are recomputed when needed
MEMORY_AND_DISKOverflow to local disk (DataFrame default, serialized columnar)
DISK_ONLYLocal disk only

When caching hurts
  • DataFrame used once: pure overhead.
  • Caching the raw scan before filters: you store everything and lose pushdown for later filters.
  • Huge DataFrames that evict each other and spill: slower than re-reading Parquet from S3.
  • Forgetting unpersist() in loops: storage memory fills and squeezes execution memory.

checkpoint vs cache

cache() keeps the lineage; if an executor is lost, the partition is recomputed. checkpoint() writes to reliable storage (set sc.setCheckpointDir("s3://...")) and truncates the lineage. Use it in iterative algorithms or loops where the plan grows each iteration (plans with thousands of nodes make the driver slow or throw StackOverflowError). localCheckpoint() truncates lineage using executor storage: faster, not fault tolerant.

Interview: Does df.cache() cache immediately?

No, it is lazy. It marks the plan; the first action fills the cache partition by partition. If that first action is take(5), only the partitions needed for 5 rows get cached. That is why people use count() to fully materialize. Check the Storage tab for “Fraction Cached”.

Optimization

Pushdown, pruning and dynamic partition pruning

Column pruning
Only selected columns are read from columnar files. Kills it: select("*") carried to the end, UDFs over whole structs, reading JSON/CSV.
Predicate pushdown
Filters sent into the Parquet/ORC reader to skip row groups using min/max statistics (and dictionary/bloom filters). Works best when data is sorted or clustered on the filter column.
Partition pruning
Filters on partition columns skip whole directories. Must be a filter on the partition column itself.
Dynamic partition pruning
When a partitioned fact joins a filtered dimension (fact.dt = dim.dt AND dim.is_holiday), Spark computes the qualifying dt values from the dimension at runtime and prunes the fact scan. On by default (spark.sql.optimizer.dynamicPartitionPruning.enabled). In the plan: PartitionFilters: [dynamicpruningexpression(dt IN dynamicpruning#...)].
Make row-group skipping effectivepyspark
# sort within files on a commonly filtered high-cardinality column
(df.repartition("dt").sortWithinPartitions("customer_id")
   .write.partitionBy("dt").parquet(out))
# Iceberg equivalent:
spark.sql("ALTER TABLE glue_catalog.db.orders WRITE ORDERED BY customer_id")

Unsorted data gives every row group a min/max range covering almost all IDs, so pushdown skips nothing. Sorted data makes the ranges narrow.

Debugging & failures

Playbook: a job that got slow

“Our daily Glue job used to take 40 minutes and now takes 3 hours. What do you do?” Answer as a sequence.

  1. What changed? Input volume (S3 bytes / file count per run), code deploys, Glue version/worker changes, new joins, upstream schema change, a new hot key (a big customer onboarded).
  2. Compare two runs in the Spark UI (History Server): which job and stage grew? Is the slow stage new, or the same stage with more data?
  3. Inside the slow stage: Summary Metrics. Max ≫ median → skew. All tasks slow + spill → too few partitions or too little memory. Few tasks → parallelism problem. High GC → memory pressure. Long scheduler delay / waiting → not enough executors (check auto scaling, max workers).
  4. SQL tab: files read (small-file explosion?), join output rows (row explosion from duplicate keys?), did a broadcast become sort-merge because the dim grew past 10 MB?
  5. Plan diff: explain("formatted") today vs a known-good version. Lost partition pruning (someone wrapped the date column in a function)? New Python UDF?
  6. Fix, then measure: change one thing at a time, compare stage durations.

Debugging & failures

Playbook: out-of-memory failures

First question: driver or executor? The log says which. Then: heap or overhead?

Driver OOM

  • collect(), toPandas(), take(huge) on big data. Fix: write to S3 and read the result elsewhere, or aggregate first.
  • Broadcasting a large table (the driver collects it first). Fix: lower autoBroadcastJoinThreshold, remove the hint.
  • Millions of files/partitions: file index and task metadata live in driver memory. Fix: compact, prune, bigger driver.
  • Huge query plans (hundreds of chained withColumn, loops with unions). Fix: select with a list, checkpoint.

Data correctness bugs

Silent bugs worry senior interviewers more than crashes. Know these:

  • Join row explosion: duplicate keys in a dimension. Guard: assert key uniqueness before joins.
  • Dropped rows: inner join where a left join was needed; nulls removed by != / ~isin.
  • Non-deterministic dedup: dropDuplicates keeps a random row; reruns differ.
  • Overwrite wiping partitions: static overwrite mode.
  • Duplicates on retry: append mode re-run appends twice. Make loads idempotent: overwrite partitions, or MERGE on a key.
  • Time zones: session time zone differs between jobs; date boundaries shift.
  • Decimal/float: money as double drifts; use DecimalType. Decimal overflow returns NULL in non-ANSI mode.
  • Schema drift: a new upstream column or type change silently becomes null when reading with an old schema.
  • Late data: a daily job reading only dt=today misses records that arrive late for yesterday.
Lightweight data quality gatepyspark
def assert_quality(df, key_cols, not_null_cols, min_rows):
    stats = df.agg(
        F.count("*").alias("rows"),
        F.countDistinct(*key_cols).alias("distinct_keys"),
        *[F.sum(F.col(c).isNull().cast("int")).alias(f"null_{c}") for c in not_null_cols]
    ).first().asDict()
    problems = []
    if stats["rows"] < min_rows:
        problems.append(f"row count {stats['rows']} < {min_rows}")
    if stats["distinct_keys"] != stats["rows"]:
        problems.append(f"duplicate keys: {stats['rows'] - stats['distinct_keys']}")
    problems += [f"{k}={v}" for k, v in stats.items() if k.startswith("null_") and v]
    if problems:
        raise ValueError("DQ failed: " + "; ".join(problems))
    return stats

Job bookmarks

Bookmarks track what a job already processed so the next run reads only new data: for S3 by file modification time and paths, for JDBC by a key column (monotonically increasing). Requirements: --job-bookmark-option job-bookmark-enable, job.init(), a transformation_ctx on sources, and job.commit() at the end. A failed run does not commit, so the next run re-reads the same input.

Bookmark gotchas
  • Spark DataFrame reads (spark.read) are not tracked; only Glue sources with transformation_ctx.
  • Overwriting existing S3 files with new content but same name/time can be missed.
  • Reprocessing needs a bookmark reset (aws glue reset-job-bookmark) or job-bookmark-pause with from/to run IDs.
  • Bookmarks + append-mode writes are not exactly-once if the job fails after writing but before commit(): the retry re-appends. Make the sink idempotent.

PySpark on AWS

S3 specifics: committers, consistency, throttling

  • S3 is an object store: “rename” is copy + delete. The classic Hadoop output committer renames task output into place, which is slow and not atomic on S3. Use the EMRFS S3-optimized committer (EMR), S3A magic committer (open source), Glue’s defaults, or a table format that commits via metadata (Iceberg).
  • Strong read-after-write consistency since December 2020, so the old “eventual consistency” listing issues (and EMRFS consistent view) are history. Say this; it shows you are current.
  • Request rates: about 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD per second per prefix. Many writers into one prefix or millions of tiny files trigger 503 Slow Down. Fewer, bigger files and well-spread partitions fix most cases.
  • Partial output on failure: a failed overwrite can leave a partition half-deleted with plain Parquet. Write to a staging prefix and swap the catalog location, or use Iceberg.
  • S3 URI schemes: s3:// on EMR/Glue (EMRFS), s3a:// for open-source Hadoop.

Output modes
append: only finalized rows (needs watermark for aggregations). update: changed rows each batch. complete: whole result table each batch (small aggregates only).
Triggers
processingTime="1 minute", availableNow=True (process everything available in batches, then stop: great for incremental batch on Glue), once=True (deprecated in favour of availableNow).
Checkpoint
Offsets, commits and state store. One checkpoint per query; never share. Changing the query shape (aggregation keys, stateful ops) can make the checkpoint incompatible.
Watermark
max(event time seen) − threshold. State older than the watermark is dropped; later events for those windows are discarded.
Exactly-once
Replayable source (Kafka offsets) + checkpoint + idempotent or transactional sink (Iceberg/Delta, or foreachBatch with MERGE keyed on batch id).
foreachBatch
Run any batch code per micro-batch: MERGE into Iceberg, write to Redshift/DynamoDB, multiple sinks.

Dimension columns: customer_id, name, city, start_date, end_date, is_current. Incoming daily snapshot: customer_id, name, city.

run_date = F.to_date(F.lit("2026-11-02"))
attrs = ["name", "city"]
hash_of = lambda df: F.sha2(F.concat_ws("||", *[F.coalesce(df[c].cast("string"), F.lit("~")) for c in attrs]), 256)

cur  = dim.filter("is_current").withColumn("h", hash_of(dim))
hist = dim.filter(~F.col("is_current"))

                .withColumn("end_date", F.lit(None).cast("date"))
                .withColumn("is_current", F.lit(True)))

              .unionByName(expired.drop("h")).unionByName(new_versions))
Iceberg MERGE version (what you would ship)spark sql
spark.sql("""
MERGE INTO glue_catalog.dw.dim_customer t
USING (
  -- rows to expire/insert keyed normally, plus a second copy of changed rows with NULL key to force INSERT
  SELECT s.customer_id AS merge_key, s.* FROM stg_customer s
  UNION ALL
  SELECT NULL AS merge_key, s.* FROM stg_customer s
  JOIN glue_catalog.dw.dim_customer d
    ON d.customer_id = s.customer_id AND d.is_current
   AND (d.name <=> s.name AND d.city <=> s.city) = false
) u
ON t.customer_id = u.merge_key AND t.is_current
WHEN MATCHED AND NOT (t.name <=> u.name AND t.city <=> u.city) THEN
  UPDATE SET is_current = false, end_date = date_sub(current_date(), 1)
WHEN NOT MATCHED THEN
  INSERT (customer_id, name, city, start_date, end_date, is_current)
  VALUES (u.customer_id, u.name, u.city, current_date(), NULL, true)
""")

The NULL merge_key trick makes changed customers both update (expire old row) and insert (new row) in one atomic MERGE. Unchanged rows match but fail the condition, so nothing happens. <=> is null-safe equality.

19. Idempotent incremental load using a high-water mark

Show solution
watermark in a control tablepyspark
ctl = spark.table("glue_catalog.ops.load_control").filter("table_name = 'orders'")
hwm = ctl.select("last_updated_at").first()[0]          # one small row to the driver

# 2-hour lookback catches rows committed late in the source
new =(spark.read.format("jdbc").options(**jdbc_opts)
         .option("dbtable", f"(select * from orders where updated_at > '{hwm}'::timestamp - interval '2 hours') q")
         .load())

new.createOrReplaceTempView("new_orders")
spark.sql("""MERGE INTO glue_catalog.curated.orders t
  USING (SELECT * FROM (SELECT *, row_number() OVER (PARTITION BY order_id ORDER BY updated_at DESC) rn
                        FROM new_orders) WHERE rn = 1) s
  ON t.order_id = s.order_id
  WHEN MATCHED AND s.updated_at >= t.updated_at THEN UPDATE SET *
  WHEN NOT MATCHED THEN INSERT *""")

new_hwm = new.agg(F.max("updated_at")).first()[0]
if new_hwm:   # update control table only after MERGE succeeded
    spark.sql(f"UPDATE glue_catalog.ops.load_control SET last_updated_at = TIMESTAMP '{new_hwm}' WHERE table_name = 'orders'")

Why it is idempotent: the lookback overlap plus MERGE on the key means re-running or overlapping windows never creates duplicates, and the HWM only advances after a successful write.

Interview prep

Scenario questions with model answers

Answer shape: clarify → hypothesis → evidence (UI/plan/logs) → fix → prevent. Numbers make answers credible.

1. A join between a 2 TB fact and a 40 GB dimension takes 3 hours. Walk me through it.

Evidence: SQL tab: SortMergeJoin with two Exchanges; Stages tab: max task 50× median → skew on the join key; spill on the reduce side.

Fixes in order: (1) filter both sides and select only needed columns before the join (40 GB may become 3 GB, then broadcastable with a raised threshold or AQE’s runtime switch); (2) check hot keys: null/default IDs filtered or handled separately; (3) confirm AQE skew join splits partitions, tune thresholds; (4) salt the hot keys if AQE cannot; (5) if this join runs daily, store both tables bucketed/partitioned on the key (Iceberg bucket(n, key) + storage-partitioned join) to avoid the shuffle; (6) right-size shuffle partitions (2 TB / 200 MB ≈ 10,000).

2. The Glue job fails with “Container killed … exceeding memory limits” only on month-end.

Month-end volume is larger and probably one key or partition grows disproportionately. I would open the History Server for a failed run: which stage, is the same task index failing repeatedly (data-driven) or random tasks (resource-driven)? “Killed by YARN” is off-heap: suspect Python UDFs/pandas or Arrow batches. Fixes: replace UDFs with built-ins, raise spark.executor.memoryOverhead, reduce rows per task (more shuffle partitions), move to G.2X for that run, or split month-end processing by day. Prevent: alarm on CloudWatch memory metrics and data volume; make worker type a parameter so the orchestrator can pick a larger size for month-end.

3. Daily output has 40,000 small files and Athena queries are slow.

Cause: write tasks × partition values. Fix the writer: repartition("dt") (or by dt plus a small random bucket for big days) before partitionBy("dt"), enable AQE coalescing with a larger advisory size. Compact existing data with a one-off job or Iceberg rewrite_data_files. Target 256 MB–1 GB files. Measure Athena scanned bytes and query time before/after.

4. The pipeline produced duplicate rows after a retry.

The job appended output, then failed (or Step Functions retried) before marking success, and the retry appended again. Make writes idempotent: overwrite the run’s partitions with dynamic partition overwrite, or MERGE on a business key, or write to a run-ID staging path and swap atomically. Bookmarks commit only at job.commit(), so they do not prevent duplicate output by themselves. Add a uniqueness check gate before publishing.

5. A job is fast in dev and slow in prod with the same code.

Differences to check: data volume and distribution (prod has hot keys dev lacks), file count/size (prod has small files), Glue version/worker type/count, configs in the Environment tab (AQE, shuffle partitions, broadcast threshold), broadcast decision flipping because a prod dimension is above the threshold, catalog partition count (millions of partitions slow planning), and concurrency (other jobs competing for S3 prefixes or a shared JDBC source). Compare the two Spark UIs stage by stage.

6. How would you reprocess the last 90 days after a logic bug, safely?

Parameterize the job by date range; run in chunks (e.g. 7 days per run) to bound resource use; write to the same partitions with dynamic overwrite or to an Iceberg branch/staging table, validate counts and sums against the old output, then publish (fast-forward the branch or swap). Pause downstream consumers or notify them. Throttle concurrency to avoid S3 503s and source DB load. Keep the old snapshot for rollback (Iceberg time travel).

7. Upstream added a column and changed amount from int to string. What breaks and how do you guard?

With an explicit schema, the new column is ignored and amount parses to NULL (PERMISSIVE) or fails (FAILFAST). Reading Parquet with mixed types across files can throw “column cannot be converted”. Guards: schema contract check at ingestion comparing incoming schema with the registered one (fail or quarantine on breaking changes, auto-add on additive ones), Glue Schema Registry for streams, Iceberg for safe evolution, and alerting on null-rate spikes per column.

8. Design a pipeline: clickstream JSON in S3 every 5 minutes → analytics tables for Athena.

Raw zone: S3 landing as-is, partitioned by ingest hour. Processing: Glue Spark job with availableNow streaming over the S3 source (or scheduled every 15 minutes via EventBridge/Step Functions), explicit schema, quarantine for bad records, dedup on event_id within a watermark window, sessionization in a later daily job. Storage: Iceberg tables in the Glue Catalog partitioned by days(event_ts), merge-on-read for upserts, daily compaction and snapshot expiry. Serving: Athena views; aggregates for dashboards. Ops: CloudWatch alarms on job failures and lateness, DQ checks, SNS notifications, cost tags. Mention sizing: events/day, bytes/day, files/day, expected task count.

9. Driver OOM right after the job starts, before any task runs.

Planning-time memory: listing a huge number of S3 objects or partitions, schema inference over many JSON files, a very large plan (generated SQL, loops), or broadcasting a large table built from a small-looking file. Fixes: partition predicates so fewer partitions are listed, explicit schema, catalog partition indexes / Iceberg manifests, checkpointing long lineages, raise driver memory (on Glue the driver uses a worker, so a bigger worker type), disable the broadcast.

10. How do you reduce the cost of a Glue job by 50%?

Measure first: DPU-hours per run and where the time goes. Typical wins: auto scaling instead of fixed max workers; Flex for non-urgent jobs; reading less (partition pruning, column pruning, Parquet instead of CSV); removing double reads (cache or single action); removing UDFs; fixing skew so workers are not idle waiting for one task; compacting small input files; right worker type (G.1X with more workers often beats G.2X for shuffle-light jobs); incremental processing instead of full reloads; and shorter timeouts so hung jobs do not burn DPUs.

11. Tell me about a hard Spark problem you solved. (structure)

Use STAR with numbers: Situation (pipeline, volume per run, SLA), Task (what was failing or slow, impact on consumers), Action (how you diagnosed: Spark UI stage metrics, explain plan, logs; what you changed: e.g. broadcast + salting + Iceberg compaction; why you rejected alternatives), Result (runtime 3 h → 35 min, cost per run, failure rate). Prepare two stories: one performance, one data-correctness/reliability. Keep the client-specific details at the level you are allowed to share.

12. A Step Functions workflow runs 30 Glue jobs; one fails nightly at random. How do you make it robust?

Classify the failure from logs: transient (S3 503, throttling, spot/capacity, JDBC timeouts) vs deterministic (data). Add Step Functions Retry with exponential backoff only for transient error types, Catch to a notification and a failure-state record. Make every job idempotent so retries are safe. Reduce contention (stagger jobs writing the same prefix/table, Iceberg commit retries). Track run metadata (rows in/out, duration) in a control table to spot drifts before failures.

Interview prep

Rapid-fire questions

Expect 10–15 of these in the first 15 minutes. Two to four sentences each.

cache() vs persist()?

cache() is persist() with the default level (MEMORY_AND_DISK for DataFrames, MEMORY_ONLY for RDDs). persist lets you choose the level.

repartition vs coalesce?

repartition: full shuffle, can increase or decrease, even sizes. coalesce: no shuffle, only decreases, may be uneven and reduces upstream parallelism.

What triggers a shuffle?

Wide operations: groupBy/agg, non-broadcast joins, distinct, orderBy/sort, repartition, window with partitionBy, intersect/except.

What is a broadcast variable vs a broadcast join?

A broadcast variable (sc.broadcast(obj)) ships a read-only Python/Java object to each executor once, e.g. a lookup dict for an RDD map. A broadcast join ships a small DataFrame’s hash table to every executor for a join. Same mechanism, different API.

Accumulators?

Write-only shared counters updated on executors and read on the driver. Updates inside transformations can be double-counted on task retries or recomputation; only updates in actions are guaranteed once.

What is lineage and why does it matter?

The graph of transformations that produced a dataset. Spark uses it to recompute lost partitions. Very long lineage slows planning and recovery; checkpoint to truncate.

DAG vs lineage?

Lineage is the logical dependency chain of a dataset. The DAG is the execution plan the scheduler builds from it, cut into stages at shuffle boundaries.

Why is the default 200 shuffle partitions often wrong?

It ignores data size: 200 partitions of 5 GB each spill and OOM; 200 partitions of 1 MB each waste overhead and produce tiny files. Size from data, or let AQE coalesce from a high initial number.

What does explain() show that the Spark UI doesn’t, and vice versa?

explain shows the plan before running (pushdown, join strategy, exchanges). The UI shows runtime truth: real sizes, row counts, task skew, spills, the final AQE plan.

How does Spark handle a failed task?

Retries it up to spark.task.maxFailures (4) on possibly another executor. If an executor is lost, its tasks and shuffle outputs are recomputed. If a stage’s shuffle input is lost (FetchFailed), the parent stage re-runs. After too many failures the job aborts.

What is speculative execution?

With spark.speculation=true, Spark launches duplicate copies of tasks much slower than the median and uses whichever finishes first. Helps with bad nodes, not with skew (the duplicate is just as slow). Needs idempotent output.

Dynamic allocation?

Spark requests and releases executors based on pending tasks and idle time. Needs the external shuffle service or shuffle tracking so removed executors’ shuffle files remain available.

map vs mapPartitions?

map calls your function per row; mapPartitions once per partition with an iterator, so expensive setup (connections, models) happens once per partition.

What is whole-stage code generation?

Catalyst fuses consecutive operators in a stage into one generated Java method, avoiding per-row virtual function calls and intermediate objects. Shown as *(n) in plans.

Difference between where() and filter()?

None. Aliases.

union vs unionByName?

union matches columns by position (silent bugs if order differs). unionByName matches by name; allowMissingColumns=True fills missing columns with NULL. Neither removes duplicates; add distinct() for SQL UNION semantics.

What is a temp view vs global temp view vs table?

Temp view: session-scoped name for a plan, no data stored. Global temp view: shared across sessions of one application, under global_temp. Table: registered in a catalog (Glue/Hive) with data in storage, visible to other engines.

How does Spark read a Parquet file efficiently?

Reads the footer (schema, row-group statistics), skips row groups using pushed filters, reads only needed column chunks, decodes in vectorized batches (columnar reader).

Client vs cluster deploy mode?

Client: driver runs where you submitted (logs on your console, dies with your session). Cluster: driver runs in the cluster (survives your disconnect, used for production).

Why prefer built-in functions over UDFs?

They run in the JVM inside generated code, are visible to Catalyst (pushdown, constant folding) and handle NULLs consistently. UDFs serialize every row to Python.

What does AQE do in one sentence each?

Coalesces small shuffle partitions; switches sort-merge to broadcast or shuffled hash joins at runtime; splits skewed join partitions; reads shuffle locally after a broadcast switch.

How do you handle late-arriving data in batch?

Partition by event date but process by ingestion window, reprocessing a lookback of N days with idempotent overwrite/MERGE, or use Iceberg MERGE keyed on event ID. In streaming, watermarks bound lateness.

What is the difference between narrow dependency failure and wide dependency failure recovery?

A lost partition from a narrow dependency is recomputed from one parent partition. A wide dependency may need many parent partitions, so losing shuffle data can force a whole parent stage to re-run (partially, only missing map outputs).

toPandas() on 50 GB?

Don’t. Everything goes to the driver’s memory. Aggregate or sample in Spark first; if pandas logic is needed at scale, use applyInPandas or pandas API on Spark (pyspark.pandas).

How do you test PySpark code?

Pure transformation functions that take and return DataFrames; pytest with a local SparkSession fixture (session-scoped); small hand-built DataFrames; assertDataFrameEqual (pyspark.testing, 3.5) or chispa; integration tests on a sample in a dev Glue/EMR environment; data quality checks in production.
