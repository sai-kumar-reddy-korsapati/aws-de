Why distributed computing exists

A single computer can only read so many gigabytes per second and hold so much in memory. When your data is 2 TB of orders, one machine would take hours just to read it. Distributed computing splits the data into many small pieces and gives each piece to a different computer (or CPU core) at the same time. If 200 cores each read 10 GB in parallel, the 2 TB is read in roughly the time it takes one core to read 10 GB.

Imagine you must count every vote in a city. One person counting 2 million ballots takes weeks. Instead you split the ballots into 200 boxes, give each box to a counter, and each counter writes their totals on a slip. A supervisor adds up the 200 slips. That is exactly how Spark works: the boxes are partitions, the counters are executor cores, and the supervisor is the driver.

The three hard problems Spark solves for you

  1. Splitting the work. Spark decides how to cut the input into pieces (partitions) and how many workers to use.
  2. Moving data when it has to meet. To total revenue per country, all rows for “IN” must end up on the same worker. Spark moves them over the network. This movement is called a shuffle and is the most expensive thing Spark does. You will hear this word in every interview.
  3. Surviving failures. With 200 workers, one will eventually crash. Spark remembers how each piece was produced and simply redoes the lost piece on another worker.

Where this fits in your daily work

As an AWS data engineer, your data usually lives in Amazon S3 as Parquet, JSON or CSV files, or in Iceberg tables. You write PySpark code, and a service such as AWS Glue or Amazon EMR provides the cluster of computers that runs it. You never manage the individual machines in Glue; you just choose a worker type and count.

Spark is a distributed processing engine. It splits large datasets into partitions, processes them in parallel across executor cores, moves data between machines only when an operation needs related rows together, and recovers from failures by recomputing lost partitions from their lineage.

  • Distributed = split data into pieces, process pieces at the same time, combine results.
  • Partition = a piece of data. Core = a worker that processes one piece at a time.
  • Shuffle = moving rows between machines so related rows meet. It is slow; good Spark code minimises it.

What Spark is and how PySpark fits

Apache Spark is an open-source engine for processing large amounts of data across many machines. It is written in Scala and runs on the Java Virtual Machine (JVM). PySpark is the Python way to use Spark: you write Python, and PySpark translates your instructions into work that the Spark engine runs in the JVM. For DataFrame code, the heavy lifting never happens in Python at all, which is why PySpark is just as fast as Scala Spark for most jobs.

The pieces of Spark

How Python talks to the JVM

When you start PySpark, two processes run on the driver machine: your Python program and a JVM. They talk through a bridge library called Py4J. When you write df.filter(...), Python does not filter anything; it sends a description of the filter to the JVM. The JVM builds the plan and the executors (also JVMs) do the work.

Interview: Is PySpark slower than Scala Spark?

For DataFrame and SQL code, no meaningful difference. Both produce the same plan, which runs in the JVM. PySpark is slower only when rows must go to Python: Python UDFs, RDD lambdas and collect()/toPandas() to the driver. Pandas UDFs reduce that cost using Apache Arrow; built-in functions remove it.

Interview: Why is Spark faster than MapReduce?

Spark keeps data in memory between steps instead of writing to disk after each one, reuses long-lived executor JVMs instead of starting a JVM per task, pipelines several operations into one pass over the data, and optimises the whole query before it runs (Catalyst plus generated code).

  • Spark = engine in the JVM. PySpark = Python front end that sends instructions over Py4J.
  • DataFrame code runs in the JVM at full speed. Python UDFs are the exception.
  • Spark SQL / DataFrames are what you use for almost all AWS ETL.

Architecture: driver, executors, cluster manager

Every Spark application has one driver (the boss that plans the work) and many executors (the workers that do it). A cluster manager hands out machines. On AWS Glue the cluster manager is hidden from you; on EMR it is YARN. Press Play to watch a job from start to finish.

Each role in detail

Driver
One per application. Runs your main code, keeps track of all executors and data blocks, turns your code into an execution plan, sends out tasks and collects results of actions like count() or collect(). In Glue the driver runs on one of your workers.
Executor
A JVM process on a worker machine. It has a fixed number of cores (how many tasks it can run at the same time) and a fixed amount of memory. It runs tasks, caches data you ask it to cache, and writes shuffle files to its local disk. In Glue, each worker runs one executor (for G.1X: 4 vCPU, 16 GB).
Cluster manager
Hands out machines and containers. On EMR on EC2 it is YARN. On EMR on EKS it is Kubernetes. Glue and EMR Serverless use a managed one you never see.
Task
The smallest unit of work: one piece of code applied to one partition. If a stage has 400 partitions, it has 400 tasks.
Core (slot)
One task runs on one core. Total parallelism = number of executors × cores per executor.
SparkSession
The entry point object (spark) you use to read data, run SQL and configure Spark. It wraps the older SparkContext (spark.sparkContext), which you still use for low-level things like setting the log level.

Client mode and cluster mode

This only matters on EMR, where you choose where the driver runs.

Client mode

The driver runs on the machine where you typed spark-submit (usually the EMR primary node, or your notebook). Driver logs print to your console. If your SSH session dies, the job dies. Good for interactive work.

Cluster mode

The driver runs inside a YARN container on one of the cluster's worker nodes. Your terminal can disconnect safely. Driver logs go to YARN container logs (and to S3 on EMR). Use this for production steps.

Interview: What happens when you call spark-submit?

The driver starts and creates the SparkSession. It requests executors from the cluster manager, which launches them; they register back with the driver. The code builds a logical plan lazily. When an action runs, Catalyst optimises the plan into a physical plan, the DAG scheduler splits it into stages at shuffle boundaries, and the task scheduler sends one task per partition to free executor cores, preferring cores close to the data. Executors run the tasks, write shuffle output, and the next stage reads it. Results go to storage or back to the driver. When the application ends, executors are released.

Interview: What happens if an executor dies? What if the driver dies?

If an executor dies, the driver re-runs its in-flight tasks on other executors and recomputes any lost cached or shuffle data from lineage. The job continues, just slower. If the driver dies, the application ends because the driver holds the plan and all scheduling state. That is why driver memory problems (for example collect() on a large table) are fatal.

  • One driver plans; many executors work; the cluster manager hands out machines.
  • Parallelism = executors × cores. One task per partition per core at a time.
  • Executor death = retry and continue. Driver death = job fails.
  • Glue: one executor per worker, driver on one worker. EMR: you size executors yourself.

Lazy evaluation: transformations and actions

Spark does not run anything when you write filter or select. It only writes them down in a plan. Work starts when you ask for a result, such as count(), show() or write. Operations that only add to the plan are transformations; operations that ask for a result are actions. Waiting lets Spark see the whole job first and find the fastest way to run it.

A restaurant waiter writes down your whole order (starter, main, drink) before going to the kitchen. If they ran to the kitchen after each item, the chef could not plan. Because the chef sees the whole order, they can start the slow dish first and skip things you cancelled. Transformations are the order being written; the action is “send it to the kitchen”.

Which operations are which

The cost of lazy evaluation: repeated work

Because nothing is stored by default, every action runs the whole plan again from the source.

This reads S3 twicecommon bug
clean = spark.read.parquet("s3://raw/orders/").filter("amount > 0").dropDuplicates(["order_id"])

Fixes: drop the count if it is only for logging; or cache clean before the two actions (see Caching); or get the count afterwards from the written data or the job metrics. In Glue this “hidden double read” is one of the most common reasons a job costs twice what it should.

Small exceptions

A few calls do run a small job immediately: reading CSV with inferSchema=True or JSON without a schema (Spark samples the data to guess types), and pivot() without a list of values (Spark finds the distinct values first). This is another reason to always pass schemas.

Interview: What are the benefits of lazy evaluation?

Whole-plan optimisation (filter pushdown, column pruning, combining steps, choosing join strategies), pipelining several narrow operations into a single pass over each partition, and skipping work whose results are never used. The downside is that each action recomputes the lineage unless you cache.

  • Transformations build a plan; actions run it.
  • Laziness lets the optimiser read less data and combine steps.
  • Every action re-runs the plan from the source unless something is cached.

Jobs, stages, tasks and the shuffle

One action creates a job. Spark cuts the job into stages wherever data must move between machines (a shuffle). Each stage runs as many tasks as it has partitions. Operations that can work on each partition alone are narrow and stay in the same stage; operations that need rows from other partitions are wide and start a new stage.

Back to counting votes. Step 1: every counter tallies their own box per candidate (narrow: no one needs anyone else's box). Step 2: all slips for candidate A go to one table, all slips for B to another (that is the shuffle). Step 3: each table adds up its slips (a new stage). You cannot start step 3 until every step 1 counter is finished, which is why a stage boundary is also a waiting point.

Narrow versus wide

Narrow (no shuffle)

Each output partition comes from one input partition.

select, filter, withColumn, drop, cast, union, coalesce, explode, map and a broadcast join.

Wide (shuffle, new stage)

Each output partition needs rows from many input partitions.

groupBy().agg(), join (not broadcast), distinct, dropDuplicates, orderBy, repartition, window with partitionBy, intersect, except.

Why the shuffle is expensive

  1. CPU: rows are serialised (turned into bytes) and compressed.
  2. Disk: every map task writes shuffle files to the executor's local disk.
  3. Network: every reduce task fetches pieces from every map task. With 1,000 map tasks and 1,000 reduce tasks that is up to a million small fetches.
  4. Waiting: the next stage cannot start until the slowest task of the previous stage finishes. One slow task holds everyone up.

Stage boundaries: scan + filter orders (stage 1), scan customers (stage 2), join + partial sum (stage 3), final sum (stage 4), sort (stage 5). The orderBy also adds a small sampling job to decide the sort ranges, so the UI may show two jobs for one action. With AQE on (the default), Spark may skip or merge stages at run time. Do not expect a perfect one-action-one-job match in the UI.

Interview: What decides the number of tasks in a stage?

The number of partitions in that stage. For a file scan: total input size divided by spark.sql.files.maxPartitionBytes (128 MB default), adjusted for many small files. After a shuffle: spark.sql.shuffle.partitions (200 default), which AQE can merge down. After repartition(n): n.

Interview: What is a skipped stage in the Spark UI?

A stage whose shuffle output already exists from an earlier job in the same application, so Spark reuses the shuffle files instead of computing them again. You see it when two actions share the same upstream shuffle.

A job is created by an action. The DAG scheduler splits it into stages at every shuffle boundary, because a wide operation like a groupBy or a non-broadcast join needs rows from all partitions. Inside a stage, narrow operations are pipelined per partition, and the stage runs one task per partition. The shuffle is the expensive part: serialisation, local disk writes and network fetches, and the next stage waits for the slowest task.

  • Action → job → stages (cut at shuffles) → tasks (one per partition).
  • Narrow = stays in a stage. Wide = shuffle = new stage.
  • Reducing shuffles is the core of Spark performance tuning.

Partitions: the unit of parallelism

A partition is one chunk of a DataFrame's rows. One task processes one partition, on one core. The number and size of partitions decide how much work happens in parallel and how much memory each task needs. Too few big partitions: cores sit idle and tasks run out of memory. Too many tiny partitions: Spark spends more time scheduling than working, and you write thousands of tiny files.

You have 8 friends to help move house (8 cores). If you pack everything into 2 giant boxes, 6 friends stand around and the 2 carrying boxes might collapse (out of memory). If you pack 10,000 tiny boxes, everyone spends the day walking back and forth. About 16–32 sensible boxes keeps everyone busy.

Two different things are both called “partition”

In-memory partition (this lesson): a chunk of rows a task processes while the job runs. On-disk partition: a folder in S3 such as dt=2026-11-01/, created by write.partitionBy("dt"), used to skip folders when reading. They are related but not the same; the disk partitioning lesson covers the second kind.

Interview: When would you use repartition and when coalesce?

Use coalesce to reduce the number of partitions cheaply when the data is already small and evenly spread, for example after a selective filter and just before a write. Use repartition when you need more partitions, need even sizes, need rows with the same key together (repartition("dt") before partitionBy("dt")), or when coalescing would reduce the parallelism of expensive upstream work.

  • One partition = one task = one core at a time.
  • Target 100–200 MB per partition and 2–3× more partitions than cores.
  • Gzip files cannot be split: one file, one task.
  • coalesce is cheap but shrinks upstream parallelism; repartition shuffles but balances.

Spark has three APIs. The RDD (Resilient Distributed Dataset) is the original low-level one: a distributed list of Python or Java objects with no schema, so Spark cannot optimise it. RDD terms interviewers still ask

reduceByKey vs groupByKey
reduceByKey adds values up inside each partition first, then shuffles the small partial sums. groupByKey shuffles every single value and builds a list per key, which is slower and can run out of memory on popular keys. DataFrame groupBy().agg() behaves like reduceByKey.
map vs flatMap
map turns one item into exactly one item. flatMap turns one item into zero or more items and flattens them (one line → many words).
mapPartitions
Your function is called once per partition with all its rows. Useful to open one database or HTTP connection per partition instead of one per row.
Lineage
The recipe of transformations that produced an RDD. Spark uses it to rebuild lost partitions, which is the “resilient” in RDD.
df.rdd
Converts a DataFrame to an RDD of Row objects. It throws away optimisation and costs serialisation. Avoid in hot code.
Interview: When would you still use an RDD today?

Rarely. When the DataFrame API cannot express the logic (custom partitioners, processing raw binary records, very specific per-partition side effects) or when maintaining old code. Even then I would prefer mapPartitions to amortise setup cost, and convert back to a DataFrame as early as possible.

  • DataFrame = RDD + schema + optimiser. Use DataFrames.
  • Know reduceByKey vs groupByKey and mapPartitions for interviews.

Schemas and data types

A schema is the list of columns in a DataFrame, with each column's name, data type and whether it may be empty (NULL). Spark needs it to store data efficiently and to optimise your query. You can let Spark guess the schema by reading the data (inference) or give it yourself (explicit schema). In production, always give it yourself.

Why explicit schemas matter

Inferred

  • Spark reads the data an extra time to guess types (slow on big S3 folders).
  • Guesses can be wrong: zip code 01234 becomes the number 1234; an ID column becomes a double.
  • A single odd file changes the schema of the whole job.

Explicit

  • No extra read.
  • Types are exactly what downstream tables expect.
  • Bad values are caught by the read mode instead of silently changing types.
  • The schema doubles as documentation of the data contract.

Two ways to write a schema

  • Always pass an explicit schema in production reads.
  • Money = DECIMAL. IDs = STRING.
  • Failed casts return NULL in Spark 3.5 and raise an error in Spark 4 (ANSI).

Read performance tips

  • Prefer Parquet or Iceberg tables over CSV/JSON: columnar, typed, compressed, and Spark can skip data.
  • Point at the narrowest folder or filter on the partition column so Spark lists fewer S3 objects.
  • Gzip CSV/JSON cannot be split; many medium files are better than one giant .gz.
  • mergeSchema=true on Parquet reads every file footer; use it only when you must.
Interview: How do you handle corrupt or malformed records?

Read in PERMISSIVE mode with an explicit schema and a corrupt-record column, split the DataFrame into good and bad rows, write bad rows with the raw text and a load timestamp to a quarantine location, continue with good rows, and alert when the bad ratio crosses a threshold.   • spark.read.schema(...).option(...).format(path) is the pattern.
  • PERMISSIVE + corrupt column + quarantine is the production standard.
  • JDBC reads need partitionColumn + numPartitions to run in parallel.

Retries and append

If a job appends data, fails afterwards, and your orchestrator retries it, the same rows get appended twice. Production loads should be idempotent (running twice gives the same result): overwrite the run's partitions with dynamic mode, or MERGE on a key with Iceberg.

Interview: How do you make a daily batch load idempotent?

Partition the output by the business date and overwrite only that date's partition with dynamic partition overwrite, or use Iceberg overwritePartitions() or a MERGE keyed on the business key. The job takes the run date as a parameter, so a re-run for the same date replaces the same data. I never rely on plain append for retried jobs.

  • Default overwrite is static: it wipes the whole path. Set partitionOverwriteMode=dynamic.
  • repartition(col) before partitionBy(col) to control file counts.
  • Design every load to be safe to re-run.

File formats and how Parquet works

Row formats (CSV, JSON, Avro) store one record after another. Columnar formats (Parquet, ORC) store all values of one column together. Analytics queries usually read a few columns from many rows, so columnar formats let Spark read only the columns it needs and skip blocks of rows that cannot match a filter. On AWS, Parquet is the default choice for data lakes, and Iceberg tables store their data as Parquet too.

Compression

Snappy (default for Parquet) is fast with moderate compression. Zstd compresses better at similar speed and is a good choice for cold data. Gzip is slower. Compression codec applies inside Parquet pages, so a .snappy.parquet file is still splittable.

Interview: Why is Parquet faster than CSV for analytics?

Spark reads only the columns the query needs (column pruning), skips whole row groups using min/max statistics in the footer (predicate pushdown), decodes values in vectorised batches, and reads far fewer bytes because columnar data compresses well. CSV must be read fully and parsed as text, with no types or statistics.

  • Columnar = read only needed columns + skip row groups by statistics.
  • Parquet file = row groups of column chunks + a footer with stats.
  • Sorted data makes pushdown effective.

NULLs in aggregates and joins
  • count("col"), sum, avg, countDistinct ignore NULLs; count("*") counts every row.

Interview: Why did my filter return fewer rows than expected?

  • Filter keeps only TRUE; NULL comparisons give NULL; those rows vanish.
  • Use & | ~ with brackets, never Python and/or/not.
  • count(*) counts NULLs; count(col) does not.

Interview: How does Spark execute groupBy().sum() physically?

As two HashAggregate operators around one shuffle. Interview: left_semi vs inner join — what is the difference?

A semi join returns each left row at most once, even when the right side has several matches, and returns only left columns. An inner join returns one row per matching pair, so duplicates on the right multiply left rows. Semi is also cheaper because it can stop at the first match. Anti join is the safe NOT EXISTS; unlike NOT IN, it is not broken by NULLs on the right side.

  • left = keep all facts; inner = only matched; anti = find missing; semi = filter by existence.
  • Join on column names to avoid duplicate key columns.
  • How Spark physically runs joins (broadcast vs sort-merge) is in Join strategies.

Join pitfalls that break production

Joins rarely fail loudly. They usually return the wrong number of rows. These five mistakes cover most join bugs you will meet at work and in interviews.

1. Duplicate keys on the “lookup” side multiply rows

If customers accidentally has two rows for c1, every order of c1 appears twice and revenue doubles. Always check uniqueness before trusting a join:

Key uniqueness checkpyspark
dups = cust.groupBy("customer_id").count().filter("count > 1")
if dups.limit(1).count() > 0:
    raise ValueError("customers has duplicate customer_id values")

2. A WHERE on the right table turns a left join into an inner join

Wrong

o.join(c, "customer_id", "left")
 .filter(F.col("segment") == "GOLD")

Orders without a customer have segment NULL, so the filter removes them. You just wrote an inner join.

Right

gold = c.filter(F.col("segment") == "GOLD")
o.join(gold, "customer_id", "left")

Filter the right side before joining.

3. NULL keys

NULLs never match. In big left joins, millions of NULL keys all hash to the same partition and create one giant task. Filter them out, join the rest, and union the NULL rows back.

4. Type mismatch

Joining a string customer_id to a bigint one forces a cast on every row, can lose matches ("007" vs 7), and can stop Spark from using statistics. Cast both sides to the same type first.

5. Accidental cross join

A missing or always-true condition multiplies 1 million × 1 million rows. Spark detects some cases (Detected implicit cartesian product). In plans, CartesianProduct or BroadcastNestedLoopJoin is a red flag.

Interview: After a join, your row count went from 10 million to 14 million. Why?

The right side has duplicate keys, so some left rows matched more than once. I would group the right side by the join key and count, find the duplicated keys, then fix it at the source or deduplicate (for a dimension, keep the current version with row_number). If I only need to check existence, I switch to a left semi join.

  • Check key uniqueness on the lookup side.
  • Filter the right table before a left join, not after.
  • Match key types; watch for NULL keys and missing conditions.

Window functions explained

A window function calculates a value for each row by looking at a group of related rows, without collapsing them. A groupBy turns ten rows into one; a window keeps all ten rows and adds a column, such as “rank within department” or “running total so far”. You describe the window with three parts: partitionBy (which rows belong together), orderBy (their order), and the frame (how many neighbouring rows to look at).

Think of a school results board. partitionBy("class") puts each class on its own board. orderBy(marks desc) sorts each board. Now every student gets a rank on their own board, and every student is still listed. That is a window. A groupBy would just print one line per class with the average.

Window without partitionBy

W.orderBy("ts") with no partitionBy moves all rows into one partition, so one task does all the work. Spark warns: No Partition Defined for Window operation! Moving all data to a single partition. Fine for a 30-row monthly summary, fatal for a billion-row table.

A window function computes a value per row over a set of related rows without collapsing them. partitionBy defines the groups and causes a shuffle, orderBy sorts within each group, and the frame decides which neighbouring rows are included.   • Window = keep every row, add a calculated column.
  • partitionBy → shuffle; orderBy → sort; frame → which rows count.
  • No partitionBy = everything in one task.

Flatten a deeply nested record

Generic flattener (common interview ask)pyspark
from pyspark.sql.types import StructType, ArrayType

def flatten(df, sep="_"):
    """Expand structs into columns and explode arrays until nothing nested remains."""
    while True:
        nested = [(f.name, f.dataType) for f in df.schema.fields
                  if isinstance(f.dataType, (StructType, ArrayType))]
        if not nested:
            return df
        name, dtype = nested[0]
        if isinstance(dtype, StructType):          # struct -> one column per field
            new_cols = [F.col(f"`{name}`.`{c.name}`").alias(f"{name}{sep}{c.name}") for c in dtype.fields]
            df = df.select([F.col(f"`{c}`") for c in df.columns if c != name] + new_cols)
        else:                                      # array -> one row per element
            df = df.withColumn(name, F.explode_outer(F.col(f"`{name}`")))

Mention the trade-off in an interview: exploding two independent arrays in the same record multiplies rows (3 items × 4 tags = 12 rows). In real pipelines you write a header table and separate child tables (order_items, order_tags), each keyed by the parent id.

  • Struct → dot access. Array → explode / explode_outer. Map → col["key"], map_keys.
  • Higher-order functions (transform, filter, aggregate) avoid explode and stay in the JVM.
  • from_json needs a schema; invalid JSON becomes NULL.

Memory

Python workers live outside the JVM heap, inside the executor's memory overhead. Heavy pandas UDFs are a top cause of “Container killed … exceeding memory limits”. Lower spark.sql.execution.arrow.maxRecordsPerBatch (default 10,000) for wide rows, and raise spark.executor.memoryOverhead on EMR or choose a larger / R-type worker on Glue.

Interview: Why are Python UDFs slow, exactly?

Three reasons. Each row is converted from Spark's binary format, pickled, sent over a socket to a Python worker, unpickled, processed and sent back. Catalyst treats the UDF as a black box, so it cannot push filters through it or include it in whole-stage code generation. And the Python process needs its own memory outside the JVM. UDFs can also run more than once per row, so they must be deterministic or marked asNondeterministic().

  • Built-in > pandas UDF > plain UDF.
  • UDFs show as BatchEvalPython / ArrowEvalPython in plans.
  • Python memory lives in overhead, not heap.

Catalyst: how Spark optimises your query

Catalyst is Spark's query optimiser. Whatever you write (DataFrame code or SQL), Catalyst turns it into a tree of operations, checks that every column exists, rewrites the tree to do less work, and then picks a concrete way to run each step. Tungsten is the execution engine underneath: it stores rows in a compact binary format and generates Java code for each stage so it runs close to hand-written speed.

You tell a satnav “take me to the airport, but stop for fuel”. You did not say which roads. The satnav checks the places exist (analysis), simplifies your request (“the fuel station on the airport road counts”, that is optimisation), then chooses actual roads based on traffic (physical planning). Catalyst is the satnav for your query.

What breaks optimisation

  • Python UDFs: Catalyst cannot look inside, so filters on UDF output cannot be pushed down.
  • Functions on partition or filter columns: substring(dt, 1, 7) = '2026-11' often stops partition pruning; write dt BETWEEN '2026-11-01' AND '2026-11-30' instead.
  • Caching early: a filter applied after cache() filters the cached data, not the source.
  • Going through df.rdd: leaves the optimiser entirely.
  • CSV / JSON sources: filters can be applied during parsing, but there are no statistics to skip data.
Interview: Give a concrete example of Catalyst changing your code.

If I write orders.join(customers, "customer_id").filter(orders.country == "IN"), Catalyst pushes the filter below the join so only Indian orders are joined, then further into the Parquet scan as PushedFilters: [EqualTo(country,IN)]. If country is a partition column it becomes PartitionFilters and whole S3 folders are skipped. It also prunes columns: if I select 3 of 80 columns, only those 3 are read.

Interview: What is the difference between Catalyst and Tungsten?

Catalyst decides what to run: it analyses and optimises the query plan and chooses physical operators. Tungsten decides how efficiently it runs: compact binary row format (UnsafeRow), explicit memory management on and off heap, cache-friendly sorting, and whole-stage code generation.

  • Parsed → analyzed → optimized → physical → generated code; AQE adjusts at run time.
  • Pushdown and column pruning are the optimisations you will point at most.
  • UDFs, functions on filter columns and early caches block optimisation.

Interview: You see BroadcastNestedLoopJoin in a plan. What do you do?

It means there is no equality condition Spark can hash on: a non-equi join, an OR across keys, or a forgotten key. First I check the condition. Interview: How do you prove partition pruning happened?

In explain() the FileScan shows PartitionFilters: [...] (static pruning) or dynamicpruningexpression (dynamic pruning). In the Spark UI SQL tab, the scan node shows “number of partitions read” and “number of files read”, which should be a small fraction of the table.

I read plans bottom-up. At the scans I check partition filters, pushed filters and the read schema. After execution I check the final adaptive plan to see whether AQE coalesced partitions, switched a join or split skewed partitions.

  • Bottom-up. Scans → filters → joins → aggregates → output.
  • Count Exchanges. Each is a shuffle.
  • Run an action, then explain() again for the final AQE plan.

Shuffle internals

During a shuffle, every task in the first stage splits its output into buckets, one per partition of the next stage, and writes them to its executor's local disk. Every task in the next stage then fetches its bucket from all of those files over the network. The executor's disk, the network and serialisation all add cost, and the second stage cannot start until the first has finished.

Shuffle metrics in the Spark UI

Shuffle Write
Bytes the map tasks wrote. Large = expensive boundary. Compare it with the input size: if a join writes 10× its input, rows exploded.
Shuffle Read
Bytes the reduce tasks fetched. Uneven read per task = skew.
Spill (Memory)
Size, in memory form, of data that did not fit and was moved to disk.
Spill (Disk)
The same data after serialisation on disk. Any spill means tasks had too little execution memory for their partition.
Shuffle Read Fetch Wait Time
Time reducers waited for blocks: slow network, busy or dead executors.
Shuffle Remote Reads
Bytes fetched from other machines (vs local reads on the same executor).
Who serves shuffle files when an executor is gone?

With dynamic allocation, an idle executor can be removed while its shuffle files are still needed. On EMR the external shuffle service (a process on each node, port 7337) keeps serving those files. Spark 3 can also track shuffle files and keep such executors alive (spark.dynamicAllocation.shuffleTracking.enabled) or migrate blocks during graceful decommissioning. If shuffle files are truly lost (node died, spot instance reclaimed), the reduce task fails with FetchFailedException and Spark re-runs the parent stage for the missing pieces.

Sizing spark.sql.shuffle.partitions

Aim for 100–200 MB per shuffle partition. Find the biggest Shuffle Write in the Stages tab and divide. With AQE you can set a higher starting number and let AQE merge small partitions.

Interview: How do you reduce shuffle in a job?
  • Filter and select needed columns before wide operations.
  • Broadcast small tables in joins.
  • Aggregate the fact table to the join grain before joining.
  • Reuse partitioning: data already hash-partitioned by a key, joined or aggregated again on the same key with the same partition count, skips the Exchange.
  • Bucketed or storage-partitioned tables for repeated joins on the same key.
  • Remove unnecessary distinct, orderBy and repartition.
  • Use approximate distinct counts where allowed.
  • Map side writes bucketed files to local disk; reduce side fetches its bucket from every map task.
  • Spill = not enough execution memory per task.
  • FetchFailedException = shuffle files lost; parent stage re-runs.

Executor memory model

An executor's memory is divided into regions with different jobs. Most of the JVM heap is a shared pool called unified memory, split dynamically between execution (shuffles, joins, sorts, aggregations) and storage (cached data and broadcast tables). The rest of the heap is user memory for your own objects. Outside the heap sits overhead, used by Python workers, network buffers and native code. Knowing which region ran out tells you how to fix an out-of-memory error.

Try it: how much memory does each task really get?

With a 16 GB heap and 4 cores, unified memory is about 9.4 GB, so each running task gets roughly 2.3 GB of execution memory when all cores are busy and nothing is cached. A task never gets less than 1/(2 × cores) or more than 1/cores of the execution pool. If one partition needs 6 GB to sort, it spills heavily or fails. That is why making partitions smaller (more of them) often fixes memory errors without adding a single gigabyte.

Sizing executors on EMR

On Glue you choose a worker type and AWS sizes the executor. On EMR (and EMR Serverless) you set cores and memory. The classic method:

  1. Leave 1 core and about 1 GB per node for the operating system and YARN.
  2. Use about 5 cores per executor: enough parallelism, sane garbage collection, good S3 throughput.
  3. Divide the node's memory between its executors, keep about 10% for overhead.
  4. Leave one executor's worth for the driver / YARN application master.
On AWS

Interview: You doubled executor memory and the job still fails with OOM. Why?

Because the problem is probably one partition that is far bigger than the others (skew) or a single group that must be held in memory (a huge window partition or collect_list). More memory per executor shared by the same number of cores does not split that partition. I would check the Stages tab: if the max task's shuffle read is many times the median, it is skew, and I would fix it with broadcast, salting or AQE. If the message is a YARN container kill, the problem is overhead, not heap, so heap increases do not help at all.

  • Heap = reserved 300 MB + unified 60% (storage ↔ execution) + user 40%.
  • Overhead (off-heap) holds Python and network buffers.
  • Heap OOM → smaller/balanced tasks. Container killed → more overhead.

Join strategies: broadcast, sort-merge, hash

Spark has several physical ways to run the same join. If one table is small, it copies that table to every executor and joins locally without moving the big table: a broadcast hash join. If both are big, it shuffles both by the join key, sorts them and merges: a sort-merge join. Choosing correctly is often the difference between a 3-minute job and a 3-hour job.

Which side can be broadcast

In a left outer join only the right side can be broadcast, because every left row must be kept and checked. In a right outer join, only the left. A full outer join cannot use a broadcast hash join. Inner joins can broadcast either side.

Why a “9 MB” table can break a broadcast

The threshold is compared with Spark's estimate, which for Parquet is the compressed file size. Nine megabytes of snappy Parquet can be 80+ MB once decompressed into a hash table on every executor. If broadcasts cause driver or executor OOM, lower the threshold or remove the hint. AQE also has its own threshold, spark.sql.adaptive.autoBroadcastJoinThreshold, applied to real post-filter sizes at run time.

Interview: When is a broadcast join a bad idea?

When the “small” side is large in memory after decompression (driver must collect it and every executor must hold it), when it is the preserved side of an outer join (not allowed), when building it is slow and hits the broadcast timeout, or when executors are already memory-tight. In those cases a sort-merge join (with AQE skew handling) or a shuffled hash join is safer.

  • Small side → broadcast hash join, zero shuffles.
  • Both large → sort-merge join: 2 shuffles + 2 sorts.
  • Threshold compares estimated compressed size. AQE re-decides using real sizes.

Adaptive Query Execution (AQE)

Before a query runs, Spark only has estimates of data sizes, and estimates are often wrong. AQE lets Spark pause after each shuffle stage, look at the real sizes it just produced, and re-plan the rest of the query. It is on by default in Spark 3.2+ (so on Glue 5.x and EMR 7.x). It does three main things: merges tiny partitions, switches to a cheaper join, and splits oversized partitions in joins.

  • Skew handling works for joins only, not for skewed groupBy or window partitions. Those still need salting or two-phase aggregation.

  • For outer joins it can only split the preserved side: the left side of a left join, the right side of a right join. Skew on the other side, or in a full outer join, is not split.

Interview: AQE is on, but one task still runs for an hour. Why?

Possible reasons: the skew is in an aggregation or window, which AQE does not split; the slow partition is below the 256 MB threshold but each row is expensive (a UDF, a regex); the skew is in the scan stage (one huge unsplittable file); the skew is on the non-preserved side of an outer join (for example the right side of a left join), which AQE cannot split; or the thresholds do not match my data. I check the final plan or the SQL tab for skew=true. If AQE did not act, I lower the thresholds, broadcast, or salt.

AQE re-optimises the query at every shuffle boundary using actual statistics. It coalesces small shuffle partitions toward the advisory size, converts sort-merge joins to broadcast or shuffled hash joins when a side turns out small, and splits skewed join partitions that exceed both five times the median and 256 megabytes. It does not fix skew in aggregations or windows, and it cannot help the initial scan stage.

  • AQE = runtime re-planning after each shuffle.
  • Coalesce, switch join, split skew (joins only).
  • Skewed = > 5× median AND > 256 MB.

Fault tolerance, retries and speculation

Spark expects machines to fail. It remembers how every partition was produced (its lineage), so when a task or executor fails it re-runs only the missing work somewhere else. If the same task keeps failing, the job stops. Knowing the retry rules helps you read logs: a task that fails four times on different machines is a data problem, not a machine problem.

Speculative execution

With spark.speculation=true, Spark launches a second copy of tasks that are much slower than the median and keeps whichever finishes first. It helps when one machine is unhealthy. It does not help with skew (the copy has the same giant partition) and is dangerous with non-idempotent side effects, such as writing to a database from foreachPartition.

Checkpointing

df.checkpoint() writes the DataFrame to reliable storage (set spark.sparkContext.setCheckpointDir("s3://...")) and cuts the lineage, so recovery and planning no longer walk back through hundreds of steps. Use it in loops or iterative algorithms where the plan grows each iteration. localCheckpoint() is faster but stores data on executors, so it is not fault-tolerant.

Interview: How do you tell a data problem from an infrastructure problem in a failed job?

If the same task index fails on every attempt across different executors, and other tasks succeed, the partition itself is the problem: a skewed key, a poison record, a NULL reaching a UDF. If random tasks on one host fail, or executors are lost with exit codes from the cluster (spot reclaim, node failure, disk full), it is infrastructure or resources. The Executors tab and the failed-task error column show both patterns.

  • 4 attempts per task, then the job fails.
  • Same task index failing everywhere = data issue.
  • Speculation fixes bad nodes, not skew.

Interview: A stage is stuck at 199 of 200 tasks. What do you do?

That is the classic skew signature. I open the stage's summary metrics and compare max and median shuffle read: if the max is many times larger, one key dominates. I find which operator it is in the SQL tab, count rows per key to identify the hot key (often NULL, an empty string or a default ID), then choose a fix: filter or separately handle junk keys, broadcast the other side, confirm AQE skew join is splitting it, or salt the key. If max and median are similar but the last task is slow, I check that task's executor for GC or a bad node, and consider speculation.

  • Max ≫ median = skew. All tasks slow + few tasks = under-partitioned.
  • Tiny inputs + scheduler delay = small files / too many partitions.
  • High GC + spill = memory pressure per task.

While your job runs, the driver writes an event log: a file of JSON lines recording every job, stage and task start and end, their metrics, and the SQL plans. The Spark History Server reads those files and rebuilds the full Spark UI, so you can investigate a job that finished, or failed at 3 a.m., hours later. On AWS you mainly need to know where event logs go and how to open the UI.

Partitioning data on S3

When you write with partitionBy("dt"), Spark creates one folder per value: dt=2026-11-01/, dt=2026-11-02/. A later query with WHERE dt = '2026-11-02' reads only that folder and skips the rest. This is partition pruning, and choosing the right partition column is one of the most important design decisions in a data lake.

Choosing the partition column

  • Pick what most queries filter on. For event and transaction data, that is almost always a date.
  • Keep cardinality low to medium. Each partition should hold at least a few hundred MB. A month of daily partitions is fine; partitioning by customer_id or by timestamp is not.
  • Avoid deep nesting such as year/month/day/hour/country. It multiplies folders and tiny files and slows S3 listing.
  • Partition columns are strings in folder names; keep the format fixed (yyyy-MM-dd).
  • With Iceberg, use hidden partitioning transforms (days(event_ts), bucket(16, id)): users filter on the real column and still get pruning, and you can change partitioning later without rewriting data.

Interview: What is the difference between repartition and partitionBy?

repartition changes how rows are split into in-memory partitions (tasks) during the job, and causes a shuffle. partitionBy on the writer decides the folder layout on storage. They are often used together: df.repartition("dt").write.partitionBy("dt") groups each date's rows into one task so each folder gets few, larger files.

  • Disk partitioning = folders; enables pruning.
  • Partition by what you filter on, usually a date; low cardinality.
  • Never wrap the partition column in a function inside the filter.

The small-file problem

Thousands of tiny files (a few KB or MB each) make everything slower: every file is a separate S3 request, a separate footer to read and often a separate task. A table with 2 million 50 KB files can take longer to list than to read. The cure is to write fewer, larger files (128 MB–1 GB) and to compact tables that already have the problem.

All the tools

Controlling output file sizepyspark
# 1. one task per partition value
df.repartition("dt").write.partitionBy("dt").parquet(out)

# 2. big partition values spread over N files each

# 3. cap rows per file (a task writes several files if needed)
df.write.option("maxRecordsPerFile", 2_000_000).partitionBy("dt").parquet(out)

spark.conf.set("spark.sql.adaptive.coalescePartitions.parallelismFirst", "false")
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "256m")

spark.sql("ALTER TABLE glue_catalog.db.orders SET TBLPROPERTIES ('write.distribution-mode'='hash')")

Reading small files you cannot fix yet

  • DataFrames: raise spark.sql.files.maxPartitionBytes (e.g. 256 MB) and lower spark.sql.files.openCostInBytes (e.g. 1 MB) so more files are packed into each task.
  • Glue DynamicFrames: connection_options={"groupFiles": "inPartition", "groupSize": "134217728"} groups small files into ~128 MB read tasks.
  • At the source: increase Kinesis Data Firehose buffer size/interval; use longer micro-batch triggers in streaming.
Interview: Your S3 table has 2 million 50 KB files. Fix it.

Short term, a compaction job that reads each partition and rewrites it into 256 MB–1 GB files, and swaps safely: write to a new prefix and repoint the Glue partition locations, or, if the table is Iceberg, use rewrite_data_files (or the Glue Data Catalog compaction optimizer), which commits atomically so readers never see a half-written state. Long term, fix the writer (repartition by the partition column before writing, AQE with a larger advisory size, longer streaming triggers or Firehose buffers) and schedule compaction and snapshot expiry.

  • Files written ≈ write tasks × partition values each task holds.
  • repartition(partition_col) before partitionBy(partition_col).
  • Target 128 MB–1 GB files; compact existing tables.

Data skew: find it and fix it

Skew means a few key values have far more rows than the rest, so after a shuffle a few tasks get most of the data. The stage waits for those few tasks while every other core sits idle. Typical culprits: NULL or empty keys, a placeholder like UNKNOWN or -1, one giant customer or tenant, a bot user in clickstream.

A supermarket opens 20 checkouts, but one customer arrives with 400 trolleys and must use a single checkout. Nineteen cashiers finish in minutes; the shop stays open for hours. Salting is splitting that customer's trolleys across many checkouts.

Fix it: cheapest option first

  1. Remove junk keys. Filter NULL / placeholder keys before the join, process them separately if needed, and union back.
  2. Broadcast the other side if it fits. A broadcast join has no shuffle, so no skew.
  3. Check AQE skew join (default on). Confirm skew=true in the final plan; lower skewedPartitionThresholdInBytes / skewedPartitionFactor if your skewed partitions are smaller than 256 MB.
  4. Salt the key for joins AQE cannot handle.
  5. Two-phase aggregation for skewed groupBy (AQE does not split aggregations).
  6. Isolate hot keys: join the top N hot keys with a broadcast join and everything else normally.

The hot-key version is built as a union because Spark does not allow a generator such as explode inside when(). Only the hot keys are copied N times, so the dimension barely grows.

Interview: Skew in a window function partitioned by user_id. Options?

AQE does not split window partitions. Options: remove bot, test or NULL users; add a second partition key if the logic allows (user and day, when the window never crosses days); pre-aggregate to (user, day) first and run the window on the much smaller table, then join back; handle the few hot users with separate logic; and as a last resort give executors more memory per core so the large partition spills rather than fails.

I confirm skew from the stage's max versus median shuffle read, then find the hot keys with a count by key. Often they are NULLs or placeholders that I can filter. If the other side is small I broadcast; otherwise I check AQE split the partitions. When AQE cannot help, for example skewed aggregations or windows, I salt: random salt on the skewed side, replicate the other side across salt values, or a two-phase aggregation.

  • Skew = few keys, most rows → one slow task.
  • Filter junk keys → broadcast → AQE → salt → two-phase aggregate.
  • AQE only splits skewed joins.

Caching and persistence

cache() asks Spark to keep a DataFrame in executor memory (and disk if needed) after the first time it is computed, so later actions reuse it instead of re-reading and recomputing from the source. It helps only when the same DataFrame is used by two or more actions. Caching something used once just wastes memory.

Cache what is reused, then release itpyspark
from pyspark import StorageLevel

clean = raw.filter("amount > 0").dropDuplicates(["order_id"])   # expensive
clean.persist(StorageLevel.MEMORY_AND_DISK)                    # same as clean.cache() for DataFrames
clean.count()                                                  # fills the cache (optional, makes timing clear)

clean.filter("country = 'IN'").write.parquet(path_in)          # reads from cache
clean.groupBy("dt").count().write.parquet(path_counts)         # reads from cache
clean.unpersist()                                              # free memory for the rest of the job

MEMORY_AND_DISKDataFrame default. Partitions that do not fit go to local disk

*_2 (e.g. MEMORY_AND_DISK_2)Two copies on different executors: faster recovery, double memory

When caching hurts
  • The DataFrame is used once: pure overhead.
  • You cache the raw scan before filters: you store everything, and later filters no longer push down to the files.
  • The cache is larger than memory and keeps getting evicted: re-reading Parquet from S3 can be faster.
  • You forget unpersist() in a loop: storage memory fills and squeezes execution memory, causing spills.

cache vs checkpoint

cache / persist

Keeps the lineage. If an executor dies, the lost partitions are recomputed from the source. Lives only for the application.

checkpoint

Writes to reliable storage (S3) and cuts the lineage. Use when the plan has become huge (loops, iterative algorithms). localCheckpoint is faster but not fault tolerant.

Interview: Does df.cache() cache the data immediately?

No. It is lazy: it only marks the plan. The first action fills the cache, and only for the partitions that action computes. take(5) may cache one partition. That is why people call count() once to fully materialise it. The Storage tab shows the fraction cached, and the plan shows InMemoryTableScan when the cache is used.

  • Cache only DataFrames used by 2+ actions; unpersist after.
  • cache is lazy; the first action fills it.
  • checkpoint cuts lineage; cache keeps it.

Playbook: out-of-memory errors

Two questions decide the fix. Driver or executor? The log says which process died. Heap or overhead? “Java heap space” means the JVM heap; “Container killed … exceeding memory limits” or exit code 137 means the container's total, usually overhead. Then fix the cause (oversized tasks, collects, UDFs) before adding memory.

Driver OOM

  • collect(), toPandas(), take(huge) → write to S3 or aggregate first.
  • Broadcasting a large table → lower the threshold, remove the hint.
  • Millions of files or partitions → compact, prune, use Iceberg.
  • Huge plans from loops of withColumn/union → one select, checkpoint.
  • Total size of serialized results ... bigger than spark.driver.maxResultSize → fix the collect; raising the limit is last resort.

Executor OOM

  • Same task fails every time → skew or a giant group: fix skew, more partitions.
  • collect_list / window on a hot key → restructure.
  • Container killed / 137 → raise memoryOverhead, smaller Arrow batches, replace UDFs.
  • Many cores share one heap → fewer cores per executor.
  • Glue: G.1X → G.2X, or R-type workers for memory-heavy jobs.

Before adding memory, I make tasks smaller and balanced, because doubling memory on a skewed key only delays the failure. I pick heap versus overhead from the actual error message: Java heap space means more partitions, fixing skew or fewer cores per executor; a YARN container kill means overhead, usually from Python UDFs or Arrow, so I raise memoryOverhead or remove the UDF.

A one-pass quality gatepyspark
def assert_quality(df, key_cols, not_null_cols, min_rows):
    stats = df.agg(
        F.count("*").alias("rows"),
        F.countDistinct(*key_cols).alias("distinct_keys"),
        *[F.sum(F.col(c).isNull().cast("int")).alias(f"null_{c}") for c in not_null_cols],
    ).first().asDict()                       # one small row comes back to the driver
    problems = []
    if stats["rows"] < min_rows:
        problems.append(f"only {stats['rows']} rows (expected ≥ {min_rows})")
    if stats["distinct_keys"] != stats["rows"]:
        problems.append(f"{stats['rows'] - stats['distinct_keys']} duplicate keys")
    problems += [f"{k} = {v}" for k, v in stats.items() if k.startswith("null_") and v]
    if problems:
        raise ValueError("Data quality failed: " + "; ".join(problems))
    return stats

Three incidents, solved end to end

These are realistic incidents written the way you would explain them in a project deep-dive: symptom, evidence, root cause, fix, and how you prevented it from happening again. Practise telling each in under two minutes.

Incident 1: month-end OOM in a Glue job

Symptom
A daily Glue 5.1 job (10 × G.1X) failed only on the 1st of each month with ExecutorLostFailure … Container killed … exceeding physical memory limits.
Evidence
Spark UI from event logs: stage 14, the same task index failed four times. Its shuffle read was 9 GB vs a median of 120 MB. SQL tab: the stage was a window partitionBy("account_id") computing running balances. Month-end loads the full month for one large corporate account.
Root cause
A window partition for one account was far larger than one task's memory. AQE does not split window partitions.
Fix
Pre-aggregated transactions to (account, day) before the window, cutting that account's rows from 40 million to 31; computed running balances on the daily table and joined back to transactions for intra-day detail with a second window partitioned by (account, day). Runtime dropped from failing at 52 minutes to 14 minutes on the same workers.
Prevention
Added a CloudWatch alarm on Glue observability skewness metrics and a pre-check that logs the top 5 keys by row count.

Incident 2: a join that suddenly took 3 hours

Symptom
Nightly enrichment went from 25 minutes to 3 hours with no code change.
Evidence
Plan diff: BroadcastHashJoin had become SortMergeJoin. The product dimension had grown from 8 MB to 14 MB of Parquet, crossing the 10 MB threshold. The new SMJ also showed skew on a popular product.
Fix
Selected only the 4 needed columns from the dimension (3 MB), restoring the broadcast; kept an explicit broadcast() hint with a size check that falls back if the dimension exceeds 200 MB.
Prevention
Recorded the plan's join strategies in the job's run log; alert when a strategy changes.

Incident 3: Athena queries slowed down over six months

Symptom
Analysts complained that Athena queries on an Iceberg table went from seconds to minutes.
Evidence
The files metadata table showed 1.8 million data files averaging 3 MB, plus thousands of delete files from hourly MERGE jobs (merge-on-read). The snapshots table had 4,000 snapshots and was never expired.
Fix
Ran rewrite_data_files with sort order on the most filtered column, expire_snapshots keeping 7 days, remove_orphan_files, and rewrite_manifests. Then enabled Glue Data Catalog table optimizers (compaction, snapshot retention, orphan file deletion) so it stays healthy.
Result
Files fell to 21,000 and median query time returned to under 10 seconds; S3 storage dropped 40% after snapshot expiry.
How to tell your own story

Use the same five headings for your real incidents. Numbers make answers credible: data volume, runtime before and after, cost per run, failure rate. Keep client-specific details at the level you are allowed to share.

Glue job bookmarks

A job bookmark is Glue remembering what a job has already processed, so the next run reads only new data. For S3 sources it tracks file paths and modification times; for JDBC sources it tracks the highest value of a key column. The bookmark only moves forward when job.commit() runs at the end of a successful run.

Requirements and gotchas

  • Enable with --job-bookmark-option job-bookmark-enable, call job.init() at the start and job.commit() at the end, and give every Glue source a unique transformation_ctx.
  • Only Glue sources are tracked. Plain spark.read.parquet(...) ignores bookmarks.
  • For JDBC, set jobBookmarkKeys to a column that only increases (an ID or an updated_at timestamp) and jobBookmarkKeysSortOrder.
  • To reprocess, reset the bookmark (aws glue reset-job-bookmark --job-name ...) or run with job-bookmark-pause and explicit from/to run IDs.
  • Files overwritten in place with the same name may be missed.
  • Bookmark advances only on job.commit().
  • Needs transformation_ctx on Glue sources.
  • At-least-once: make writes idempotent.

S3 behaviour every Spark engineer must know

S3 is an object store, not a file system. There are no real folders and no cheap renames: renaming means copying then deleting. Classic Hadoop jobs commit output by renaming temporary files, which is slow and not atomic on S3. AWS's committers, and table formats like Iceberg, avoid that problem.

Consistency
Since December 2020 S3 has strong read-after-write consistency: new and overwritten objects and listings are immediately visible. The old “EMRFS consistent view” workaround is obsolete. Saying this shows you are current.
Request rates
About 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per prefix. Millions of tiny files or thousands of tasks hitting one prefix cause 503 Slow Down.
Committers
EMRFS S3-optimised committer (EMR), Glue's defaults, S3A magic committer (open source). Iceberg commits by writing new metadata, so data files never need renaming.
Partial output
A failed overwrite on a plain Parquet table can leave a partition half-deleted. Write to a staging prefix and switch the catalog location, or use Iceberg.
URI schemes
s3:// on EMR and Glue (EMRFS); s3a:// in open-source Hadoop.
Encryption
SSE-S3 by default; SSE-KMS needs kms:Decrypt / kms:GenerateDataKey on the job role, a frequent cause of 403 errors.
  • Renames are copies: use proper committers or Iceberg.
  • Strongly consistent since 2020.
  • Rate limits are per prefix: avoid tiny files.

Why table formats exist

A plain “table” on S3 is just a folder of Parquet files plus a Glue Catalog entry that says “the table lives at this path”. That works until you need to update a row, two jobs write at once, a job fails halfway, or a query must read a consistent version while a job is writing. Apache Iceberg fixes this by adding a layer of metadata files that list exactly which data files belong to each version of the table. The data stays in Parquet on S3; Iceberg tracks it.

A plain S3 table is a shared folder of photos where anyone can drop or delete files at any time: you never know if you are looking at a complete album. Iceberg is a photo album with a table of contents. A new version of the album is published by writing a new table of contents in one step. Readers always follow one complete table of contents, so they never see half an update, and old tables of contents let you go back in time.

Iceberg is an open table format that adds a metadata layer over Parquet files on S3. Each commit writes new metadata describing the full set of data files for that version and atomically swaps the catalog pointer, which gives ACID transactions, snapshot isolation for readers, time travel and rollback, row-level MERGE, UPDATE and DELETE, schema evolution by column ID and hidden partitioning with partition evolution. It also speeds up planning because file-level statistics live in manifests instead of S3 listings. The trade-off is that tables need regular maintenance: compaction, snapshot expiry and orphan-file cleanup.

  • Plain S3 tables can't update rows, aren't atomic, and break on concurrent writes.
  • Iceberg = metadata that lists files per version + an atomic pointer swap in the catalog.
  • Data is still Parquet on S3; any engine can read it.

How Iceberg works: the metadata tree

An Iceberg table is a tree of files. At the top, the catalog points to the current metadata file (JSON). The metadata file lists the table's schema, partition spec, properties and every snapshot. Each snapshot points to a manifest list, which points to manifest files, which list the actual data files with their row counts and column min/max values. A write never edits existing files; it adds new ones and moves the catalog pointer.

Why reads are fast

To answer WHERE order_date = '2026-11-03' AND amount > 5000, Spark reads the metadata file, the manifest list (skipping manifests whose partition range doesn't match), then the manifests (skipping data files whose amount max is ≤ 5000). It never lists S3 folders. This is why Iceberg plans big tables faster than Hive-style tables.

Interview: What happens physically when you commit to an Iceberg table?

Data files are written first, then a manifest for the new files, then a new manifest list representing the new snapshot, then a new metadata JSON that includes that snapshot. Finally the catalog's pointer is updated with a compare-and-swap from the old metadata location to the new one. If the swap fails because someone else committed, Iceberg validates for conflicts and retries on the latest metadata. Old files are never modified, which is what makes time travel and snapshot isolation possible.

  • Catalog → metadata.json → manifest list (snapshot) → manifests → data files.
  • Files are immutable; a commit is an atomic pointer swap.
  • Manifests carry stats, so planning skips files without listing S3.

Writing: append, overwrite, MERGE, delete

Iceberg supports four kinds of writes. Append adds rows. Overwrite partitions replaces whole partitions found in your data. MERGE matches incoming rows to existing rows by a key and updates, deletes or inserts each one: the standard way to apply changes (CDC, upserts). DELETE / UPDATE change rows matching a condition. Every one of them creates a new snapshot.

Append and partition overwritepyspark
new_orders.writeTo("glue_catalog.sales.orders").append()              # add rows
fixed_day.writeTo("glue_catalog.sales.orders").overwritePartitions()  # replace only the partitions present
# SQL equivalents
spark.sql("INSERT INTO glue_catalog.sales.orders SELECT * FROM new_orders")
spark.sql("INSERT OVERWRITE glue_catalog.sales.orders SELECT * FROM fixed_day")   # follows partitionOverwriteMode: set dynamic!

Why the source must be deduplicated

If two source rows match the same target row, MERGE fails with an error that a target row matched multiple source rows (the SQL standard forbids it). That is why the subquery keeps one row per key. The s.updated_at > t.updated_at condition makes the MERGE safe to re-run and protects against late, older changes overwriting newer data.

Delete and update

Row-level changesspark sql

Write efficiently

  • Filter the target in the ON clause when possible (AND t.order_ts >= '2026-10-01') so Iceberg scans fewer files to find matches.
  • Set write.distribution-mode to hash (or range with a sort order) so each partition is written by few tasks, giving fewer, larger files.
  • Run frequent small MERGEs with merge-on-read, and compact regularly.
Interview: How do you implement CDC upserts from DMS into Iceberg?

DMS writes change files to S3 with an operation column (I/U/D) and a change timestamp. A Glue job reads the new files (bookmarks or a high-water mark), deduplicates to the latest change per primary key with row_number, and runs a MERGE into the Iceberg table: delete when the operation is D, update when matched and the change is newer, insert when not matched. The table uses merge-on-read for cheap frequent commits and is compacted on a schedule. Because MERGE is keyed and guarded by the timestamp, a retried batch does not create duplicates.

  • append / overwritePartitions / MERGE / DELETE-UPDATE: each makes a snapshot.
  • Deduplicate the MERGE source; guard updates with a timestamp.
  • Deleted rows live on in old snapshots until expiry.

Copy-on-write vs merge-on-read

Parquet files can't be edited. So when you update or delete one row, Iceberg has two choices. Copy-on-write (COW) rewrites the whole data file containing that row, without it. Writes are slow; reads stay fast. Merge-on-read (MOR) leaves the data file alone and writes a small delete file saying “row 4 of file A is deleted”. Writes are fast; readers must combine data and delete files until compaction merges them.

Snapshots, time travel, rollback, branches

Every commit creates a snapshot: a complete, read-only version of the table at that moment. Because old snapshots are kept until you expire them, you can query the table as it was (time travel), undo a bad load (rollback), and prepare changes in isolation before publishing them (branches).

Time travel and rollbackspark sql
-- what did the table look like before last night's load?
SELECT * FROM glue_catalog.sales.orders TIMESTAMP AS OF '2026-11-02 03:00:00';
SELECT * FROM glue_catalog.sales.orders VERSION AS OF 4812391123;          -- snapshot id

-- which snapshots exist?
SELECT committed_at, snapshot_id, operation, summary['added-records'] AS added
FROM glue_catalog.sales.orders.snapshots ORDER BY committed_at;

-- undo the bad load (metadata only: instant)
CALL glue_catalog.system.rollback_to_snapshot('sales.orders', 4812391123);
CALL glue_catalog.system.rollback_to_timestamp('sales.orders', TIMESTAMP '2026-11-02 03:00:00');

A branch is a named line of snapshots, like a Git branch. You can write a day's load to a branch, run data-quality checks on it, and only then make it visible on main. A tag is a named, retained snapshot (for example month-end for auditors).

Schema evolution and hidden partitioning

Iceberg gives every column a permanent numeric ID. Files store values by ID, not by name, so renaming a column, adding one, dropping one or widening a type changes only metadata, and old files are still read correctly. Hidden partitioning means you partition by a transform of a real column (like the day of a timestamp), so users filter on the column they know and Iceberg prunes partitions automatically.

Schema changes (metadata only, no rewrite)spark sql
ALTER TABLE glue_catalog.sales.orders ADD COLUMN channel STRING;
ALTER TABLE glue_catalog.sales.orders RENAME COLUMN status TO order_status;
ALTER TABLE glue_catalog.sales.orders ALTER COLUMN qty TYPE BIGINT;          -- int → long is allowed
ALTER TABLE glue_catalog.sales.orders DROP COLUMN legacy_flag;
ALTER TABLE glue_catalog.sales.orders ALTER COLUMN channel AFTER customer_id;

Allowed type changes are safe widenings: int → long, float → double, decimal precision increase. Anything else (string → int) needs a new column and a backfill. To let writers add new columns automatically, set the table property write.spark.accept-any-schema=true and write with .option("mergeSchema", "true").

Hive-style

PARTITIONED BY (days(order_ts)). Users write WHERE order_ts >= '2026-11-03' and Iceberg prunes. Transforms: years, months, days, hours, bucket(n, col), truncate(n, col), or identity.

  • Columns tracked by ID → safe add/rename/drop/widen.
  • Partition by transforms; users filter on real columns.
  • Partition evolution changes the spec for new data only.

Table maintenance: what, why, when

Iceberg never changes or deletes files on its own. Every commit only adds files: new data files, new manifests, a new metadata file. Over time that leaves three kinds of waste: too many small files (slow queries), old snapshots holding on to files nobody needs (storage cost, and deleted data that is not really gone), and orphan files from failed jobs that no snapshot references. Maintenance is the scheduled clean-up of each. Without it, an Iceberg table gets slower and more expensive every week.

Think of a busy office's filing cabinet. People keep adding small notes instead of updating the main document (small files and delete files). Every old version of every document is kept “just in case” (snapshots). Drafts from cancelled projects lie around with no folder (orphans). Once a week someone merges notes into clean documents, shreds versions older than the retention policy, and throws away unclaimed drafts. That person is your maintenance job.

Each procedure explained

1. Compaction: rewrite_data_files

Why: queries open fewer files, read bigger sequential chunks, skip more data with sorted files, and stop applying thousands of delete files. What it does: reads groups of small files in a partition and writes them back as files near the target size (table property write.target-file-size-bytes, 512 MB by default), then commits a replace snapshot. Readers are never blocked.

Compaction optionsspark sql
-- default: bin-pack (just combine files), whole table
CALL glue_catalog.system.rewrite_data_files(table => 'sales.orders');

-- only recent partitions, and allow partial commits on big tables
CALL glue_catalog.system.rewrite_data_files(
  table   => 'sales.orders',
  where   => 'order_ts >= TIMESTAMP ''2026-10-27 00:00:00''',
  options => map('min-input-files', '5',
                 'target-file-size-bytes', '536870912',
                 'partial-progress.enabled', 'true'));

-- sort while compacting: much better pushdown for lookups by customer
CALL glue_catalog.system.rewrite_data_files(
  table => 'sales.orders', strategy => 'sort', sort_order => 'customer_id ASC NULLS LAST');

-- z-order for queries that filter on two columns together
CALL glue_catalog.system.rewrite_data_files(
  table => 'sales.orders', strategy => 'sort', sort_order => 'zorder(customer_id, product_id)');

-- MOR tables: compact the delete files themselves
CALL glue_catalog.system.rewrite_position_delete_files(table => 'sales.orders');

2. Snapshot expiry: expire_snapshots

Why: storage cost, faster metadata, and real deletion of erased data. What it does: removes snapshots older than older_than (default: 5 days ago), always keeping at least retain_last (default 1), then deletes data and metadata files no longer reachable from any kept snapshot. Trade-off: you can no longer time-travel or roll back past the oldest kept snapshot, so align retention with your recovery needs.

Expirespark sql
CALL glue_catalog.system.expire_snapshots(
  table       => 'sales.orders',
  older_than  => TIMESTAMP '2026-10-27 00:00:00',   -- keep 7 days of history
  retain_last => 10);                               -- but never fewer than 10 snapshots

3. Orphan file removal: remove_orphan_files

Why: failed or killed writers leave data files in S3 that no metadata points to; they cost money forever. What it does: lists every file under the table location, compares with all files referenced by metadata, and deletes the unreferenced ones older than older_than (default 3 days). The margin protects files that a running job has written but not committed yet. Never set it to minutes.

Find, then removespark sql
CALL glue_catalog.system.remove_orphan_files(table => 'sales.orders', dry_run => true);   -- list only
CALL glue_catalog.system.remove_orphan_files(table => 'sales.orders',
                                             older_than => TIMESTAMP '2026-10-31 00:00:00');

4. Manifest rewrite: rewrite_manifests

Why: many small commits create many small manifests; planning reads all of them. What it does: rewrites manifests so they are fewer and grouped by partition. Run it weekly or when planning time grows.

CALL glue_catalog.system.rewrite_manifests('sales.orders');

Let AWS do it: Glue Data Catalog table optimizers

For Iceberg tables in the Glue Data Catalog you can switch on three managed optimizers per table (console, CLI or API) or at catalog level through Lake Formation:

  • Snapshot retention: expires snapshots by age and count and removes the files they held.
  • Orphan file deletion: periodically removes unreferenced files.

Maintenance mistakes
  • Compacting but never expiring: storage keeps growing, because old snapshots still hold the small files.
  • remove_orphan_files with a tiny older_than: deletes files a running job is about to commit.
  • Running compaction and a big MERGE on the same partitions at the same time: one commit fails on conflict. Schedule them apart or compact older partitions only.
  • Expiring so aggressively that you lose the ability to roll back a bad load.
Interview: What maintenance do Iceberg tables need, and why?

Four things. Compaction with rewrite_data_files, because frequent writes create small files and merge-on-read creates delete files that slow every read; I compact recent partitions, sometimes with a sort or z-order. Snapshot expiry with expire_snapshots, because every snapshot keeps its files alive: expiring frees storage, speeds metadata and completes GDPR deletes, at the cost of shorter time travel. Orphan cleanup with remove_orphan_files, for files from failed writes, with a safety margin of a few days. And rewrite_manifests to keep planning fast. On AWS I would enable the Glue Data Catalog optimizers for compaction, snapshot retention and orphan deletion, or use S3 Tables which manage it automatically.

  • Compaction = fewer, bigger (sorted) files; applies deletes.
  • Expire snapshots = frees storage and really deletes data; limits time travel.
  • Orphans = files from failed writes; keep a 3-day margin.
  • Order: compact → expire → rewrite manifests → orphans. Or use Glue optimizers / S3 Tables.

Concurrent writers and conflicts

Iceberg uses optimistic concurrency: writers don't lock the table. Each writer prepares its commit, then tries to swap the catalog pointer. If someone else committed first, Iceberg checks whether the two changes actually conflict. Two appends never conflict, so it simply retries. Two jobs rewriting or deleting the same files do conflict, and one fails with CommitFailedException or a validation error.

Writer AWriter B (same time)Result
AppendAppendBoth succeed (automatic retry)
MERGE on November partitionsAppend October dataUsually both succeed (no overlapping files)
MERGE on partition XCompaction of partition XOne fails: both replace the same files
MERGEMERGE on the same rowsOne fails validation (serializable isolation)
  • Increase retries for busy tables: commit.retry.num-retries (default 4) and commit.retry.min-wait-ms.
  • Isolation level for MERGE/UPDATE/DELETE: write.merge.isolation-level = serializable (default, strict) or snapshot (allows more concurrency).
  • Design so writers touch different partitions, and schedule compaction away from heavy MERGE windows (or compact only older partitions).
  • No locks; conflicts detected at commit.
  • Appends never conflict; overlapping rewrites do.
  • Separate writers by partition and time.

Iceberg interview questions

Why Iceberg over plain Parquet with Glue partitions?

ACID commits so readers never see partial writes, row-level MERGE/UPDATE/DELETE, schema evolution by column ID, hidden partitioning with partition evolution, time travel and rollback, file-level statistics in manifests that avoid S3 listing during planning, and safe concurrent writers. The cost is regular maintenance.

Explain the Iceberg metadata layers.

Catalog pointer → metadata JSON (schema, partition specs, snapshots, properties) → manifest list per snapshot (which manifests, with partition ranges) → manifests (data and delete files with row counts and column bounds) → data files in Parquet.

Copy-on-write vs merge-on-read: which would you pick for hourly CDC?

Merge-on-read, because each hourly MERGE then writes small delete files instead of rewriting large data files. I would schedule daily compaction (including position-delete compaction) so readers don't pay for accumulated deletes, and keep copy-on-write for daily batch tables that are read heavily.

Your Iceberg table's queries got slow over months. Diagnose.

Query the files metadata table for file counts and average size per partition, all_delete_files for delete-file buildup, snapshots for how many snapshots exist, and manifests for manifest count. Typical fixes: compaction (with sort or z-order on filter columns), snapshot expiry, manifest rewrite, and enabling Glue table optimizers so it stays healthy.

How do you undo a bad load?

Find the last good snapshot in table.snapshots or table.history and call rollback_to_snapshot (or rollback_to_timestamp). It is a metadata change, so it is instant. Then fix and re-run the job; with a keyed MERGE the re-run is safe. To prevent it, use write-audit-publish with a branch.

Is data really deleted after DELETE FROM for GDPR?

Not until the snapshots that still reference the old data files are expired and those files are removed. Until then, time travel can still read the deleted rows. A GDPR process therefore runs the DELETE, then expire_snapshots past that point (and, for merge-on-read, compaction so the original data files are rewritten without the rows).

How does hidden partitioning differ from Hive partitioning?

Hive partitioning requires an explicit partition column and users must filter on it to prune. Iceberg partitions by a transform of a source column (days, hours, bucket, truncate) stored in metadata, so users filter on the source column and pruning happens automatically; the partition scheme can also evolve without rewriting existing data.

What is the role of the Glue Data Catalog with Iceberg?

It stores the pointer to each table's current metadata file and performs the atomic compare-and-swap on commit. Athena, EMR, Glue and Redshift all find the table there. It also hosts managed table optimizers for compaction, snapshot retention and orphan cleanup.

Event time, windows and watermarks

Event time is when something happened (a click at 10:03); processing time is when Spark sees it (maybe 10:09, because a phone was offline). To count clicks per 5-minute window correctly, Spark must keep windows open for late events. A watermark tells Spark how late events may be: “wait up to 10 minutes, then close the window, write it out and forget its state”.

Windowed counts with a watermarkpyspark
views = (events
         .withWatermark("event_ts", "10 minutes")                       # how late data may be
         .groupBy(F.window("event_ts", "5 minutes"), "page_id")          # tumbling 5-minute windows
         .agg(F.count("*").alias("views")))
# sliding windows: F.window("event_ts", "10 minutes", "5 minutes")
# session windows: F.session_window("event_ts", "30 minutes")

# streaming dedup within the watermark (Spark 3.5)
deduped = events.withWatermark("event_ts", "1 hour").dropDuplicatesWithinWatermark(["event_id"])
Without a watermark

An aggregation keeps state for every window forever; memory grows until the job fails. Always set a watermark on stateful streaming queries (aggregations, dedup, stream-stream joins).

  • Event time ≠ processing time. Windows use event time.
  • Watermark = max event time − allowed lateness; older state is dropped.
  • Later-than-watermark events are discarded.

Exactly-once, foreachBatch and AWS streaming

“Exactly once” means every input event affects the output once, even after crashes and retries. Spark gets there with three ingredients: a replayable source (Kafka/Kinesis offsets), the checkpoint recording which offsets each batch covered, and an idempotent or transactional sink (Iceberg commits, or a MERGE keyed on the data). If the sink is a plain append to files or a database insert, a replayed batch can duplicate rows.

foreachBatch: run batch code (like MERGE) per micro-batchpyspark
def upsert(batch_df, batch_id):
    (batch_df.withColumn("rn", F.row_number().over(
         W.partitionBy("user_id").orderBy(F.desc("updated_at"))))
      .filter("rn = 1").drop("rn")
      .createOrReplaceTempView("updates"))
    batch_df.sparkSession.sql("""
        MERGE INTO glue_catalog.crm.users t USING updates s ON t.user_id = s.user_id
        WHEN MATCHED AND s.updated_at > t.updated_at THEN UPDATE SET *
        WHEN NOT MATCHED THEN INSERT *""")

(cdc_stream.writeStream
   .foreachBatch(upsert)
   .option("checkpointLocation", "s3://chk/users_upsert/")
   .trigger(availableNow=True)          # run as a scheduled incremental job
   .start().awaitTermination())

A replayed batch runs the same MERGE again; because it is keyed and guarded by updated_at, the result is the same. That is exactly-once in effect. batch_id can also be stored in the target to skip a batch already applied.

MERGE INTO glue_catalog.dw.dim_customer t
USING (
  SELECT s.customer_id AS merge_key, s.* FROM stg_customer s          -- normal match: expire / insert new
  UNION ALL
  SELECT NULL AS merge_key, s.* FROM stg_customer s                   -- changed rows again with NULL key:
  JOIN glue_catalog.dw.dim_customer d                                  --   they can never match, so they INSERT
    ON d.customer_id = s.customer_id AND d.is_current
   AND NOT (d.name <=> s.name AND d.city <=> s.city)
) u
ON t.customer_id = u.merge_key AND t.is_current
WHEN MATCHED AND NOT (t.name <=> u.name AND t.city <=> u.city) THEN
  UPDATE SET is_current = false, end_date = date_sub(current_date(), 1)
WHEN NOT MATCHED THEN
  INSERT (customer_id, name, city, start_date, end_date, is_current)
  VALUES (u.customer_id, u.name, u.city, current_date(), NULL, true)

The trick: each changed customer appears twice in the source. The copy with the real key matches the current row and expires it; the copy with a NULL key cannot match anything, so it is inserted as the new current row. All in one atomic commit. <=> is NULL-safe equality.

19. Idempotent incremental load with a high-water mark

Approach: store the last processed updated_at in a control table; read source rows newer than it minus a small lookback (to catch late commits); MERGE on the key; advance the mark only after the MERGE succeeds.

Show solution
Solutionpyspark
hwm = (spark.table("glue_catalog.ops.load_control")
            .filter("table_name = 'orders'").select("last_updated_at").first()[0])

query = f"""(SELECT * FROM orders
             WHERE updated_at > TIMESTAMP '{hwm}' - INTERVAL '2 hours') q"""     # 2 h lookback
new = spark.read.format("jdbc").options(**jdbc_opts).option("dbtable", query).load()

new.createOrReplaceTempView("new_orders")
spark.sql("""
  MERGE INTO glue_catalog.curated.orders t
  USING (SELECT * FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) rn
                        FROM new_orders) WHERE rn = 1) s
  ON t.order_id = s.order_id
  WHEN MATCHED AND s.updated_at >= t.updated_at THEN UPDATE SET *
  WHEN NOT MATCHED THEN INSERT *""")

new_hwm = new.agg(F.max("updated_at")).first()[0]
if new_hwm is not None:                                       # only after the MERGE committed
    spark.sql(f"UPDATE glue_catalog.ops.load_control SET last_updated_at = TIMESTAMP '{new_hwm}' "
              "WHERE table_name = 'orders'")

Why it is safe to re-run: the overlap window plus a keyed, timestamp-guarded MERGE means overlapping or repeated reads never create duplicates, and the mark only moves forward after success.

Scenario questions with model answers

Senior rounds are mostly scenarios. Use the same shape every time: clarify (size, platform, SLA) → hypothesis → evidence (Spark UI, plan, logs) → fix → prevent. Numbers make your answer believable.

1. A join between a 2 TB fact table and a 40 GB dimension takes 3 hours. Walk me through it.

Evidence: SQL tab shows a SortMergeJoin with two Exchanges; the stage's max task reads 50× the median, so the join key is skewed; reduce tasks spill.

Fixes in order: (1) select only needed columns and filter both sides before the join; 40 GB may shrink to a few GB, which AQE can broadcast at run time or I can broadcast with a raised threshold if executors have memory; (2) find hot keys; NULL or default IDs are filtered or handled separately; (3) confirm AQE split the skewed partitions (skew=true in the final plan), tune the thresholds; (4) salt the hot keys if AQE can't; (5) right-size shuffle partitions: 2 TB / 200 MB ≈ 10,000, or let AQE coalesce from a high start; (6) if this join runs every day, store both tables bucketed on the key in Iceberg and use storage-partitioned joins to remove the shuffle.

2. A Glue job fails with “Container killed … exceeding memory limits” only at month-end.

Month-end data is bigger and probably concentrated on some keys. In the Spark UI from event logs I check whether the same task index fails every attempt (data-driven) or random tasks fail (resource-driven). A container kill means off-heap overhead, so I suspect Python UDFs, Arrow batches or too many cores per executor. Fixes: replace UDFs with built-ins, reduce rows per task (more partitions), fix skew (pre-aggregate, salt), and for that run use a larger or memory-optimised worker (G.2X or R.1X). To prevent it, alarm on Glue observability memory and skew metrics, and make worker type a parameter the workflow can raise at month-end.

3. The daily output has 40,000 small files and Athena is slow.

Files written ≈ write tasks × partition values per task. I fix the writer with repartition("dt") before partitionBy("dt") (or by dt plus a small random bucket for big days), and enable AQE coalescing with parallelismFirst=false and a larger advisory size. I compact existing data with a one-off job or, for Iceberg, rewrite_data_files and the Glue compaction optimizer. Target 256 MB–1 GB files, then compare Athena scanned bytes and runtime before and after.

4. The pipeline wrote duplicate rows after a retry. Why, and how do you stop it?

The job appended output, then failed (or the orchestrator retried after a timeout) before it marked success, and the retry appended again. Bookmarks don't prevent this because they only commit at the end. I make writes idempotent: dynamic partition overwrite for the run date, or an Iceberg MERGE on the business key with a timestamp guard, or write to a run-ID staging location and publish atomically. A uniqueness check before publishing catches anything that slips through.

5. A job is fast in dev and slow in prod with the same code.

Compare: data volume and distribution (prod has hot keys dev doesn't), file counts (prod has small files), Glue version and worker settings, effective configs in the Environment tab, join strategy (a prod dimension above the broadcast threshold flips BHJ to SMJ), catalog partition counts (planning time), and contention (other jobs on the same S3 prefixes or the same source database). I compare the two Spark UIs stage by stage.

6. Reprocess 90 days after a logic bug, safely.

Parameterise the job by date range, run in chunks of a week to bound resources, write to the same partitions with dynamic overwrite or, better, to an Iceberg branch; validate counts and sums against the old output; then publish (fast-forward the branch). Notify downstream consumers, throttle concurrency to protect S3 and source systems, and keep the old snapshot so I can roll back.

7. Upstream added a column and changed amount from int to string. What breaks?

With an explicit schema the new column is ignored and amount becomes NULL in PERMISSIVE mode, or the job fails in FAILFAST. Parquet files with mixed types can throw “column cannot be converted”. I guard with a schema contract check at ingestion (fail or quarantine on breaking changes, allow additive ones), NULL-rate alerts per column, and Iceberg for safe evolution of the curated layer.

8. Design: clickstream JSON lands in S3 every 5 minutes; analysts query it in Athena.

Raw: S3 landing as-is, partitioned by ingest hour. Process: a Glue job with availableNow streaming over the S3 source (or scheduled every 15 minutes via EventBridge and Step Functions), explicit schema, quarantine for bad records, dedup on event_id within a watermark, sessionisation in a daily job. Store: Iceberg tables in the Glue Data Catalog partitioned by days(event_ts), merge-on-read where upserts happen, Glue table optimizers for compaction, snapshot retention and orphan cleanup. Serve: Athena views and pre-aggregated tables for dashboards. Operate: CloudWatch alarms on failures and lateness, DQ checks, SNS alerts, cost tags. I'd quote sizing: events per day, bytes per day, files per day, expected partitions and workers.

9. The driver runs out of memory right at the start, before any task runs.

That's planning-time memory: listing huge numbers of S3 objects or partitions, inferring schema over thousands of JSON files, a gigantic plan from loops, or collecting a broadcast table that is large in memory. Fixes: partition predicates so fewer partitions are listed (Glue catalog partition indexes or Iceberg manifests), explicit schemas, collapsing loops into one select, checkpointing long lineages, disabling the broadcast, and a larger driver (on Glue a larger worker type, since the driver runs on a worker).

10. Cut the cost of a Glue job by half.

First measure DPU-hours and where time goes. Typical wins: auto scaling instead of fixed max workers; Flex for non-urgent jobs; reading less (pruning, Parquet instead of CSV, only needed columns); removing double reads (one action, or cache); replacing UDFs; fixing skew so workers are not idle waiting for one task; compacting small input files; incremental processing instead of full reloads; a sensible timeout so hung runs stop; and, where Spark 4 is acceptable, Glue 6.0's lower DPU price.

11. A workflow of 30 Glue jobs fails randomly at night. Make it robust.

Classify failures from logs: transient (S3 throttling, capacity, JDBC timeouts, concurrent run limits) versus deterministic (data). Add Step Functions retries with exponential backoff only for transient error types, and a Catch that sends an alert with the job run ID. Make every job idempotent so retries are safe. Reduce contention by staggering jobs that write the same table and increasing Iceberg commit retries. Record run metadata (rows in/out, duration) in a control table to spot drift before it fails.

12. Iceberg MERGE jobs are getting slower every week.

Check the table's files and all_delete_files metadata tables: merge-on-read writes delete files, and small files accumulate. Also check whether the MERGE scans the whole table: adding a partition predicate on the target in the ON clause (for example only the last 30 days) limits files read. Fix with compaction including delete files, snapshot expiry, manifest rewrite, and enable Glue table optimizers. Consider a sort order on the merge key to improve file pruning.

13. You must join a 500 GB table to a 300 GB table every day on the same key.

Both sides are too big to broadcast, so a sort-merge join shuffles 800 GB daily. If both tables are written with the same bucketing on the key, the shuffle disappears: with Iceberg, partition both by bucket(256, key) and enable storage-partitioned joins (spark.sql.sources.v2.bucketing.enabled), or use Spark bucketed tables if only Spark reads them. Also pre-filter to the changed partitions only, if the business logic allows incremental joins.

14. Tell me about a hard Spark problem you solved.

Use the story builder: situation with volumes and SLA, the symptom, how you diagnosed it with the Spark UI and plans, what you changed and why you rejected alternatives, and the measured result. Prepare one performance story, one reliability or data-correctness story, and one design story.

Rapid-fire questions

Expect 10 to 15 of these in the first quarter of a senior round. Answer each in two to four sentences. The answers below are written to be said out loud.

cache() vs persist()?

cache() is persist() with the default level, MEMORY_AND_DISK for DataFrames. persist() lets you choose the storage level. Both are lazy.

repartition vs coalesce?

repartition does a full shuffle, can increase or decrease, and gives even partitions. coalesce avoids a shuffle by merging partitions, can only decrease, may be uneven, and reduces the parallelism of the upstream stage it is pipelined with.

Narrow vs wide transformation?

Narrow: each output partition depends on one input partition (filter, select, withColumn); no shuffle. Wide: an output partition needs data from many input partitions (groupBy, join, distinct, orderBy); requires a shuffle and a new stage.

What triggers a new stage?

A shuffle dependency, i.e. a wide transformation such as a non-broadcast join, groupBy, distinct, orderBy, repartition or a window with partitionBy.

How many tasks will a stage have?

One per partition: about input size / 128 MB for a file scan, spark.sql.shuffle.partitions after a shuffle (adjusted by AQE), or n after repartition(n).

What is lineage?

The chain of transformations that produced a dataset. Spark uses it to recompute lost partitions instead of replicating data. Very long lineage slows planning and recovery; checkpointing cuts it.

Broadcast variable vs broadcast join?

A broadcast variable ships a read-only object (like a lookup dict) to each executor once. A broadcast join ships a small table's hash table to each executor so the big table is joined without a shuffle. Same mechanism, different API.

What are accumulators?

Counters that executors add to and the driver reads. Updates inside transformations can be counted twice on task retries; only updates inside actions are guaranteed once.

Why is the default of 200 shuffle partitions often wrong?

It ignores data size: 200 partitions of 5 GB spill and fail; 200 partitions of 1 MB waste scheduling and write tiny files. Size from the shuffle volume, or set a high start and let AQE coalesce.

What does AQE do?

Re-optimises at each shuffle boundary using real statistics: coalesces small partitions, switches sort-merge joins to broadcast or shuffled hash joins, and splits skewed join partitions.

Catalyst vs Tungsten?

Catalyst optimises the query plan (analysis, rule-based and cost-based optimisation, physical planning). Tungsten executes efficiently: binary row format, memory management, whole-stage code generation.

How does Spark recover from a failed task?

It retries the task up to four times, possibly on another executor. Lost executors' tasks are re-run, lost cached partitions recomputed, and lost shuffle output triggers re-running the parent stage for the missing partitions. After repeated failures the job aborts.

What is speculative execution?

Launching duplicate copies of unusually slow tasks and using whichever finishes first. It helps with bad nodes, not skew, and needs idempotent output.

Dynamic allocation?

Spark adds executors when tasks are waiting and removes idle ones. It needs the external shuffle service or shuffle tracking so removed executors' shuffle files stay available.

map vs mapPartitions?

map runs per row; mapPartitions runs once per partition with an iterator, so expensive setup like a database connection happens once per partition.

reduceByKey vs groupByKey?

reduceByKey combines values on the map side before shuffling; groupByKey shuffles every value and builds a list per key, which is slower and can run out of memory.

union vs unionByName?

union matches columns by position, a source of silent bugs; unionByName matches by name and with allowMissingColumns=True fills missing columns with NULL. Neither removes duplicates.

Client vs cluster deploy mode?

Client: the driver runs where you submitted, logs in your terminal, dies if you disconnect. Cluster: the driver runs inside the cluster; used for production.

Why prefer built-in functions over UDFs?

They run in the JVM inside generated code, Catalyst can optimise around them, and they handle NULLs consistently. Python UDFs serialise every row to a Python worker.

Temp view vs global temp view vs table?

A temp view is a session-scoped name for a plan. A global temp view is shared by sessions in one application under global_temp. A table is registered in a catalog such as Glue with data in storage and is visible to other engines.

How does Spark read Parquet efficiently?

It reads the footer, skips row groups using min/max statistics for pushed filters, reads only the needed column chunks and decodes them in vectorised batches.

toPandas() on 50 GB?

Don't: it loads everything into driver memory. Aggregate or sample in Spark first, or use applyInPandas or the pandas API on Spark for distributed pandas logic.

Static vs dynamic partition overwrite?

Static (the default) deletes all partitions under the target path before writing. Dynamic replaces only the partitions present in the DataFrame. Set dynamic for idempotent reloads.

What is a skipped stage?

A stage whose shuffle output already exists from an earlier job in the same application, so Spark reuses it.

How do you test PySpark code?

Pure DataFrame-in, DataFrame-out functions; pytest with a session-scoped local SparkSession; small hand-built inputs with edge cases; assertDataFrameEqual from pyspark.testing; integration tests on sample data in a dev Glue environment; data-quality checks in production.

What is the difference between partitionBy on a window and on a writer?

On a window it defines groups of rows for the calculation and causes a shuffle. On a writer it defines the folder layout on storage. Same word, unrelated features.

What changes in Spark 4 that could break a job?

ANSI mode on by default (invalid casts, overflow and divide-by-zero raise errors), Java 17 and Scala 2.13 only, and Python 3.8 dropped. Most DataFrame code is unchanged.

Glue DynamicFrame vs DataFrame?

DynamicFrames have per-record schemas with choice types and integrate with bookmarks and Glue connectors; DataFrames have fixed schemas and the full optimised Spark API. Common practice: read and write with DynamicFrames where useful, transform as DataFrames.

Execution

  • Action → job → stages (cut at shuffles) → tasks (1 per partition)
  • Narrow = same stage; wide = shuffle
  • Lazy: plan first, run on action; re-runs per action unless cached
  • Driver plans; executors run; driver death = job death

Partitions

  • 100–200 MB each; 2–3× cores
  • Read: 128 MB maxPartitionBytes; gzip = 1 task/file
  • Shuffle: 200 default; AQE coalesces
  • coalesce = no shuffle but shrinks upstream

Joins

  • BHJ: small side < 10 MB est. → no shuffle
  • SMJ: 2 shuffles + 2 sorts
  • SHJ: shuffle, hash per partition
  • BNLJ / Cartesian = missing equality key

AQE

  • Coalesce → 64 MB advisory (set parallelismFirst=false)
  • SMJ → BHJ at run time
  • Skew split: > 5× median AND > 256 MB, joins only

Memory

  • Heap: 300 MB reserved, 60% unified (storage ↔ execution), 40% user
  • Overhead: max(384 MB, 10%), Python lives here
  • Heap OOM → smaller tasks/skew; YARN kill → overhead

Re-optimisation of the remaining query after each shuffle using real data sizes.

Join where the small table is copied to every executor, so the big table is not shuffled.

Storing a table pre-hashed by a key into a fixed number of buckets to avoid shuffles in later joins.

Reduce the number of partitions without a shuffle.

Rewriting many small files into fewer large ones (Iceberg rewrite_data_files).
