Modules: one file, one namespace

A module is simply a .py file. When you import it, Python runs the file top to bottom once, collects everything it defined (functions, classes, variables) into a module object, and gives you a name to reach them. That is the whole trick behind splitting code across files.

A module is like a labelled toolbox. helpers.py is the box called helpers. import helpers puts the whole box on your bench; helpers.add_tax takes one tool out of it. from helpers import add_tax takes the tool out and puts it straight on your bench with no box label.

The four import forms

Ways to importPython

The second import printed nothing. After the first import, Python stores the module object in the dictionary sys.modules. Every later import of the same name, from any file, just returns that cached object.

Why this matters at work

Because a module runs once and is cached, module-level code is shared state. A boto3 client created at the top of a Lambda module is created once per container and reused across invocations, which is good and is AWS's recommended pattern. A list created at module level and appended to in a handler keeps growing across invocations, which is a classic bug.

What a module object holds

Inspect a modulePython
import helpers
print(type(helpers))          # <class 'module'>
print(helpers.__name__)       # 'helpers'
print(helpers.__file__)       # full path of helpers.py
print([n for n in dir(helpers) if not n.startswith("__")])   # ['add_tax']

A module is a namespace: a dictionary of names (helpers.__dict__). Two modules can both define clean() without clashing, because one is transform.clean and the other is utils.clean.

Common mistake

Heavy work at import time: connecting to Redshift, reading S3 or parsing a big file at module level. Every test that imports the module pays that cost, and it fails if AWS is not reachable. Keep import-time code cheap (definitions and constants); do real work inside functions.

A module is a single .py file. On first import Python executes it once, builds a module object holding everything it defined, and caches it in sys.modules, so later imports anywhere in the process return the same object. That's why module-level code should be cheap and side-effect free, and why things like a boto3 client at module level get reused across Lambda invocations.

  • Module = one .py file = one namespace.
  • Import executes the file once; the result is cached in sys.modules.
  • Prefer import x or from x import y; never import * in real code.
  • Keep import-time code cheap; do work in functions.

How Python finds a module

When you write import orders_etl, Python looks through a list of folders called sys.path, in order, and uses the first match. Nearly every ModuleNotFoundError comes from the folder you expect not being on that list, or a different file being found first.

Look at sys.pathShell

Output

The empty first line is '': "the current folder" (with python -c; with python script.py it is the script's folder). Inside an activated virtual environment, the last entry is .venv/lib/python3.13/site-packages.

Shadowing: your file hides a real library

Because the script folder comes first, a file you name json.py, boto3.py, logging.py or pandas.py hides the real library. Then import boto3 loads your file and you get baffling errors like module 'boto3' has no attribute 'client'. Recent Pythons even suggest it in the error: "consider renaming … if it has the same name as a library you intended to import".

Never name your files after libraries

test.py, email.py, queue.py, types.py, select.py, boto3.py, pyspark.py, airflow.py. Use names like s3_client.py or orders_dag.py.

The hack to avoid

sys.path.append("../src") at the top of files, or exporting PYTHONPATH in every terminal. It works on your machine and nowhere else. Install your package into the environment instead; then import orders_etl works the same in tests, scripts, CI and containers.

Python resolves an import by checking sys.modules, then built-ins, then each folder on sys.path in order: script directory, PYTHONPATH, standard library, then site-packages of the active environment. First match wins, which is why a local file named like a library shadows it. For my own code I don't patch sys.path; I install the project into the venv, editable, so imports behave identically everywhere.

  • Lookup order: cache → built-ins → sys.path (script dir, PYTHONPATH, stdlib, site-packages).
  • First match wins → don't name files json.py, boto3.py, test.py.
  • module.__file__ tells you which file was actually imported.
  • Fix imports by installing the project, not by editing sys.path.

Packages and __init__.py

A package is a folder of modules that you can import with dots: orders_etl.transform. The special file __init__.py inside the folder marks it as a regular package and is the code that runs when the package is first imported. It can be empty, and often should be nearly empty.

If a module is a toolbox, a package is a tool cabinet with labelled drawers. __init__.py is the label and the little tray on top of the cabinet: you can put the most-used tools on the tray (from orders_etl import clean_orders) so people don't have to open the right drawer (orders_etl.transform.clean_orders).

What belongs in __init__.py

Good

  • Nothing at all (most sub-packages)
  • A docstring describing the package
  • __version__ = "0.1.0"
  • Re-exports of the public API: from .transform import clean_orders
  • __all__ listing the public names

Avoid

  • Creating clients, connections, Spark sessions
  • Reading config files or env vars that may not exist
  • Importing heavy libraries (pandas, pyarrow) that most users of the package don't need
  • Long chains of imports that cause circular imports

__all__: the public list

__all__ is a list of names. It controls what from package import * exports, and it tells readers, linters and documentation tools "these are the supported names; everything else is internal". It does not stop anyone importing other names explicitly.

Circular imports and how to fix them

A circular import happens when module A imports B while B imports A. Python starts running A, pauses at the import to run B, and B asks A for a name that A hasn't defined yet because A is only half-run. It's almost always a sign that responsibilities are tangled.

orders.pyPython
from customers import get_customer

def get_order(oid):
    return {"id": oid, "customer": get_customer("C1")}
customers.pyPython
from orders import get_order

def get_customer(cid):
    return {"id": cid}
main.py imports ordersShell
$ python main.py
Output
    import orders
  File "/home/sai/c1/orders.py", line 1, in <module>
    from customers import get_customer
  File "/home/sai/c1/customers.py", line 1, in <module>
    from orders import get_order
ImportError: cannot import name 'get_order' from 'orders' (consider renaming '/home/sai/c1/orders.py' if it has the same name as a library you intended to import)

Read the traceback bottom-up: orders → customers → back to orders, which is only half-run, so get_order does not exist yet. (Recent Python versions add a "consider renaming" hint because they cannot tell this apart from shadowing. The real cause here is the cycle; older versions said "partially initialized module … most likely due to a circular import".)

Four fixes, best first

  1. Move the shared piece into a third module. If both need common helpers or models, put them in models.py or common.py that imports neither. Dependencies then flow one way: orders → common ← customers.
  2. Restructure by layer. Low-level modules (config, models, utils) never import high-level ones (pipeline, cli). A cycle usually means a low-level module reached upward.
  3. Import the module, not the name. import orders and calling orders.get_order() inside the function looks the name up at call time, after both modules have finished loading.
  4. Import inside the function as a last resort, or under if TYPE_CHECKING: when the import exists only for type hints.
Fix for type-hint-only cyclesPython
from __future__ import annotations
from typing import TYPE_CHECKING

if TYPE_CHECKING:                     # True only for type checkers, never at runtime
    from orders_etl.pipeline import Pipeline

def describe(p: Pipeline) -> str:
    return f"pipeline for {p.config.bucket}"

A circular import is two modules importing each other at load time; the second one sees the first half-initialised and the name isn't there yet. I fix it structurally: move the shared code into a lower-level module so dependencies are one-directional, or make lower layers never import higher ones. Deferring the import into a function or a TYPE_CHECKING block works, but I treat that as a patch, not the design.

  • Cycle = A imports B imports A; B sees a half-initialised A.
  • Best fix: extract shared code into a third module; keep imports one-directional (low layers never import high layers).
  • Patches: import module instead of from module import name, function-level import, TYPE_CHECKING.

if __name__ == "__main__" explained

Every module has a built-in variable called __name__. Python sets it to the module's import name ("helpers") when the file is imported, and to the special string "__main__" when the file is the one you ran. So if __name__ == "__main__": means "only do this when I am the program being run, not when someone imports me".

Think of a chef's recipe card that also says "if you are the head chef tonight, cook the full menu". When the card is just borrowed by another kitchen (imported), they only take the recipe. When it is the card running tonight's kitchen (run directly), the extra instruction kicks in.

Why you need it

  • Tests import your module. Without the guard, pytest importing load_orders.py would actually run the load against S3.
  • Other code reuses your functions. A Glue job, a Lambda and an Airflow task can all import transform.clean_orders without triggering a run.
  • Multiprocessing needs it. On macOS and Windows, multiprocessing and ProcessPoolExecutor start workers by re-importing your main module. Without the guard, each worker starts more workers. (Linux uses fork by default, but Python 3.14 changed the default start method on Linux to forkserver, so write the guard everywhere.)

The professional pattern: a main() function

Keep the guard to one linePython
import argparse
import logging


def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(prog="load-orders")
    parser.add_argument("--date", required=True)
    args = parser.parse_args(argv)          # argv=None → read sys.argv; tests pass a list
    logging.basicConfig(level=logging.INFO)
    # ... do the work by calling functions ...
    return 0                                # exit code: 0 = success


if __name__ == "__main__":
    raise SystemExit(main())

Putting the logic in main(argv) rather than directly under the if gives you three things. Tests can call main(["--date", "2026-11-17"]). Variables don't leak into module globals. And the same main can be wired up as a console command in pyproject.toml (next lesson).

Glue and Lambda note

A Lambda handler is called by the runtime, which imports your module, so a __main__ block in app.py never runs on Lambda. That makes it a handy place for a local smoke test. Glue Spark jobs run your script as __main__, so code under the guard does run in Glue. Either works; just know which is which.

__name__ is set to the module's import name when it's imported and to "__main__" for the file Python was asked to run. The guard lets one file be both a reusable module and a runnable program: tests and other modules can import its functions without triggering the run. I keep the guard to one line calling main(argv) that returns an exit code, which makes the CLI testable and lets me expose it as a console script.

  • __name__ = "__main__" when run, = module name when imported.
  • Guard = "run only when executed directly".
  • Pattern: def main(argv=None) -> int + raise SystemExit(main()).
  • Needed for safe imports in tests and for multiprocessing.

Gotcha: a package that imports its own module in __init__

If etl/__init__.py does from .transform import clean and you run python -m etl.transform, Python imports etl.transform once through __init__ and then runs it again as __main__. It warns: RuntimeWarning: 'etl.transform' found in sys.modules after import of package 'etl'. The file has run twice. The cure is the same as above: run the package through __main__.py or an entry point, not its inner modules.

  • python file.py = loose script; python -m pkg.mod = module inside its package.
  • __main__.py makes python -m pkg work.
  • [project.scripts] creates a real command that calls module:function.
  • Use python -m pip / python -m pytest, or let uv run pick the right environment.

Modular coding: from one script to modules

Modular code means splitting a program into small pieces that each do one job and talk to each other through clear inputs and outputs. The goal is not more files. The goal is code you can test piece by piece, reuse in a Glue job, a Lambda and an Airflow task, and change without breaking unrelated things.

A one-file pipeline is a kitchen where one cook does everything on one counter. It works until there are three orders at once. A modular kitchen has stations: prep, grill, plating. Each station has one job, a clear hand-off, and can be swapped (a new grill) without retraining everyone.

src/orders_etl/transform.py: pure business rulesPython
def clean_orders(rows: list[dict]) -> list[dict]:
    """Drop rows without an id, keep the latest version of each order, uppercase status."""
    latest: dict[str, dict] = {}
    for row in rows:
        oid = row.get("order_id")
        if not oid:
            continue
        if oid not in latest or row["updated_at"] > latest[oid]["updated_at"]:
            latest[oid] = row
    return [
        {**r, "status": r.get("status", "unknown").upper()}
        for r in sorted(latest.values(), key=lambda r: r["order_id"])
    ]

import json

import boto3


def list_keys(bucket: str, prefix: str, s3=None) -> list[str]:
    s3 = s3 or boto3.client("s3")
    keys = []
    for page in s3.get_paginator("list_objects_v2").paginate(Bucket=bucket, Prefix=prefix):
        keys += [obj["Key"] for obj in page.get("Contents", [])]
    return keys


def read_json_lines(bucket: str, key: str, s3=None) -> list[dict]:
    s3 = s3 or boto3.client("s3")
    body = s3.get_object(Bucket=bucket, Key=key)["Body"].read().decode("utf-8")
    return [json.loads(line) for line in body.splitlines() if line.strip()]

How small is small enough?

A function should fit on a screen and have a name that says what it does without "and" (read_and_clean_and_write is three functions). A module groups functions that change together, usually 50–400 lines. Don't create a module per function; that's the opposite mistake.

I structure pipelines as a pure core with I/O at the edges. Business rules live in pure functions that take and return data, so they're trivially unit-testable and reusable from Glue, Lambda or Airflow. I/O modules wrap boto3 and accept the client as a parameter, which makes them easy to fake. A thin pipeline or CLI layer wires everything together. Dependencies only point downward, which also prevents circular imports.

  • Split by responsibility: config, extract (I/O), transform (pure), load (I/O), pipeline (wiring), cli (entry).
  • Pure functions for business rules → tests need no AWS.
  • Pass clients in (s3=None) → easy to fake.
  • Imports flow one way: high level → low level.

Config, logging and CLIs done right

Three small things separate a script from a professional tool. Configuration comes from the environment, not from constants buried in code. Logging goes through the logging module, not print. And a CLI parses its arguments in a testable main().

Config: one immutable object, built at the edge

src/orders_etl/config.pyPython

from dataclasses import dataclass


@dataclass(frozen=True)

    bucket: str
    prefix: str = "raw/orders/"
    region: str = "ap-south-1"

The limits of the raw way

  • pip freeze dumps everything in the venv, including things you installed by hand to try out. You can't tell direct dependencies from transitive ones.
  • pip uninstall leaves orphaned dependencies behind.
  • No lock file across platforms: a freeze from your Mac may pin a version with no Linux wheel.
  • No Python version management: you install Python yourself (pyenv, Homebrew, deadsnakes).
  • Slow on large data stacks (pyarrow, pandas, boto3 plus stubs) and in CI.

The next lesson shows how teams patched these gaps with requirements.in and pip-tools. After that come pyproject.toml and uv, which fix them properly.

Common mistakes

Committing .venv/ to Git (add it to .gitignore). Moving or renaming a venv folder (venvs hard-code their path; delete and recreate). Running sudo pip install. Mixing conda and pip in one environment.

  • python -m venv .venv → source .venv/bin/activate → pip install … → pip freeze > requirements.txt.
  • Activation only changes PATH; .venv/bin/python works without it.
  • pip install -e . installs your own project in editable mode.
  • Raw pip can't tell direct from transitive dependencies and doesn't lock across platforms.

Where did setup.py go?

Old projects have setup.py calling setuptools.setup(name=..., install_requires=[...]). It is executable code, which was the problem: tools had to run it to learn the dependencies. Setuptools now reads [project] from pyproject.toml too. When you inherit a setup.py project, the migration is mostly copying install_requires into dependencies and entry_points into [project.scripts].

pyproject.toml is the standard project file. [project] holds metadata, requires-python and runtime dependencies as ranges. Optional-dependencies are user-facing extras published with the package; dependency-groups are dev-only and never published. [build-system] names the backend that builds the wheel, and [tool.*] tables hold config for pytest, ruff, mypy and the package manager. Exact versions don't go here; they go in the lock file.

  • [project] = metadata + runtime dependencies (ranges).
  • Extras (optional-dependencies) are for users; dependency-groups are for developers.
  • [build-system] picks the backend; [tool.x] configures tools.
  • Pins belong in the lock file, not in pyproject.toml.

Why it caught on in data teams

  • Speed in CI and Docker. Data stacks are heavy (pyarrow, pandas, boto3, great-expectations). Cold installs drop from minutes to seconds, and warm installs from a global cache take milliseconds.
  • One universal lock file. uv.lock covers macOS laptops, Linux CI and AWS together, unlike a pip freeze made on one machine.
  • No activation dance. uv run always uses the project's environment, so the "wrong Python" class of bugs disappears.
  • Python versions included. Matching Glue 5.1's Python 3.11 locally is one command.
  • Standards-based. It uses the normal pyproject.toml [project] table, so you can leave uv later without rewriting anything.
Version note

uv is still versioned 0.x and moves quickly. uv 0.13.0 (9 Oct 2026) made Python 3.15 the default when it downloads a Python, and it changed the cache format, so the first run after upgrading re-downloads. Pin the uv version in CI (and in the uv_build requirement) so upgrades are deliberate.

  • uv = Python installer + venv + pip + pip-tools + pipx + build/publish, in one fast binary.
  • It uses standard pyproject.toml, so there is no lock-in.
  • Pin its version in CI because it changes often.

The lock file: uv.lock

A lock file records the exact outcome of dependency resolution: every package (direct and transitive), its exact version, where it came from and the hashes of its files. Install from the lock and you get the same environment, byte for byte, on every machine. pyproject.toml says what you accept; uv.lock says what you get.

pyproject.toml is a shopping list: "milk, any brand, at least 1 litre". uv.lock is the receipt: "Heritage toned milk 1L, batch 4471, ₹68". Hand the receipt to anyone and they come back with exactly the same items.

--locked vs --frozen

--locked (CI, tests)

"Assert the lock is up to date, then install." If a developer edited pyproject.toml but forgot to re-lock, the build fails loudly.

--frozen (Docker layers)

"Trust the lock blindly." Used when pyproject isn't even copied yet, for example installing dependencies before the source code to get better layer caching.

Rules for working with lock files

  1. Commit it for applications (Glue jobs, Lambdas, DAG repos). It's what makes deployments reproducible.
  2. Never edit it by hand. Change pyproject.toml or run uv commands, then let uv rewrite the lock.
  3. Merge conflicts in uv.lock: don't hand-merge. Resolve the conflict in pyproject.toml, then run uv lock to regenerate the lock and commit the result.
  4. Upgrade deliberately: a weekly Dependabot or Renovate PR (both support uv.lock) that runs the tests, rather than accidental upgrades.
  5. Libraries: commit the lock too (it keeps CI reproducible), but remember users of your library don't use it; they resolve from your ranges.

uv.lock is a universal, cross-platform record of the fully resolved dependency graph: exact versions, sources and hashes for every platform's wheels. pyproject declares acceptable ranges; the lock pins what we actually run. We commit it, never hand-edit it, regenerate it on conflicts with uv lock, run uv sync --locked in CI so stale locks fail the build, and upgrade with uv lock --upgrade-package through reviewed PRs.

  • Lock = exact versions + sources + hashes for the whole graph, for all platforms.
  • Commit it; never hand-edit; regenerate on conflict.
  • --locked = verify then install (CI); --frozen = trust and install (Docker).
  • Upgrades: uv lock --upgrade-package X, through PRs.

uv pip, uvx, scripts, export and workspaces

Beyond the project workflow, uv has four more modes you'll use. uv pip is a drop-in fast pip for existing requirements-based repos. uvx runs command-line tools without installing them. Which one should my project use?

  • New project: uv + uv.lock. Export requirements.txt or pylock.toml where a deployment target needs it.
  • Existing Poetry project: keep poetry.lock; migrating is optional.
  • Glue / MWAA / plain Docker: they consume requirements.txt, so generate it from your lock in CI. Never hand-write it.
  • Watch pylock.toml: it is the cross-tool standard (accepted in 2025). As pip's support leaves "experimental", expect deployment targets to accept it directly.

All four record exact resolved versions with hashes so installs are reproducible. A pinned requirements.txt is the lowest common denominator but covers only one environment. uv.lock and poetry.lock are universal, cross-platform and tool-specific. pylock.toml is the new PEP 751 standard that any tool can read; pip can write it experimentally, but only for the current platform today. I keep the tool's native lock as the source of truth and export requirements.txt for targets like Glue or MWAA.

  • requirements.txt (pinned) = universal to read, but single-platform.
  • uv.lock / poetry.lock = universal across platforms, tool-specific.
  • pylock.toml = the standard (PEP 751); support is growing.
  • Commit the lock; generate requirements.txt from it for AWS targets.

pytest basics: write, run, read failures

A test is a small function that calls your code with known input and asserts the output is what you expect. pytest finds these functions, runs them all, and shows exactly what differed when one fails. Tests let you refactor a Glue job on Friday without fearing Monday's run.

Your first test file

tests/test_transform.pyPython
from orders_etl.transform import clean_orders


def test_keeps_latest_version(raw_rows):        # raw_rows is a fixture (next lesson)
    result = clean_orders(raw_rows)
    assert [r["order_id"] for r in result] == ["A1", "B7"]

That's all a test is: a function named test_* containing plain assert statements. No classes and no self.assertEqual; pytest rewrites assert so failures show both sides.

How pytest finds tests

  • Files named test_*.py or *_test.py, under testpaths (or the current folder).
  • Functions named test_*, and methods named test_* inside classes named Test* (classes without an __init__).
  • conftest.py files are loaded automatically and share fixtures with every test in their folder and below.

Mocking: Mock, MagicMock, return_value, side_effect

A mock is a stand-in object that pretends to be something slow, expensive or unreachable (S3, Redshift, an HTTP API, the clock). It answers with values you choose and records how it was called, so your test can check "did my code call delete_object with the right key?" without touching AWS.

A mock is a crash-test dummy. You don't need a real person in the car to learn whether the seatbelt works. The dummy behaves the way you configure it, and afterwards its sensors tell you exactly what happened to it.

Why OOP (and when not)

Object-oriented programming (OOP) bundles data and the functions that work on that data into one unit called a class. You then create objects (instances) from the class. A Pipeline object knows its config and how to run; an S3Path knows its bucket and key and how to build a URI.

A class is a cookie cutter; objects are the cookies. One cutter (class S3Path) makes many cookies (raw, curated), each with its own decoration (bucket and key), all the same shape (same methods).

The four pillars in one table

InheritanceA new class reuses and extends an existing oneS3JsonExtractor(Extractor)→
PolymorphismDifferent classes answer the same method call in their own wayEvery extractor has .extract(); the pipeline doesn't care which→

Where you already use OOP every day

  • boto3.client("s3") returns an object; .get_object() is a method.
  • spark.read.parquet(...) returns a DataFrame object; .filter() returns another one.
  • Airflow operators are classes: class GlueJobOperator(BaseOperator), and you subclass BaseOperator to write custom ones.
  • datetime, Path, Decimal, exceptions: all classes.

When a class is the right tool, and when it isn't

Use a class when

  • Data and behaviour belong together and the data must stay valid (config, a connection wrapper)
  • You need several interchangeable implementations (S3 vs API extractor)
  • You keep state across calls (a client with retries and a cache)
  • A framework expects it (Airflow operators, unittest)

Prefer a function when

  • It's a stateless transformation: clean_orders(rows) -> rows
  • A class would have just __init__ and one method
  • You'd be wrapping a single value with no rules

Good Python mixes both: pure functions for transformations, small classes for things with identity and rules, and dataclasses for records.

  • Class = blueprint (data + behaviour); object = one instance.
  • Pillars: encapsulation, inheritance, polymorphism, abstraction.
  • Don't force classes on stateless transformations.

The same bug in two shapes

A list or dict defined in the class body, or used as a default argument, is created once and shared. In a long-running Lambda container this leaks data between invocations. Create mutable values in __init__, or use None as the default and create the list inside the function.

A class is a blueprint; calling it creates an instance and runs __init__ to set instance attributes on self. self is just the instance passed explicitly as the first argument: obj.method() is Class.method(obj). Instance attributes are per object; class attributes are shared and found by lookup falling back from instance to class. Never put mutable defaults at class level or in default arguments, because they're shared.

  • __init__ initialises a new object; self = that object.
  • obj.method() == Class.method(obj).
  • Instance attributes per object; class attributes shared.
  • Never use mutable class attributes or default arguments for per-object data.

Inheritance, overriding and super()

Inheritance lets a new class (child or subclass) start with everything an existing class (parent or base) has, then add or change parts. Redefining a parent's method in the child is overriding. super() calls the parent's version, most often in __init__, so the parent can set up its own attributes.

o4_inherit.pyPython
class Extractor:
    def __init__(self, source: str):
        self.source = source

    def extract(self) -> list[dict]:
        raise NotImplementedError

    def describe(self) -> str:
        return f"{type(self).__name__} reading {self.source}"

Inheritance is the strongest coupling there is

A child depends on its parent's internals. Deep chains (Base → S3Base → S3JsonBase → S3JsonGzip…) become fragile fast. Keep hierarchies shallow (one or two levels), inherit to share a contract, and use composition to share behaviour.

  • class Child(Parent): inherit, then override or extend.
  • super().__init__(...) in the child's __init__.
  • isinstance / issubclass check relationships; __mro__ shows the lookup order.
  • Keep hierarchies shallow.

Multiple inheritance, MRO and mixins

A Python class can inherit from several parents. Python then needs one clear order for looking up methods: the Method Resolution Order (MRO), computed by the C3 algorithm. super() doesn't mean "my parent"; it means "the next class in the MRO". That's what makes cooperative mixins work.

o5_mro.pyPython
class Base:
    def run(self):
        print("Base.run")

class LoggingMixin(Base):
    def run(self):
        print("LoggingMixin: start")
        super().run()
        print("LoggingMixin: end")

class RetryMixin(Base):
    def run(self):
        print("RetryMixin: attempt 1")
        super().run()

class Job(LoggingMixin, RetryMixin):
    def run(self):
        print("Job.run")
        super().run()

Job().run()
print([c.__name__ for c in Job.__mro__])

Mixins in practice

A mixin is a small class that adds one capability (logging, retries, serialisation) and is meant to be combined, never used alone. Rules: mixins call super() so the chain continues, take no required __init__ arguments, and list before the main base class: class OrdersJob(LoggingMixin, RetryMixin, BaseJob).

Diamond problem, solved

Both mixins inherit from Base (a diamond), yet Base.run ran exactly once. C3 linearisation guarantees each class appears once in the MRO, and in an order that respects every class's own parent order.

  • MRO = lookup order; see it with Class.__mro__.
  • super() = next class in the MRO of the actual object, not "my parent".
  • Mixins: small, single-purpose, always call super(), listed first.

Polymorphism, duck typing and Protocols

Polymorphism means "many shapes": code calls writer.write(rows) and each kind of writer does its own thing. In Python you don't even need a shared parent class. If an object has the right method, it works. That's duck typing: "if it walks like a duck and quacks like a duck…". Protocols let type checkers verify duck typing.

o7_protocol.pyPython
from typing import Protocol, runtime_checkable


@runtime_checkable
class Writer(Protocol):
    def write(self, rows: list[dict]) -> int: ...


class S3Writer:                       # no inheritance from Writer at all
    def write(self, rows):
        return len(rows)


class ListWriter:
    def __init__(self):
        self.out = []
    def write(self, rows):
        self.out += rows
        return len(rows)


def publish(writer: Writer, rows: list[dict]) -> None:
    print(type(writer).__name__, "wrote", writer.write(rows))


for w in (S3Writer(), ListWriter()):
    publish(w, [{"id": 1}, {"id": 2}])
print(isinstance(ListWriter(), Writer), isinstance("text", Writer))

Abstraction with abstract base classes

An abstract base class (ABC) defines a contract: "every Loader must have load(rows)". It can't be instantiated itself, and Python refuses to create any subclass instance that hasn't implemented every @abstractmethod. The ABC can also provide shared concrete methods built on the abstract ones.

Dunder (magic) methods

Dunder methods ("double underscore", like __len__) are hooks Python calls for you. len(x) calls x.__len__(), x + y calls x.__add__(y), print(x) calls x.__str__(). Implement them and your objects behave like built-in types.

o8_dunder.pyPython
class Batch:
    def __init__(self, name: str, rows: list[dict]):
        self.name = name
        self.rows = rows

    def __repr__(self):                    # for developers / logs / REPL
        return f"Batch(name={self.name!r}, rows={len(self.rows)})"

    def __str__(self):                     # for humans / print()
        return f"{self.name} ({len(self.rows)} rows)"

    def __len__(self):
        return len(self.rows)

    def __iter__(self):
        return iter(self.rows)

    def __getitem__(self, i):
        return self.rows[i]

    def __contains__(self, order_id):
        return any(r["id"] == order_id for r in self.rows)

    def __add__(self, other):
        return Batch(f"{self.name}+{other.name}", self.rows + other.rows)

    def __eq__(self, other):
        return isinstance(other, Batch) and self.rows == other.rows

    def __bool__(self):
        return bool(self.rows)

Composition over inheritance and SOLID

Composition means building an object out of other objects it has (HAS-A), instead of inheriting from them (IS-A). A Pipeline has a source, steps and a sink, each swappable on its own. "Favour composition over inheritance" is the most quoted rule of object-oriented design, and SOLID is the five-principle checklist behind it.

o12_compose.pyPython
from abc import ABC, abstractmethod


class Source(ABC):
    @abstractmethod
    def read(self) -> list[dict]: ...

class Sink(ABC):
    @abstractmethod
    def write(self, rows: list[dict]) -> int: ...


class ListSource(Source):
    def __init__(self, rows): self.rows = rows
    def read(self): return list(self.rows)

class MemorySink(Sink):
    def __init__(self): self.data = []
    def write(self, rows):
        self.data += rows
        return len(rows)


class Pipeline:
    """HAS-A source, transforms and a sink (composition), instead of IS-A."""
    def __init__(self, source: Source, sink: Sink, steps=()):
        self.source, self.sink, self.steps = source, sink, list(steps)

    def run(self) -> int:
        rows = self.source.read()
        for step in self.steps:
            rows = step(rows)
        return self.sink.write(rows)


drop_nulls = lambda rows: [r for r in rows if r.get("amount") is not None]
to_inr = lambda rows: [{**r, "amount": round(r["amount"] * 88.5, 2)} for r in rows]

sink = MemorySink()
n = Pipeline(ListSource([{"amount": 10}, {"amount": None}, {"amount": 2.5}]), sink, [drop_nulls, to_inr]).run()
print(n, sink.data)

Modules, packages and imports

What's the difference between a module and a package?

A module is one .py file. A package is a directory of modules importable with dotted names; a regular package has __init__.py, which runs on first import. Separately, a "distribution package" is the installable artifact (a wheel on PyPI), which can contain several import packages.

What does __init__.py do, and what should go in it?

It marks a regular package and executes once when the package or any submodule is first imported. I keep it minimal: a docstring, __version__, re-exports of the public API, and __all__. No I/O, clients or heavy imports, because every importer pays for them and they cause circular imports.

Explain if __name__ == "__main__":.

__name__ is "__main__" for the file Python was started with and the module's import name otherwise. The guard runs code only when the file is executed directly, so tests and other modules can import it without side effects. It's also required for multiprocessing on spawn and forkserver start methods. I keep it to raise SystemExit(main()).

How does Python find a module when you import it?

It checks sys.modules, then built-ins, then each entry of sys.path in order: the script directory (or cwd for -m/-c), PYTHONPATH, the standard library, then site-packages. First match wins, which is why a local json.py shadows the standard library.

"attempted relative import with no known parent package": what happened?

A module using relative imports was run as a script (python pkg/mod.py), so it has no package context. Run it as python -m pkg.mod from the parent directory, or better, use an entry point and install the package.

How do you fix a circular import?

Extract the shared code into a lower-level module so dependencies are one-directional, and make sure lower layers never import higher ones. Short-term patches: import the module instead of the name, import inside the function, or use TYPE_CHECKING for annotation-only imports.

Why is importing something twice cheap?

The first import executes the module and stores the module object in sys.modules; subsequent imports anywhere return the cached object without re-executing it. That's also why module-level state is shared process-wide, and why Lambda containers reuse module-level clients.

Absolute or relative imports?

Absolute by default (PEP 8): explicit and they work from scripts and tests. Relative only for short intra-package references, mainly re-exports in __init__.py.

Packaging, uv, lock files

What is pyproject.toml? What goes in [project] vs [tool.*]?

The standard project configuration file. [project] holds metadata, requires-python, runtime dependencies as ranges, extras and scripts; [build-system] selects the build backend; [dependency-groups] holds dev-only groups; [tool.x] holds per-tool config (uv, pytest, ruff, mypy).

Extras vs dependency groups?

Extras (optional-dependencies) are user-facing optional features published in the package metadata: pip install pkg[parquet]. Dependency groups (PEP 735) are development-only (test, lint) and are never published.

What is a lock file and why commit it?

It records the fully resolved dependency graph (exact versions, sources and hashes, including transitive dependencies) so every environment installs identically. For applications we commit it, never hand-edit it, regenerate it on conflicts, and verify it in CI (uv sync --locked).

uv.lock vs poetry.lock vs requirements.txt vs pylock.toml?

A pinned requirements.txt is universally readable but describes one environment. uv.lock and poetry.lock are universal (all platforms) but tool-specific. pylock.toml is the PEP 751 standard any tool can consume; pip can write it experimentally, for the current platform only. I keep the native lock as the source of truth and export requirements.txt for Glue and MWAA.

Why did teams move from pip/Poetry to uv?

One fast tool for Python versions, venvs, locking, syncing, running, tools and builds; a universal lock; no activation needed with uv run; 10–100× faster installs, which matters with heavy data stacks in CI and Docker; and it stays on standard pyproject, so there's no lock-in.

uv sync --locked vs --frozen?

--locked asserts the lock matches pyproject and fails otherwise, which is what you want in CI. --frozen installs from the lock without checking pyproject, used in Docker layers where pyproject may not be present yet.

What's a wheel? What does cp313-manylinux_2_28_x86_64 mean?

A built distribution: installing it is just unzipping, with no build step. The tags say CPython 3.13, glibc 2.28+ Linux, x86_64. AWS needs manylinux wheels for the right Python and architecture; macOS wheels cause "invalid ELF header" on Lambda.

How do you package dependencies for Lambda when developing on a Mac?

Install for the target platform: uv pip install -r req.txt --target build --python-platform x86_64-manylinux2014 --python-version 3.13 --only-binary :all: (or aarch64 for Graviton), add the code, and zip with contents at the root. Use layers (python/ prefix) to share dependencies, and container images when you exceed 250 MB unzipped.

How do you add libraries and your own code to a Glue job?

Libraries: --additional-python-modules with pinned versions, S3 wheels, a requirements.txt on Glue 5.0+, or a gluewheels zip with --no-index for offline installs. Own code: a wheel built in CI (preferred) or a zip with __init__.py files via --extra-py-files. Glue doesn't compile native code, so ship manylinux wheels matching its Python (3.13 for 6.0, 3.11 for 5.x).

Applications vs libraries: how do they pin?

Applications lock exact versions of everything. Libraries declare compatible ranges so they can co-exist with other libraries; pinning == in a library causes resolver conflicts for its users.

What changed in Poetry 2?

It adopted the standard [project] table, moved shell and export to plugins, made poetry lock non-upgrading by default (removed --no-update), and added poetry sync. Recent versions also write standard [dependency-groups].

What is a virtual environment, technically?

A directory with a pyvenv.cfg, links to a base interpreter and its own site-packages. Python detects it because sys.prefix differs from sys.base_prefix. Activation only prepends its bin to PATH; it's optional.

Testing and mocking

What is a pytest fixture? How do scopes work?

A function providing setup (and teardown after yield) that tests request by parameter name. Scope controls reuse: function (default), class, module, session. Share only read-only or expensive objects at wide scope, for example a session-scoped local SparkSession.

Mock vs MagicMock? return_value vs side_effect?

MagicMock adds magic methods (len, iteration, context manager). return_value is what a call returns; side_effect can raise an exception, return successive values from an iterable, or call a function, which is great for retries and pagination.

Where do you patch?

Where the name is looked up by the code under test, not where it's defined. If report.py does from datetime import date, patch report.date. If it does import boto3 and calls boto3.client, patching boto3.client works because the lookup goes through the module attribute.

Why autospec?

Plain mocks accept any attribute and any arguments, so tests pass while code calls misspelled methods. autospec=True / create_autospec enforce the real signatures and attributes.

How do you test boto3 code?

Design for injection (pass the client in). For behaviour, use moto's mock_aws with fake credentials and clients created inside the mock. For exact calls and error codes, use botocore's Stubber, which validates against the API model. Keep business logic pure so most tests need neither.

patch vs monkeypatch vs mocker?

patch creates Mocks and undoes them at the end of the block or decorator. monkeypatch swaps in values you provide (great for env vars) and undoes them after the test. mocker is pytest-mock's fixture wrapping patch, auto-undone, with no nested decorators.

What makes tests flaky in data pipelines and how do you avoid it?

Shared mutable fixtures, time (date.today()), randomness, ordering of dict, set or Spark output, network calls, and leftover state in moto or tmp folders. Fix the clock by injecting it or patching, sort before comparing, use function-scoped data, and fake the network.

OOP

Explain the four pillars with a data example.

Encapsulation: a JobConfig validates workers via a property. Inheritance: S3Extractor(Extractor). Polymorphism: the pipeline calls .extract() on any extractor. Abstraction: a Loader ABC exposes load(rows) and hides Redshift details.

What is self?

The instance the method was called on, passed explicitly as the first argument: obj.m(x) is Type(obj).m(obj, x). The name is a convention.

classmethod vs staticmethod?

A classmethod receives the class (cls) and is used for alternative constructors that also work for subclasses (from_env). A staticmethod receives nothing implicit; it's a namespaced helper.

Class attribute vs instance attribute, and the mutable default bug?

Class attributes are shared by all instances; instance attributes live on each object. A list defined at class level or as a default argument is created once and shared, so appends leak across objects or Lambda invocations. Create it in __init__ or use None plus field(default_factory=list).

What is the MRO and what does super() really do?

The Method Resolution Order is the C3-linearised lookup order of a class and its bases, visible via __mro__. super() returns a proxy to the next class in the MRO of the instance's type, not the literal parent. That enables cooperative multiple inheritance and mixins.

ABC vs Protocol?

An ABC is nominal (you must inherit), enforced at instantiation, and can share code. A Protocol is structural (any object with matching methods qualifies) and is checked by type checkers. That makes it ideal for accepting third-party objects or test fakes.

__repr__ vs __str__?

__repr__ is an unambiguous developer representation (logs, REPL, containers), ideally looking like the constructor call. __str__ is a human-friendly display; it falls back to __repr__. Always implement __repr__.

Why does defining __eq__ make my objects unhashable?

Python sets __hash__ = None when you define __eq__, because equal objects must have equal hashes. Implement __hash__ over the same immutable fields, or use @dataclass(frozen=True).

When would you use a dataclass, NamedTuple or pydantic?

Dataclass for internal records and config (frozen for value objects). NamedTuple for lightweight immutable rows with tuple behaviour. Pydantic for validating untrusted external input: events, API payloads, settings.

Composition vs inheritance?

Inheritance models IS-A and couples the child to the parent's internals; composition models HAS-A with injected collaborators. I favour composition: a pipeline taking a Source, steps and a Sink avoids subclass explosions and is trivially testable with fakes. I use inheritance for small abstract contracts.

How do you implement a singleton in Python?

Usually you don't need class machinery: a module-level instance is already a singleton because modules import once, or use an @functools.cache factory like s3_client(). Avoid overriding __new__ unless there's a strong reason.

What is a context manager? Write one.

An object with __enter__/__exit__ used with with, guaranteeing cleanup even on exceptions. Example: a Timer that records start in __enter__ and logs status and duration in __exit__, returning False so exceptions propagate. Or use @contextlib.contextmanager around a try/finally with yield.

Scenario questions

A Glue job works locally but fails with ModuleNotFoundError in AWS. Walk me through it.

Confirm what was shipped: job parameters (--additional-python-modules, --extra-py-files), the S3 objects and the Glue version's Python. Common causes: a library never listed; a zip whose package folder isn't at the root or lacks __init__.py; a wheel for the wrong Python or platform; a name shadowed by a local file. Fix by building a wheel in CI from the lock and installing that same artifact.

CI passes but production installs a different pandas version. Why?

No lock file, or the deployment path re-resolves from ranges (for example Glue installing unpinned names, or a Dockerfile running pip install pandas). Generate pinned requirements or wheels from the lock and install exactly those, with --locked/--frozen or hashes.

Your test mocks boto3 but still calls real AWS. What's wrong?

Probably patched in the wrong place (the module did from boto3 import client), or the client was created at import time before the patch or moto context started. Patch where it's used, create clients lazily or inject them, and set fake credentials so accidental real calls fail fast.

How would you refactor a 1,500-line Glue script?

Add a characterisation test on a small input first. Extract pure transformations into functions and test them, isolate I/O behind small functions or classes that take clients, introduce a Config object and a thin entry script, then package it with pyproject and ship it as a wheel. Do it in small PRs, keeping the job runnable throughout.
