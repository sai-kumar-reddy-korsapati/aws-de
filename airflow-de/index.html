What orchestration actually means

A data pipeline is rarely one job. To build a daily sales table you might wait for files to land in S3, run a Glue crawler, run a Glue PySpark job, compact an Iceberg table with Athena, check row counts, load Redshift, and email the team. Each step must run in the right order, only after the previous one succeeds, retry when AWS has a hiccup, run every day at the right time, and tell someone when it breaks. An orchestrator is the software that does all of that for you. It does not process the data itself; it tells other systems (Glue, EMR, Redshift, Lambda) what to do and when.

Think of a wedding planner. The planner does not cook the food, play the music or take the photos. The planner knows that the caterer must arrive before the guests, the photographer must be there for the vows, and if the band cancels someone must call the backup band. Airflow is the wedding planner for your data jobs: Glue, EMR and Redshift are the caterer, band and photographer.

The six jobs of an orchestrator

  1. Dependencies: run B only after A succeeds; run C and D in parallel; join them before E.
  2. Scheduling: run daily at 02:00 IST, hourly, on the first business day, or when new data arrives.
  3. Retries and timeouts: AWS throttles, networks drop. Retry three times with back-off, fail after one hour.
  4. Backfills: a bug corrupted last week's data; re-run the pipeline for those seven days only.
  5. Visibility: one screen showing what ran, what failed, how long it took, and the logs.
  6. Alerting: page someone, post to Slack, or publish to SNS when something fails or runs late.

What people did before orchestrators

cron + scripts

Each job scheduled at a fixed time and "hoped" the previous one finished. No dependencies, no retries, no history, logs scattered across servers. Breaks silently.

One giant script

All steps in one Python file run by cron. A failure at step 7 means re-running steps 1–6. No parallelism.

An orchestrator

Steps are separate tasks with explicit dependencies. Failed tasks retry or re-run alone. History, logs and alerts in one place.

An orchestrator manages the order, timing, retries and visibility of the jobs in a pipeline. It does not do the heavy data processing itself; in my pipelines Airflow tells Glue, Athena and Redshift what to run and when, and those services do the compute.

  • Orchestration = dependencies + schedules + retries + backfills + visibility + alerts.
  • Airflow coordinates work; Glue/EMR/Redshift do the work.
  • Pipelines are graphs (DAGs) of tasks.

What Airflow is and where it came from

Apache Airflow is an open-source platform to author, schedule and monitor workflows as Python code. You write a Python file that describes the steps and their order (a DAG). Airflow reads the file, runs each step at the right time on workers, stores every run in a database, and shows it all in a web UI.

The core idea: workflows as code

Older schedulers (Control-M, Informatica scheduler, Oozie) defined jobs in XML or a GUI. Airflow's breakthrough was that a pipeline is a Python file. That means:

  • You can version-control it in Git, code-review it, and deploy it with CI/CD.
  • You can generate tasks in loops (one task per table, per country, per file).
  • You can test it with pytest.
  • You can use any Python library and call any API.
The smallest useful Airflow 3 DAGPython
from datetime import datetime
from airflow.sdk import dag, task


@dag(schedule="@daily", start_date=datetime(2026, 11, 1), catchup=False, tags=["demo"])
def hello_pipeline():

    @task
    def extract() -> list[int]:
        return [1, 2, 3]

    @task
    def transform(nums: list[int]) -> int:
        return sum(n * 10 for n in nums)

    @task
    def load(total: int) -> None:
        print(f"Loaded total={total}")

    load(transform(extract()))   # this line defines the order: extract >> transform >> load


hello_pipeline()

Three tasks, run once a day. The return value of extract is passed to transform automatically (through XCom, covered later), and Airflow infers the order from the function calls.

What Airflow is NOT

  • Not a data processing engine. Don't load 50 GB into a Python task. Push heavy work to Glue, EMR, Athena, Redshift or Spark and let Airflow wait for it.
  • Not a streaming system. It runs batches (even if every few minutes, or triggered by events). For sub-second latency use Kinesis, MSK/Kafka or Flink.
  • Not a data movement tool by itself. It has transfer operators, but they call S3, Redshift COPY or Glue to move data.
  • Airflow = workflows as Python code, scheduled and monitored.
  • Born at Airbnb (2014), Apache top-level (2019), 2.0 (2020), 3.0 (2025).
  • Orchestrate heavy work, don't do it inside Airflow workers.

Airflow is popular because pipelines are plain Python, it has operators for almost every system, and it gives one place to see, retry and backfill everything. Benefits and drawbacks (honest version)

Senior interviews almost always ask "what are the downsides of Airflow?" An answer with only benefits sounds junior. Know both sides, and know how each drawback is mitigated on AWS.

Benefits

  • Code-first: Git, code review, tests, CI/CD, loops to generate tasks.
  • Rich scheduling: cron, presets, timedeltas, custom timetables, assets, events, partitions.
  • Retries, timeouts, callbacks per task; backfills over any date range.
  • Visibility: Grid, Graph and Gantt views, logs per try, DAG version history.
  • Ecosystem: provider packages for AWS, dbt, Snowflake, Databricks, Slack…
  • Extensible: custom operators, hooks, sensors, timetables, plugins.
  • Open source: no lock-in; the same DAG runs locally, on MWAA, on Kubernetes.
  • Managed on AWS: MWAA handles servers, scaling, patching and IAM integration.

Drawbacks

  • Not for streaming or sub-minute latency.
  • Operational weight when self-hosted: database, scheduler, workers, upgrades.
  • Fixed cost on MWAA: a provisioned environment bills every hour even when idle.
  • Parse-time pitfalls: slow top-level code in DAG files slows the whole scheduler.
  • Python dependency conflicts between DAGs sharing one environment.
  • Not for big data movement through workers; XCom is for small values.
  • Learning curve around logical dates and data intervals.
  • Python-only DAG authoring (task SDKs for Java/Go are experimental).

On AWS I handle those by keeping compute in Glue or EMR, writing lightweight DAG files, right-sizing MWAA, and using Step Functions or MWAA Serverless for simple, purely AWS flows.

  • Always give both sides, then the mitigation.
  • Biggest real-world pains: idle cost, dependency conflicts, parse-time slowness.

Decision guide

Choose MWAA when…

  • Dozens to hundreds of pipelines need one place to monitor
  • You need backfills and catch-up across date ranges
  • Pipelines touch non-AWS systems (Snowflake, Salesforce, APIs, dbt)
  • The team wants Python and code review

Choose Step Functions when…

  • The flow is triggered by an event (S3 upload, API call)
  • All steps are AWS services or Lambdas
  • You want zero idle cost and millisecond starts
  • You need long waits for callbacks (task tokens)

Use both

  • Airflow owns the daily schedule and backfills
  • It starts a Step Functions state machine for a tightly coupled serverless sub-flow with StepFunctionStartExecutionOperator
Real-world framing

"In a typical lakehouse platform the near-real-time API ingestion ran on API Gateway + Lambda + Step Functions, because it is event-driven and serverless, while the nightly lakehouse batch — Glue jobs, Iceberg maintenance, data quality and Redshift loads — fits Airflow, because those runs are scheduled, interdependent and need backfills." Adapt this to your own projects.

Q: Why not just use Step Functions for everything?

Step Functions is excellent for event-driven AWS service chains, but it has no built-in concept of a schedule with data intervals or backfills, re-running a date range means scripting many executions, and integrating non-AWS systems needs a Lambda per call. When there are hundreds of scheduled pipelines with dependencies on each other, a shared UI, catch-up and Python-defined tasks matter more, which is what Airflow gives. I'd pick Step Functions for a few event-triggered flows and MWAA for a large scheduled batch estate.

Q: Glue Workflows already chain Glue jobs. Why add Airflow?

Glue Workflows only orchestrate Glue jobs and crawlers. As soon as you need Athena, Redshift, EMR, Lambda, a data quality check, an external API or an SNS alert with custom logic, you outgrow them. They also lack Airflow's backfill and cross-pipeline dependency features.

  • Step Functions: event-driven, serverless, AWS-native. Airflow: scheduled, cross-system, backfills.
  • They combine well; Airflow can start state machines.
  • Glue Workflows only fit pure Glue chains.

The vocabulary: DAG, task, operator, run

Ten words explain 90% of Airflow. Learn the difference between a DAG (the recipe), a DAG run (cooking the recipe on one day), a task (one step in the recipe) and a task instance (that step on that day). Mixing these up is the most common beginner mistake in interviews.

DAG
Directed Acyclic Graph. The definition of a workflow: its tasks, their order, and its schedule. "Directed" = arrows have a direction; "acyclic" = no loops (a task can't depend on itself, even indirectly).
Task
One node in the DAG, for example "run the Glue job". Defined once in code.
Operator
A template for a kind of task. GlueJobOperator knows how to start a Glue job and wait; BashOperator runs a shell command. A task is an operator with its arguments filled in.
Sensor
A special operator that waits for something: a file in S3, another DAG to finish, a time.
Hook
A reusable client for an external system (S3Hook, PostgresHook). Operators use hooks inside; you can use them directly in your own tasks.
DAG run
One execution of a DAG, e.g. "the daily_sales run for 7 Nov 2026". Has a run_id, a state, and (for scheduled runs) a data interval.
Task instance (TI)
One task inside one DAG run. Has a state (queued, running, success…), a try number and its own log.
Logical date
The point in time a run "belongs to". With Airflow 3's default cron timetable it is simply the time the run was scheduled for (a 02:00 run on 8 Nov has logical date 8 Nov 02:00). With interval-style timetables (the Airflow 2 default) it is the start of the data interval, so the run on 8 Nov processing 7 Nov has logical date 7 Nov. The Scheduling chapter explains both.
Asset
A named piece of data (an S3 prefix, a table) that tasks produce. Other DAGs can be scheduled to run when an asset is updated. Called "dataset" in Airflow 2.
Provider
A pip package that adds operators, hooks and sensors for a system, e.g. apache-airflow-providers-amazon.

A DAG is a recipe card. A task is a step on the card ("chop onions"). An operator is a kind of step ("chop", "bake"). A DAG run is cooking the recipe on Saturday. A task instance is "chopping onions on Saturday", which can succeed, fail, or be retried.

Airflow 3 architecture, component by component

Airflow is not one program. It is several cooperating services around a database. In Airflow 3 the big change is that workers no longer connect to the metadata database; they talk to the API server through the Task Execution API. This made Airflow safer (a task can't corrupt the database) and opened the door to running tasks anywhere, even in other languages.

Executors you should know

LocalExecutor
Runs tasks as processes on the scheduler machine. Good for laptops and small single-node setups. airflow standalone uses it. (SequentialExecutor was removed in 3.0.)
CeleryExecutor
Sends tasks to a message broker (Redis, RabbitMQ, SQS); a fleet of workers pulls them. Scales horizontally. MWAA uses it.
KubernetesExecutor
One pod per task. Strong isolation, per-task images and resources, slower start. Common on EKS.
AWS ECS / Batch executors
From the Amazon provider: each task runs as an ECS task or Batch job. Useful for self-managed Airflow on AWS.
EdgeExecutor
Airflow 3 feature: workers in remote locations (another network, on-prem) pull work over HTTP from the API server.
Multiple executors
Since 2.10 you can configure several executors and pick one per task with executor="KubernetesExecutor".

In Airflow 3 the DAG processor parses files and stores serialized DAGs, the scheduler creates runs and queues ready tasks through the executor, workers run them and talk only to the API server through the Task Execution API, the triggerer handles deferred async waits, and everything is recorded in the metadata database. On MWAA it's CeleryExecutor with SQS as the broker, Aurora PostgreSQL as the metadata DB, and Fargate workers that autoscale.

  • Airflow 3 components: API server, scheduler, DAG processor, triggerer, workers, metadata DB.
  • Workers no longer access the DB; they use the Task Execution API.
  • Executor = how tasks run. MWAA = Celery + SQS + Fargate.

Anatomy of a DAG file

A DAG file is ordinary Python that Airflow imports again and again (every 30 seconds or so). Everything at the top level runs on every parse, so the file should only define things: the DAG, its tasks and their order. Real work happens inside tasks, at run time.

daily_sales.py — every common DAG argumentPython
from datetime import datetime, timedelta

from airflow.sdk import DAG
from airflow.providers.standard.operators.empty import EmptyOperator
from airflow.providers.standard.operators.bash import BashOperator

default_args = {                       # applied to every task unless the task overrides it
    "owner": "data-eng",
    "retries": 3,
    "retry_delay": timedelta(minutes=5),
    "retry_exponential_backoff": True,  # 5, 10, 20 minutes...
    "max_retry_delay": timedelta(minutes=30),
    "execution_timeout": timedelta(hours=1),
    "email_on_failure": False,
}

with DAG(
    dag_id="daily_sales",                     # unique name; defaults to the function name with @dag
    description="S3 -> Glue -> Iceberg -> Redshift",
    schedule="0 2 * * *",                     # 02:00 every day (UTC unless start_date has a tz)
    start_date=datetime(2026, 11, 1),         # first logical date; a fixed date, never datetime.now()
    catchup=False,                            # don't create runs for missed past intervals (default in 3.x)
    max_active_runs=1,                        # one run at a time for this DAG
    max_active_tasks=8,                       # at most 8 tasks of this DAG running at once
    dagrun_timeout=timedelta(hours=3),        # fail the run if it takes longer
    default_args=default_args,
    tags=["sales", "lakehouse"],
    doc_md="Builds the daily sales mart. Owner: data-eng. Runbook: wiki/sales",
) as dag:
    start = EmptyOperator(task_id="start")
    transform = BashOperator(task_id="transform", bash_command="echo transforming {{ ds }}")
    end = EmptyOperator(task_id="end")

    start >> transform >> end
  1. Imports: DAG authoring classes come from airflow.sdk; core operators like Bash/Python/Empty live in the standard provider in Airflow 3.
  2. default_args: shared task settings. Retries and timeouts belong here.
  3. DAG arguments: identity, schedule, start date, concurrency limits, documentation.
  4. Tasks: operator instances with a unique task_id.
  5. Dependencies: >> means "then".

Three ways to declare a DAG

with DAG(...)

Context manager. Classic style; good with traditional operators.

@dag decorator

Wrap a function; call it at the bottom of the file. The usual choice with TaskFlow (@task).

dag = DAG(...) + dag=dag

Explicit object passed to each task. Old style; avoid in new code.

Top-level code mistakes
  • start_date=datetime.now(): the start moves on every parse, so runs may never be created. Use a fixed date.
  • rows = requests.get(api).json() at module level: runs on every parse (thousands of times a day) and slows the DAG processor.
  • Variable.get("x") at module level: hits the API server / secrets backend on every parse. Use a Jinja template {{ var.value.x }} or read it inside a task.
  • import pandas, tensorflow at the top when only one task needs them: move the import inside that task.
  • DAG files are parsed constantly; keep top-level code cheap.
  • Fixed start_date; catchup=False is the 3.x default.
  • Retries/timeouts in default_args; concurrency on the DAG.

Every task instance moves through states. Reading them correctly in the UI is how you debug: a task stuck in queued is a capacity problem, a task in up_for_retry failed but will try again, and upstream_failed means it never ran because something before it failed.

Q: Tasks sit in "queued" for 20 minutes on MWAA. What do you check?

Queued means the scheduler handed the task to Celery but no worker picked it up. On MWAA I check whether the environment is at its maximum worker count (CloudWatch metrics for running/queued tasks), whether celery.worker_autoscale limits concurrency per worker, whether long poke-mode sensors are hogging slots, and whether the task targets a queue no worker listens to. Fixes: raise max workers or the environment class, convert sensors to deferrable, spread schedules, and use pools to stop one DAG flooding the queue.

  • scheduled = waiting for a slot; queued = waiting for a worker.
  • up_for_retry ≠ failed; upstream_failed = never ran.
  • deferred = waiting in the triggerer, costs no worker slot.

Dependencies and trigger rules

Dependencies say "B runs after A". Trigger rules say under what condition B runs once its upstream tasks finish. The default is all_success: run only if every upstream task succeeded. Changing the rule is how you build cleanup tasks, "notify on any failure" tasks, and joins after branches.

Ways to set dependenciesPython
from airflow.sdk import chain, cross_downstream

a >> b >> c                 # a then b then c
a >> [b, c] >> d            # b and c in parallel after a, d after both
c << b                      # same as b >> c (rarely used)

chain(a, b, [c, d], e)      # a >> b >> [c, d] >> e
chain([a1, a2], [b1, b2])   # pairwise: a1 >> b1, a2 >> b2
cross_downstream([a1, a2], [b1, b2])   # every a before every b

  • Default rule all_success; join after branches with none_failed_min_one_success.
  • all_done for cleanup; one_failed for alerts.
  • Run state follows leaf tasks; prefer setup/teardown for cleanup.

Tasks may run on different workers, so they can't share Python variables. XCom ("cross-communication") lets a task store a small value that later tasks read. Common mistake

Returning a pandas DataFrame or a list of 100,000 dicts from a @task. It works in dev with tiny data, then breaks production with serialization errors or a bloated database. Write Parquet to S3 and return the S3 URI.

  • Pass S3 URIs, not data.
  • Object storage backend offloads big XComs to S3.

Dynamic task mapping

Sometimes you don't know how many tasks you need until run time: one task per file that arrived today, per table in a config, per page of an API. Dynamic task mapping creates N copies of a task at run time from a list. Each copy is a separate task instance with its own logs and retries, shown in the UI with a map index.

A restaurant doesn't know how many orders will come tonight. Instead of hiring a fixed number of cooks for fixed dishes, the head chef looks at the order slips at 7 pm and hands one slip to each free cook. expand() is the head chef handing out slips.

One Glue run per table, with a shared configPython

Q: A Glue job takes 50 minutes; the Airflow task retried after a worker restart and started a second Glue run. How do you prevent duplicates?

Make the task idempotent: use deferrable operators (the wait lives in the triggerer and survives worker restarts), set Glue's max concurrent runs to 1 for that job, and make the job itself idempotent (overwrite the partition or MERGE by key, never blind append). Writing custom operators and hooks

When the same Python logic appears in many DAGs, wrap it in a custom operator so teams call it with arguments. If the logic talks to an external system, put the client code in a hook so other operators can reuse it. Keep them in a shared package (or plugins//dags/common/ on MWAA) with unit tests.

dags/common/operators/iceberg_maintenance.pyPython
from airflow.sdk import BaseOperator, Context
from airflow.providers.amazon.aws.hooks.athena import AthenaHook


class IcebergMaintenanceOperator(BaseOperator):
    """Runs OPTIMIZE and VACUUM for an Iceberg table through Athena."""

    template_fields = ("table", "where")          # these accept Jinja
    ui_color = "#dff1ea"

    def __init__(self, *, table: str, database: str, workgroup: str = "primary",
                 where: str | None = None, aws_conn_id: str = "aws_default", **kwargs):
        super().__init__(**kwargs)
        self.table, self.database, self.workgroup = table, database, workgroup
        self.where, self.aws_conn_id = where, aws_conn_id

    def _run(self, hook: AthenaHook, sql: str) -> str:
        qid = hook.run_query(query=sql, query_context={"Database": self.database},
                             result_configuration={}, workgroup=self.workgroup)
        state = hook.poll_query_status(qid, sleep_time=10)
        if state != "SUCCEEDED":
            raise RuntimeError(f"{sql} ended {state}: {hook.get_state_change_reason(qid)}")
        return qid

    def execute(self, context: Context) -> dict:
        hook = AthenaHook(aws_conn_id=self.aws_conn_id)
        where = f" WHERE {self.where}" if self.where else ""
        opt = self._run(hook, f"OPTIMIZE {self.table} REWRITE DATA USING BIN_PACK{where}")
        vac = self._run(hook, f"VACUUM {self.table}")
        self.log.info("Maintenance done for %s", self.table)
        return {"optimize_qid": opt, "vacuum_qid": vac}

Deferrable operators and the triggerer

Most AWS tasks spend 99% of their time waiting: for a Glue job, an EMR step, an Athena query. A normal operator holds a worker slot while it waits. A deferrable operator starts the job, then hands the waiting to the triggerer, a service that can watch thousands of jobs at once using Python asyncio. The worker slot is freed and the task resumes on a worker only when the job finishes.

Turning it onPython

AthenaOperator(task_id="q", query="...", database="lake", output_location="s3://r/", deferrable=True)

                              job_driver={...}, deferrable=True)
S3KeySensor(task_id="s", bucket_key="s3://b/k/_SUCCESS", deferrable=True)

# or make it the default for every operator that supports it:
# AIRFLOW__OPERATORS__DEFAULT_DEFERRABLE=True   (MWAA config option operators.default_deferrable)
Q: Why do deferrable operators save money on MWAA?

MWAA bills for workers, and each worker runs a fixed number of tasks at once. If 100 tasks are each waiting 30 minutes for Glue in poke mode, they occupy 100 slots and force MWAA to scale out workers that do nothing but sleep. Deferred, those 100 waits cost almost nothing in the triggerer, so the environment can run on fewer workers or a smaller class.

  • Deferrable = start, hand off the wait, resume later.
  • Triggerer runs async triggers; task state is "deferred".
  • operators.default_deferrable=True is a strong default on MWAA.

Daylight saving

With a DST zone such as America/New_York, cron schedules follow local wall-clock time (a 02:00 job may run twice or be skipped on change days for times inside the jump hour). Avoid schedules between 01:00 and 03:00 in DST zones, or schedule in UTC.

  • schedule=None is the 3.x default; always set it explicitly.
  • Cron is evaluated in the DAG's time zone; use pendulum tz-aware start dates.
  • @continuous for back-to-back runs; assets for data-driven runs.

Logical date, data intervals and run_after

This is the most misunderstood part of Airflow and a favourite interview topic. Every scheduled run has a run_after (the earliest time it may start) and a logical date (the point in time it represents). How these relate depends on the timetable. Airflow 2 used interval semantics by default: the run for "7 Nov" starts after 7 Nov ends. Airflow 3 uses trigger semantics by default: the run at 02:00 on 8 Nov is the 8 Nov 02:00 run.

Choosing explicitly

Make the semantics obvious in codePython
import pendulum
from airflow.sdk import dag
from airflow.timetables.trigger import CronTriggerTimetable
from airflow.timetables.interval import CronDataIntervalTimetable

# "Run at 02:00 and process yesterday's partition" — trigger semantics, explicit offset
@dag(schedule=CronTriggerTimetable("0 2 * * *", timezone="UTC"),
     start_date=pendulum.datetime(2026, 11, 1, tz="UTC"), catchup=False)
def sales_trigger_style():
    ...  # use {{ macros.ds_add(ds, -1) }} for the partition

# "Each run owns the interval since the last run" — Airflow 2 semantics
@dag(schedule=CronDataIntervalTimetable("0 2 * * *", timezone="UTC"),
     start_date=pendulum.datetime(2026, 11, 1, tz="UTC"), catchup=False)
def sales_interval_style():
    ...  # use {{ data_interval_start }} .. {{ data_interval_end }} for the window

To make all cron strings behave like Airflow 2 (useful during a migration), set [scheduler] create_cron_data_intervals = True. For timedelta schedules the equivalent switch is create_delta_data_intervals.

Which one should I use?

Trigger semantics

"Run at this time." Easy to explain to the business; logical date = the time the run is for. Good for reports, exports and jobs where the window is computed from the run date. Default in 3.x.

Interval semantics

"This run owns this time window." Best for incremental loads that read exactly [start, end), e.g. an hourly CDC pull WHERE updated_at >= start AND updated_at < end. Backfills then naturally process each window once.

Incremental extract by window (interval semantics)SQL template
SELECT *
FROM sales.orders
WHERE updated_at >= TIMESTAMP '{{ data_interval_start.strftime("%Y-%m-%d %H:%M:%S") }}'
  AND updated_at <  TIMESTAMP '{{ data_interval_end.strftime("%Y-%m-%d %H:%M:%S") }}'
Q: My DAG is scheduled daily at midnight. Why does the run on 8 Nov have {{ ds }} = 2026-11-07?

Because the DAG uses interval semantics (either Airflow 2, or CronDataIntervalTimetable / create_cron_data_intervals=True in Airflow 3). The run that starts on 8 Nov covers the 7 Nov interval and its logical date is the interval start. With Airflow 3's default CronTriggerTimetable, the same run would have ds = 2026-11-08. I always make the timetable explicit in important DAGs so nobody has to guess.

  • run_after = when it may start; logical_date = what it represents.
  • 3.x default CronTriggerTimetable: logical date = trigger time; zero-width interval.
  • CronDataIntervalTimetable: logical date = interval start; ideal for windowed incremental loads.

A custom timetable: weekdays except a holiday list

plugins/business_day_timetable.pyPython
from datetime import timedelta
from pendulum import DateTime, Time, timezone
from airflow.plugins_manager import AirflowPlugin
from airflow.timetables.base import DagRunInfo, DataInterval, Timetable

HOLIDAYS = {"2026-11-09", "2026-12-25", "2027-01-26"}
UTC = timezone("UTC")


class BusinessDayTimetable(Timetable):
    """Runs at 01:00 UTC on weekdays that are not company holidays."""

    def _is_business_day(self, d: DateTime) -> bool:
        return d.weekday() < 5 and d.to_date_string() not in HOLIDAYS

    def infer_manual_data_interval(self, *, run_after: DateTime) -> DataInterval:
        return DataInterval.exact(run_after)

    def next_dagrun_info(self, *, last_automated_data_interval, restriction) -> DagRunInfo | None:
        if last_automated_data_interval is not None:
            day = last_automated_data_interval.end.add(days=1)
        else:
            if restriction.earliest is None:
                return None
            day = restriction.earliest
        day = DateTime.combine(day.date(), Time(1, 0)).replace(tzinfo=UTC)
        while not self._is_business_day(day):
            day = day + timedelta(days=1)
        if restriction.latest is not None and day > restriction.latest:
            return None
        return DagRunInfo.exact(day)


class BusinessDayPlugin(AirflowPlugin):
    name = "business_day_timetable"
    timetables = [BusinessDayTimetable]

Custom timetables must be registered through a plugin because the scheduler deserializes them by class path. On MWAA put this file in plugins.zip; DAGs then use schedule=BusinessDayTimetable().

  • Every schedule is a timetable; use one directly for multi-cron, events, or business rules.
  • Custom timetables need a plugin registration (plugins.zip on MWAA).

Catchup, backfills, clearing and reruns

Catchup decides what happens when a DAG is turned on with a start date in the past (or after being paused): create a run for every missed schedule (catchup=True) or only the latest (catchup=False, default in 3.x). A backfill is a deliberate, one-off re-run over a date range, for example after fixing a bug. Clearing resets task instances so they run again.

Catchup behaviourPython
@dag(schedule="@daily", start_date=datetime(2026, 10, 1), catchup=True, max_active_runs=3)
def history_builder(): ...
# Unpaused on 8 Nov: Airflow creates runs for 1 Oct ... 7/8 Nov, at most 3 at a time.
# With catchup=False it creates only the most recent run.

Backfills in Airflow 3: run by the scheduler

In Airflow 2 a backfill was a CLI process that died if your terminal closed. In 3.x a backfill is an object the scheduler runs, so you start it from the UI ("Trigger" → backfill), the REST API or the CLI, watch it in the Grid, and cancel it.

  • Limit concurrency with --max-active-runs and pools so a 90-day backfill doesn't starve daily production.
  • Backfill in a quiet window, or on a separate MWAA environment for very large reprocessing.
Q: You found a bug that corrupted the last 30 days of a fact table. Walk me through the fix.

Fix and deploy the code; confirm tasks are idempotent (partition overwrite or MERGE). Pause downstream consumer DAGs or communicate the window. Create a backfill for the 30 days with reprocess-behavior=completed, max_active_runs 2–4 and a pool so production keeps its capacity. Validate counts and checksums per partition against the source. Then re-trigger downstream assets (or let asset events trigger them) and tell consumers when data is corrected.

  • catchup=False default; catchup=True creates all missed runs.
  • 3.x backfills are scheduler-managed: UI/API/CLI, cancellable, reprocess behaviour.
  • Idempotent tasks are the prerequisite for any rerun or backfill.

Assets: data-aware scheduling

Instead of guessing "the upstream DAG usually finishes by 03:00, so run at 04:00", let the upstream DAG announce that it updated some data, and start the downstream DAG when that happens. The data is called an asset (a name and URI such as s3://lake/orders). A task that updates it lists it in outlets; a DAG that depends on it uses schedule=[asset].

Producer and consumerPython

Batching vs one run per event

Up to 3.3, if an asset is updated three times before the consumer runs, the consumer runs once with all three events. Airflow 3.4+ changes single-asset and OR schedules to create one run per event by default (batch_asset_events=True restores batching). Know your version when you design consumers.

Important

Airflow does not look at S3. An asset event is emitted when an Airflow task with that outlet succeeds (or via the REST API). If another system writes the data, publish the event yourself (REST API POST /api/v2/assets/events) or use an asset watcher on a queue (next lesson).

Assets let me chain pipelines on data rather than time. The producing task declares the asset as an outlet; when it succeeds Airflow records an asset event; consumer DAGs scheduled on that asset, or a condition like orders and customers, start automatically. It removes fragile buffer times and cross-DAG sensors, and the UI shows lineage between DAGs.

  • outlets=[asset] on producers, schedule=[asset] or conditions on consumers.
  • &, |, and AssetOrTimeSchedule for complex rules.
  • Airflow emits events on task success; it doesn't watch storage itself.

Event-driven scheduling with SQS and asset watchers

When data arrives from outside Airflow (a vendor drops a file in S3, an app publishes an event), you used to run a sensor every few minutes. Airflow 3 can instead listen to a message queue: an AssetWatcher runs a trigger in the triggerer that waits for messages on Amazon SQS (or Kafka). Each message creates an asset event, which starts the DAG within seconds, with no polling sensor holding a worker.

dags/vendor_file_arrival.pyPython
import json
from airflow.sdk import DAG, Asset, AssetWatcher, task
from airflow.providers.common.messaging.triggers.msg_queue import MessageQueueTrigger

trigger = MessageQueueTrigger(
    scheme="sqs",
    sqs_queue="https://sqs.us-east-1.amazonaws.com/123456789012/vendor-file-events",
)
vendor_files = Asset("vendor_file_events", watchers=[AssetWatcher(name="vendor_sqs", trigger=trigger)])

with DAG(dag_id="process_vendor_file", schedule=[vendor_files]) as dag:

    @task
    def parse_event(**context) -> dict:
        evs = context["triggering_asset_events"][vendor_files]
        body = evs[-1].extra["payload"]                       # message from the trigger
        detail = json.loads(body["Body"])["detail"] if isinstance(body, dict) and "Body" in body else body
        return {"bucket": detail["bucket"]["name"], "key": detail["object"]["key"]}

    @task
    def process(obj: dict):
        print(f"Processing s3://{obj['bucket']}/{obj['key']}")

    process(parse_event())

Inspect one real event in the task log first; the exact payload shape depends on the provider version and on whether EventBridge or S3 notifications feed the queue. Install apache-airflow-providers-common-messaging and apache-airflow-providers-amazon.

AWS side (Terraform-style summary)

  1. Enable EventBridge notifications on the bucket.
  2. EventBridge rule: source aws.s3, detail-type Object Created, prefix filter incoming/vendor/ → target SQS queue.
  3. SQS queue policy allowing events.amazonaws.com; a dead-letter queue.
  4. MWAA execution role: sqs:ReceiveMessage, sqs:DeleteMessage, sqs:GetQueueAttributes on the queue.

  • Arrival time is unpredictable
  • You want minutes-to-seconds latency
  • Many files arrive over the day

Stay with schedules when…

  • Data lands at a known time
  • A downstream SLA is daily anyway
  • You need strict one-run-per-day partitions (or use partitions)

  • S3 → EventBridge → SQS → triggerer → DAG run.

Asset partitions 3.2+

Plain assets say "orders changed". In a data lake you care which partition changed: dt=2026-11-07, or hour 14:00. With asset partitions, producers record a partition key on each event, and consumers run once per matching partition. A daily rollup can even wait until all 24 hourly partitions of a day have arrived.

Deadline alerts (the SLA replacement) 3.1+

Airflow 2's SLAs were unreliable and were removed in 3.0. Deadline Alerts replace them: you declare "this DAG run must finish within X of some reference time", and Airflow calls your callback (Slack, SNS, PagerDuty…) the moment the deadline passes, even while the run is still going.

Alert if the run isn't done 45 minutes after it was queued, and if it's much slower than usualPython
from datetime import datetime, timedelta
from airflow.sdk import DAG, AsyncCallback, DeadlineAlert, DeadlineReference
from airflow.providers.amazon.aws.notifications.sns import SnsNotifier
from airflow.providers.standard.operators.empty import EmptyOperator

with DAG(
    dag_id="finance_close",
    schedule="0 3 * * *",
    start_date=datetime(2026, 11, 1),
    catchup=False,
    deadline=[
        DeadlineAlert(
            reference=DeadlineReference.DAGRUN_QUEUED_AT,
            interval=timedelta(minutes=45),
            callback=AsyncCallback(SnsNotifier, kwargs={
                "target_arn": "arn:aws:sns:us-east-1:123456789012:data-alerts",
                "message": "{{ dag_run.dag_id }} missed its 45-minute deadline",
            }),
        ),
        DeadlineAlert(
            reference=DeadlineReference.AVERAGE_RUNTIME(max_runs=15, min_runs=5),
            interval=timedelta(minutes=30),     # 30 min slower than the recent average
            callback=AsyncCallback(SnsNotifier, kwargs={
                "target_arn": "arn:aws:sns:us-east-1:123456789012:data-alerts",
                "message": "{{ dag_run.dag_id }} is running far slower than usual",
            }),
        ),
    ],
):
    EmptyOperator(task_id="close_books")

References include DAGRUN_QUEUED_AT, DAGRUN_LOGICAL_DATE, FIXED_DATETIME(...) and AVERAGE_RUNTIME(...). AsyncCallback runs in the triggerer; SyncCallback 3.2+ runs on a worker. The feature is marked experimental, so pin your Airflow version and test.

  • SLAs are gone in 3.x; use DeadlineAlert on the DAG.
  • Reference + interval + callback; several alerts per DAG.
  • Fires while the run is still in progress.

Testing DAGs: unit, integrity and CI

Three layers of tests catch almost everything before production: DAG integrity tests (every file imports, no cycles, required tags and retries present), unit tests of task logic, and an end-to-end run of the DAG in a dev environment with dag.test(). Run the first two in CI on every pull request.

import pytest

try:
    from airflow.dag_processing.dagbag import DagBag      # newer 3.x location
except ImportError:
    from airflow.models import DagBag


@pytest.fixture(scope="session")
def dagbag():

def test_no_import_errors(dagbag):

def test_every_dag_has_owner_tags_retries(dagbag):

Athena gotchas in Airflow
  • One statement per AthenaOperator; Athena doesn't run multi-statement scripts.
  • Results go to S3; set a lifecycle rule on the results prefix or it grows forever.
  • Concurrent DML on the same Iceberg table can conflict: chain MERGE → OPTIMIZE → VACUUM, or use a pool of size 1 per table.
  • Use workgroups with query limits to cap cost of runaway SQL.
  • AthenaOperator per statement; .sql files are templated.
  • Iceberg pattern: MERGE → OPTIMIZE (bin-pack recent partitions) → VACUUM.
  • Common-sql check operators turn SQL into data-quality gates.

What MWAA manages, and its architecture

Amazon Managed Workflows for Apache Airflow (MWAA) runs open-source Airflow for you. You give it an S3 bucket with your DAGs, a VPC, and an IAM role; AWS runs the schedulers, workers, web/API server and metadata database, scales workers, patches the platform, and plugs it into IAM, CloudWatch and KMS. The DAG code is the same Airflow you run locally.

AWS manages

  • Airflow installation and patching
  • Schedulers (2–5), DAG processing, triggerer
  • Celery workers on Fargate + autoscaling
  • Web/API server with IAM sign-in
  • Metadata DB (Aurora PostgreSQL), backups
  • SQS Celery queue, encryption, log shipping

You manage

  • DAG code, requirements.txt, plugins, startup script (in S3)
  • VPC, subnets, security groups, endpoints
  • Execution role permissions
  • Environment class, worker min/max, config options
  • Version upgrades, cost, monitoring/alarms

Key facts

  • Executor: CeleryExecutor with SQS as broker; metadata DB: Aurora PostgreSQL (no direct access).
  • Code comes from S3: dags/, requirements.txt, plugins.zip, startup.sh.
  • Auth: IAM. Users get a web login token mapped to an Airflow role (Admin, Op, User, Viewer, Public).
  • Logs to CloudWatch Logs; metrics to CloudWatch; encryption with an AWS-owned or customer-managed KMS key.
  • Two flavours: provisioned environments (this chapter) and MWAA Serverless (next chapter).

MWAA is AWS's managed Airflow. We keep DAGs, requirements and plugins in S3; MWAA runs CeleryExecutor workers and schedulers as Fargate containers inside our VPC, with an AWS-managed Aurora metadata database and SQS broker. Access is through IAM, logs and metrics go to CloudWatch, and secrets come from Secrets Manager. We own the DAG code, networking, execution role permissions, sizing and upgrades.

  • MWAA = Celery + SQS + Aurora + Fargate, code from S3, auth via IAM.
  • Containers run in your private subnets; DB/queue in AWS's VPC.

Q: The environment is stuck in CREATING and then fails. What do you check?

Almost always networking or permissions: subnets must be private with a route to AWS services (NAT or the required endpoints); the security group needs a self-referencing inbound rule; the execution role must have the base MWAA permissions and KMS access if a CMK is used; and the S3 bucket must be versioned with public access blocked. CloudTrail and the environment's error message point to which.

  • UI: public (IAM-protected) or private (VPN/proxy).
  • Containers: NAT, or VPC endpoints for S3, SQS, Logs, Monitoring, KMS, ECR, airflow.*, plus your services.

Sizing and scaling an environment

An environment class sets the size of the scheduler, web server and each worker, and a default number of concurrent tasks per worker. Workers autoscale between your min and max based on queued and running tasks. Right-sizing means enough capacity for the peak hour without paying for idle workers all day.

ClassRough DAG capacity*Default tasks per worker*Use
mw1.micro~253Dev, sandboxes, tiny workloads
mw1.small~505Dev/test, small teams
mw1.medium~25010Typical production
mw1.large~1,00020Large platforms
mw1.xlarge~2,00040Very large
mw1.2xlarge~4,00080Largest

*Approximate AWS guidance; real capacity depends on parse time and task weight. Confirm current numbers in the MWAA environment class docs.

How worker autoscaling works

  1. MWAA watches queued + running task counts.
  2. If demand exceeds current capacity (workers × tasks per worker), it adds workers up to max-workers (max 25).
  3. When load drops for a while, it removes workers down to min-workers.
  4. Scale-out takes minutes, so very bursty schedules (500 tasks at 02:00) briefly queue. Smooth them by staggering cron times or raising min workers in that window.

Right-sizing checklist

  • Schedulers: start with 2; add more if scheduling lag grows with many DAGs.
  • Class: driven by scheduler/parsing load and per-task memory. Memory-heavy tasks → bigger class or lower celery.worker_autoscale.
  • Workers: driven by concurrent task count at peak. Deferrable operators shrink this a lot.
  • Watch: queue age, running vs capacity, CPU/memory per component.
Q: How would you size MWAA for 300 DAGs, peak 400 concurrent tasks, mostly Glue/Athena waits?

Most tasks are waits, so I'd make all AWS operators deferrable; then actual worker concurrency at peak might be a few dozen. 300 DAGs fits mw1.medium or mw1.large depending on parse time; I'd start with medium, 2 schedulers, min 2 / max 10 workers, then watch scheduler CPU, parse time and queue age during the peak window, and stagger schedules. If scheduler CPU is saturated, move to large before adding workers.

  • Class = component size + tasks per worker; workers autoscale min..max (≤25).
  • Deferrable operators and staggered schedules reduce required capacity.
  • Scale schedulers/class for parsing load, workers for concurrency.

MWAA cost: model and optimization

Provisioned MWAA bills per hour for the environment (its class includes a scheduler, a web server and a base worker), plus additional workers, additional schedulers/web servers beyond the included ones, and metadata storage. It bills whether or not DAGs are running, so idle time costs money.

Component (us-east-1 examples from the AWS pricing page)Price
mw1.small environment$0.49 / hour (≈ $358 / month)
mw1.large environment$0.99 / hour (≈ $723 / month)
Additional worker$0.055 / hour (small) … $0.22 / hour (large)
Metadata database storage$0.10 / GB-month
MWAA ServerlessPer task execution time, one-second billing with a one-minute minimum per task

Prices change and vary by region; check the MWAA pricing page or the AWS Pricing Calculator before quoting numbers. CloudWatch Logs ingestion is billed separately and can be significant at DEBUG/INFO levels.

Optimization levers

  1. Right-size the class; don't run mw1.large for 40 DAGs.
  2. Min workers = 1 (or 2 for prod resilience); let autoscaling handle peaks.
  3. Deferrable operators so waiting tasks don't scale workers.
  4. Consolidate environments: one shared prod environment instead of one per team (with pools, tags and access controls), or use MWAA Serverless for small/spiky teams.
  5. Lower log levels for scheduler/worker/web logs; set CloudWatch retention (e.g. 30 days).
  6. Delete dev/test environments outside working hours with IaC, or move them to MWAA Serverless / local Docker.
  7. Clean the metadata DB (old runs, XComs) periodically with airflow db clean, using the method AWS documents for your MWAA version (in Airflow 3, tasks no longer have direct database access, so an ordinary task can't run it).
  • Hourly environment + extra workers + storage + logs.
  • Biggest savings: right class, min workers, deferrable, consolidation, log levels.

Upgrades, maintenance and limits

  • Minor upgrades in place (e.g. 3.2.1 → 3.3.1) via update-environment --airflow-version 3.3.1. MWAA validates and rolls back if the upgrade fails. Minor downgrades to a supported version are also allowed.
  • Major upgrades (2.x → 3.x) need a new environment (Migration lesson).
  • Weekly maintenance window: AWS applies patches and may restart components; choose a quiet time and avoid starting critical runs then.
  • Version support: each version ≥ 12 months; end-of-support announced 180 days ahead via Health Dashboard; on EOS you can't create new environments on that version.
  • Limits to remember: max 25 workers and 5 schedulers per environment; environments per account/region are quota-limited (raise via Service Quotas); multi-team mode is not supported on MWAA.

MWAA Serverless: what it is and when to use it

MWAA Serverless (launched November 2025) runs Airflow workflows without an environment. You register a workflow written in YAML; each task runs in its own short-lived ECS Fargate container, reports back through Airflow 3's Task API, and you pay only for the seconds tasks actually run. There are no workers to size and nothing billed while idle.

ScalingWorkers min..maxAutomatic, per task
IsolationShared workers and Python environmentEach task its own container; each workflow its own IAM role
UIFull Airflow UINo Airflow UI; monitor via CLI/API, CloudWatch, EventBridge events

Pick Serverless when…

  • Workflows mainly call Glue, Athena, EMR, Lambda, Redshift, SageMaker
  • They run a few times a day; an environment would sit idle
  • Teams want isolated permissions per workflow

Stay provisioned when…

  • You rely on non-AWS providers (Snowflake, dbt Cloud, Slack, Databricks…)
  • Heavy use of TaskFlow, dynamic Python, custom plugins/timetables
  • Operators need the Airflow UI for triage, clearing and backfills

MWAA Serverless removes the environment entirely: workflows are YAML in DAG Factory format, every task runs in its own Fargate container with a per-workflow IAM role, and billing is per task-second, so idle time costs nothing. It suits AWS-centric, infrequent or spiky workflows. For large estates with custom providers, complex Python and heavy UI use, provisioned MWAA is still the better fit.

  • Serverless = YAML workflows, Fargate per task, pay per task-second, no UI.
  • Amazon operators + Python/Bash bundles; per-workflow IAM role.
  • Great for AWS-only, infrequent workflows; provisioned for big, custom estates.

MERGE INTO gold.orders_daily t
USING (
  SELECT order_date, store_id, channel,
         COUNT(*)            AS orders,
         SUM(amount)         AS revenue,
         COUNT(DISTINCT customer_id) AS customers
  FROM silver.orders
  WHERE order_date = DATE '{{ macros.ds_add(ds, -1) }}'
    AND status <> 'CANCELLED'
    AND amount > {{ params.min_amount }}
  GROUP BY order_date, store_id, channel
) s
ON t.order_date = s.order_date AND t.store_id = s.store_id AND t.channel = s.channel
WHEN MATCHED THEN UPDATE SET orders = s.orders, revenue = s.revenue, customers = s.customers
WHEN NOT MATCHED THEN INSERT (order_date, store_id, channel, orders, revenue, customers)
  VALUES (s.order_date, s.store_id, s.channel, s.orders, s.revenue, s.customers)

DecisionWhy
_SUCCESS marker + deferrable sensorNever read a half-written partition; waiting costs no worker slot
MERGE by order_id in Glue, MERGE in goldIdempotent: re-runs and backfills give the same result; late updates handled
DQ gate emits the silver assetDownstream teams only trigger on validated data
max_active_runs=1Iceberg commits on the same table don't conflict across runs
Pool glue_jobsCaps concurrent Glue runs across all DAGs (DPU budget / account limits)

Q: The OMS file for 7 Nov arrived at 09:00 instead of 00:30. What happens?

The sensor waits up to 4 hours (until ~04:30) and then fails; the failure callback alerts on-call. Once the file lands, someone clears wait_for_landing for that run (or the run is re-triggered) and the rest proceeds; because every step is idempotent, nothing is duplicated. If late files are common, I'd switch the trigger to an SQS asset watcher on the _SUCCESS object so the pipeline starts whenever the file arrives, and keep a deadline alert for the 06:00 commitment.

  • Marker → Glue MERGE → DQ gate (asset) → gold MERGE → maintenance → notify.
  • Idempotency, pools, max_active_runs=1 and deferrable waits make it production-grade.

import pendulum

from common.defaults import STANDARD

QUEUE = "https://sqs.us-east-1.amazonaws.com/123456789012/vendor-price-files"
vendor_events = Asset("vendor_price_file_events",
                      watchers=[AssetWatcher(name="vendor_sqs",
                                             trigger=MessageQueueTrigger(scheme="sqs", sqs_queue=QUEUE))])

with DAG(
    dag_id="vendor_price_files",
    schedule=[vendor_events],
    start_date=pendulum.datetime(2026, 11, 1, tz="UTC"),
    max_active_runs=3,
    default_args=STANDARD,
    tags=["ingestion", "vendor", "event-driven"],
) as dag:

    @task
    def files_from_events(**context) -> list[str]:
        keys = []
        for ev in context["triggering_asset_events"][vendor_events]:
            payload = ev.extra.get("payload", {})
            body = json.loads(payload["Body"]) if isinstance(payload, dict) and "Body" in payload else payload
            obj = body["detail"]["object"]["key"] if "detail" in body else body["Records"][0]["s3"]["object"]["key"]
            keys.append(obj)
        print("files:", keys)
        return sorted(set(keys))

    @task(max_active_tis_per_dagrun=10)
    def validate(key: str) -> dict:
        s3 = S3Hook()
        head = s3.head_object(key=key, bucket_name="acme-vendor-drop")
        ok = key.endswith(".csv") and head["ContentLength"] > 0
        return {"key": key, "ok": ok, "size": head["ContentLength"]}

    @task
    def split(results: list[dict]) -> dict:
        good = [r["key"] for r in results if r["ok"]]
        bad = [r["key"] for r in results if not r["ok"]]
        return {"good": good, "bad": bad}

    @task
    def quarantine(parts: dict):
        s3 = S3Hook()
        for key in parts["bad"]:
            s3.copy_object(source_bucket_key=key, dest_bucket_key=f"quarantine/{key}",
                           source_bucket_name="acme-vendor-drop", dest_bucket_name="acme-vendor-drop")
            s3.delete_objects(bucket="acme-vendor-drop", keys=[key])
        if parts["bad"]:
            raise ValueError(f"Quarantined {len(parts['bad'])} bad files: {parts['bad']}")  # alerts via callback

    @task.short_circuit
    def any_good(parts: dict) -> bool:
        return bool(parts["good"])

    @task
    def spark_args(parts: dict) -> list[str]:
        return ["--files", ",".join(f"s3://acme-vendor-drop/{k}" for k in parts["good"]),
                "--target", "glue_catalog.silver.vendor_prices"]

    keys = files_from_events()
    parts = split(validate.expand(key=keys))
    quarantine(parts)

    merge = EmrServerlessStartJobOperator(
        task_id="merge_prices",
        application_id="{{ var.value.emr_serverless_app_id }}",
        execution_role_arn="arn:aws:iam::123456789012:role/emr-serverless-job-role",
        name="vendor-prices-{{ run_id | replace(':', '-') | truncate(40, True, '') }}",
        job_driver={"sparkSubmit": {
            "entryPoint": "s3://acme-code/spark/merge_vendor_prices.py",
            "entryPointArguments": spark_args(parts),
            "sparkSubmitParameters": "--conf spark.executor.cores=2 --conf spark.executor.memory=8g",
        }},
        configuration_overrides={"monitoringConfiguration": {
            "s3MonitoringConfiguration": {"logUri": "s3://acme-logs/emr-serverless/vendor/"}}},
        deferrable=True,
        outlets=[VENDOR_PRICES],
    )
    any_good(parts) >> merge

What makes this robust

  • SQS buffering: if Airflow is down, events wait in the queue (and a DLQ catches poison messages).
  • Mapped validation with a cap of 10 concurrent checks.
  • Partial success: good files are merged even if some are quarantined; bad files still alert.
  • Idempotent Spark merge keyed by vendor + SKU + effective date, so a replayed event does no harm.
  • max_active_runs=3 lets bursts process in parallel, while Iceberg's optimistic concurrency plus retries handles commit conflicts.
  • SQS watcher → mapped validation → split good/bad → EMR Serverless merge.
  • Quarantine instead of failing everything; alert on bad files.

Business need: pull accounts, contacts and opportunities from a SaaS CRM API every hour, only records changed in that hour, without exceeding the vendor's rate limit (e.g. 10 concurrent requests), and land raw JSON in S3 partitioned by hour for downstream Glue jobs.

import json
from datetime import timedelta
import pendulum
from airflow.sdk import dag, task
from airflow.timetables.interval import CronDataIntervalTimetable
from airflow.providers.amazon.aws.hooks.s3 import S3Hook

from common.assets import CRM_RAW
from common.defaults import STANDARD

ENDPOINTS = ["accounts", "contacts", "opportunities"]


@dag(
    schedule=CronDataIntervalTimetable("5 * * * *", timezone="UTC"),   # each run owns one hour
    start_date=pendulum.datetime(2026, 11, 1, tz="UTC"),
    catchup=True,                       # missed hours are filled automatically
    max_active_runs=2,
    default_args={**STANDARD, "retries": 4, "retry_delay": timedelta(minutes=2)},
    tags=["ingestion", "crm", "api", "backfillable"],
)
def crm_api_ingest():

    @task(pool="crm_api", max_active_tis_per_dagrun=3, outlets=[CRM_RAW])
    def pull(endpoint: str, data_interval_start=None, data_interval_end=None) -> dict:
        from common.hooks.crm import CrmApiHook          # custom hook (Writing DAGs chapter)
        hook, s3 = CrmApiHook("crm_default"), S3Hook()
        start, end = data_interval_start.isoformat(), data_interval_end.isoformat()
        cursor, page, total = None, 0, 0
        prefix = f"crm/{endpoint}/dt={data_interval_start:%Y-%m-%d}/hour={data_interval_start:%H}"
        old = s3.list_keys("acme-lake-bronze", prefix=prefix) or []
        if old:                                                      # idempotent re-runs
            s3.delete_objects(bucket="acme-lake-bronze", keys=old)
        while True:
            body = hook.get_page(f"v2/{endpoint}?updated_since={start}&updated_before={end}", cursor)
            rows = body["data"]
            if rows:
                s3.load_string("\n".join(json.dumps(r) for r in rows),
                               key=f"{prefix}/page-{page:05d}.jsonl", bucket_name="acme-lake-bronze",
                               replace=True)
                total += len(rows); page += 1
            cursor = body.get("next_cursor")
            if not cursor:
                break
        return {"endpoint": endpoint, "rows": total, "pages": page}

    @task
    def audit(results: list[dict], data_interval_start=None):
        for r in results:
            print(f"{data_interval_start:%Y-%m-%d %H}:00 {r['endpoint']}: {r['rows']} rows in {r['pages']} pages")

    audit(pull.expand(endpoint=ENDPOINTS))

DAG best practices that seniors are judged on

Anyone can make a DAG that runs once. Senior engineers write DAGs that can be re-run safely, backfilled, debugged at 3 a.m. by someone else, and that don't slow down the platform for everyone. These principles come up in every design discussion and code review.

The ten rules

  1. Idempotent tasks. Running a task twice for the same run gives the same result: overwrite a partition, MERGE by key, delete-then-insert. Never blind INSERT/append.
  2. Deterministic inputs. A task's inputs come from its run (logical date, data interval, params), never from "now". datetime.now() inside a task breaks backfills.
  3. Atomic outputs. Write to a temp location/branch and swap (Iceberg commit, rename, view swap) so readers never see half-written data.
  4. Orchestrate, don't compute. Heavy work goes to Glue/EMR/Athena/Redshift/ECS. Workers stay small and cheap.
  5. Cheap top-level code. No network calls, DB queries or heavy imports at module level; DAG files parse in well under a second.
  6. Small, meaningful tasks. One retryable unit of work per task: "run Glue job", not "do everything". But not 5,000 micro-tasks either.
  7. Pass references, not data through XCom.
  8. Explicit schedules and timetables; fixed, tz-aware start_date; catchup chosen deliberately.
  9. Ownership and docs: owner, tags, doc_md with runbook link, alert routing.
  10. Everything in Git, deployed by CI, tested with integrity and unit tests.

Performance tuning: parsing, scheduling, workers

When an Airflow platform feels slow, the cause is almost always one of three: DAG files take too long to parse, the scheduler is short of capacity or blocked by concurrency limits, or workers are full. Measure first, then tune.

1. Parsing

  • Check parse time per file: airflow dags report (locally) or the DAGProcessing logs / total parse time metric on MWAA.
  • Target well under 1 s per file. Move imports into tasks, remove top-level I/O, split giant generated files.
  • .airflowignore to skip non-DAG folders (sql/, config/, tests/).
  • Intervals: [dag_processor] refresh_interval (how often to look for new files) and min_file_process_interval (how often to re-parse a file). Raising them reduces load at the cost of slower pickup of changes.

  • Tasks "queued" with max workers reached → raise max-workers or class; convert waits to deferrable.
  • Workers OOM (SIGKILL, exit -9) → task does too much in-process; move to Glue/ECS, or reduce tasks per worker (celery.worker_autoscale).
  • Mixed workloads → queues/pools so heavy tasks don't starve light ones.
  • Measure: parse time, scheduled vs running, queue age, worker memory.
  • Fix parsing first; then the binding concurrency limit; then capacity.
  • Stagger schedules; deferrable everything that waits.

Debugging real failures: a field guide

Interviewers love "a task failed at 3 a.m., walk me through it". Have a routine: which state is it in, which log explains it (task log, scheduler, DAG processing, worker, or the external service), and is it the code, the data, the platform or AWS? Below are the failures you'll actually see, with their log signatures.

Triage routine

  1. Grid view: which task, which try, what state? Upstream failed or this one?
  2. Task log of the failed try: the last traceback or the external job id.
  3. External system: Glue run / EMR job / Athena query console and its own logs.
  4. Platform logs if the task log is empty: worker log (killed?), scheduler log (never queued?), DAG processing (import error?).
  5. Decide: fix code and clear, wait for upstream data and clear, or mark success with a note.

Question bank 1: fundamentals

Expect these in the first 10 minutes. Answer in two or three sentences, then stop; let them dig.

1. What is Apache Airflow?

An open-source platform to author, schedule and monitor workflows as Python code. Workflows are DAGs of tasks; Airflow runs them on schedule or on events, retries failures, and records every run in a metadata database with a UI for monitoring.

2. What is a DAG and why must it be acyclic?

A directed acyclic graph of tasks and dependencies. Acyclic because the scheduler needs a definite order: if A depended on B and B on A, neither could ever start. Loops in logic are expressed with mapping, re-runs or (3.4+) task loops, not cycles.

3. Operator vs task vs task instance?

An operator is a class (a template for a kind of work), a task is an operator instantiated in a DAG with arguments, and a task instance is that task for one specific DAG run, with its own state, tries and logs.

4. What are sensors? What modes do they have?

Operators that wait for a condition (file exists, another DAG done). Poke mode holds a worker slot; reschedule mode frees the slot between checks; deferrable mode hands the wait to the triggerer so no worker is used. On MWAA I default to deferrable.

5. What is XCom and what are its limits?

A mechanism for passing small values between tasks, stored in the metadata DB by default. It's for metadata like S3 paths or job ids, not datasets. For bigger values use S3 or the object-storage XCom backend.

6. What are hooks?

Reusable clients for external systems that read credentials from Airflow connections. Operators use them internally; I use them directly inside @task functions when no operator fits.

7. What does catchup do?

When a DAG is enabled with a start date in the past, catchup=True creates runs for every missed interval; catchup=False creates only the latest. In Airflow 3 the default is False.

8. What is start_date and why not datetime.now()?

The first logical date the scheduler considers. It must be fixed; datetime.now() changes on every parse, so the schedule never settles and runs may never be created.

9. What are trigger rules? Give examples.

Conditions for a task to run based on upstream states. Default all_success; all_done for cleanup; one_failed for alerts; none_failed_min_one_success for joins after branches.

10. How do you pass parameters to a DAG run?

Params with types and defaults, shown as a trigger form in the UI and passed via conf through the API/CLI; read with params in tasks or {{ params.x }} in templates.

11. Connections vs variables?

Connections store how to reach a system (host, login, password, extras) and are used by hooks; variables store general key-value settings. In production both come from a secrets backend like AWS Secrets Manager.

12. What is the TaskFlow API?

Writing tasks as decorated Python functions with @task. Return values become XComs and calling one task with another's output sets the dependency automatically.

13. Name the main Airflow 3 components.

API server (UI, REST API, Task Execution API), scheduler, DAG processor, triggerer, workers via an executor, and the metadata database.

14. What's an executor? Which ones do you know?

The scheduler plug-in that decides how tasks run: LocalExecutor, CeleryExecutor (MWAA), KubernetesExecutor, AWS ECS/Batch executors, EdgeExecutor; several can run together and be chosen per task.

15. What is Amazon MWAA?

AWS's managed Airflow: DAGs in S3, workers and schedulers on Fargate in your VPC, Aurora metadata DB and SQS broker managed by AWS, IAM for access, CloudWatch for logs and metrics.

  • Short, precise answers; mention AWS context when natural.

Question bank 2: intermediate

1. Explain logical date vs data interval vs run_after.

run_after is the earliest time a run may start. The logical date is the point in time the run represents. With Airflow 3's default CronTriggerTimetable, the logical date equals the trigger time and the data interval has zero width. With CronDataIntervalTimetable (Airflow 2's default) each run owns the interval since the previous tick and the logical date is the interval start, so the run that starts on 8 Nov has ds = 7 Nov. I make the timetable explicit in critical DAGs.

2. What is dynamic task mapping? When would you not use it?

Creating task instances at run time from a list with expand/partial, each with its own retries and logs. I avoid it for tens of thousands of tiny items (scheduler overhead, max_map_length) and batch those or hand the list to one Spark job.

3. How do deferrable operators work?

The operator starts external work, then calls defer with a trigger; the task state becomes deferred and the worker slot is freed. The triggerer runs the async trigger; when it fires, the task resumes on a worker in a completion method. It saves worker capacity and survives worker restarts.

4. Assets vs ExternalTaskSensor vs TriggerDagRunOperator?

Assets are data dependencies: producers emit events on success and consumers are scheduled on them, decoupled and visible. TriggerDagRunOperator is an explicit push from upstream (tight coupling, can pass conf). ExternalTaskSensor makes downstream wait for a task in another DAG for the same logical date, which only works when schedules align. I default to assets.

5. How do you make tasks idempotent?

Inputs from the run's dates/params, outputs written by overwriting a partition or MERGE by key, atomic commits (Iceberg, renames, view swaps), no blind appends, and no reliance on wall-clock time. Then retries, clears and backfills are safe.

6. Pools vs max_active_tasks vs parallelism?

parallelism caps running tasks per scheduler; max_active_tasks caps one DAG; pools cap any set of tasks across DAGs that share a resource like Redshift or an API rate limit. Priority weights decide who gets slots first.

7. How does branching work and what's the classic bug?

A branch task returns the task_id(s) to follow and the other direct downstreams are skipped. The classic bug is the join task keeping all_success, which gets skipped; it needs none_failed_min_one_success.

8. Setup/teardown vs trigger_rule all_done cleanup?

Both run cleanup after failures, but with all_done the cleanup is a leaf whose success can make the run look successful. A teardown doesn't affect the run outcome, runs if its setup ran, and clearing work tasks re-runs setup and teardown automatically.

9. How do you handle secrets on MWAA?

Configure the Secrets Manager backend with connection and variable prefixes and lookup patterns, grant the execution role GetSecretValue on that prefix, and reference connections by id. Nothing sensitive lives in code, variables in the DB, or logs.

10. How do you backfill in Airflow 3?

Create a backfill from the UI, API or CLI with a date range, reprocess behaviour (none, failed, completed), max active runs and optional reverse order. The scheduler runs it, so it's visible and cancellable. Tasks must be idempotent, and I use pools so production isn't starved.

11. What happens when a worker dies mid-task?

The scheduler stops receiving heartbeats and marks the task failed for retry. If the task had started a Glue job, a retry could start a duplicate unless the task is deferrable (the wait was in the triggerer), the job is idempotent or limited to one concurrent run, or, on 3.3, the task state store lets the retry re-attach.

12. How do you test DAGs?

Integrity tests that load the DagBag and assert no import errors, cycles, owners, tags, retries and catchup policy; unit tests of task functions with moto; dag.test() runs locally; Ruff with AIR rules; all in CI on every PR before deploying to dev then prod.

13. What are Jinja templates used for? Which fields are templated?

Run-time values such as dates, params, variables and XComs in operator arguments and SQL files. Only fields listed in an operator's template_fields (and template_ext files) are rendered; TaskFlow call arguments are rendered too.

14. Why did Airflow 3 remove direct DB access from tasks?

Security and scale: a task with DB credentials could read or corrupt anything, and thousands of workers each opening DB connections strained the database. The Task Execution API centralises access through the API server and enables remote and multi-language execution.

15. How do you share code between DAGs?

A common package under dags/ (synced with the DAGs) or an internal wheel in requirements; custom operators/hooks with unit tests; assets and default_args defined once and imported.

Question bank 3: senior and Airflow 3 depth

1. What changed in Airflow 3 and why does it matter to you?

Task Execution API (workers off the DB), Task SDK imports, separate DAG processor, DAG versioning and bundles, assets with @asset and event-driven watchers, scheduler-managed backfills, optional logical dates, new React UI, removal of SubDAGs/SLAs/execution_date. For us it meant safer isolation, event-driven ingestion from SQS without sensors, correct history for changed DAGs, and a migration effort on templates and imports.

2. How would you migrate 200 DAGs from MWAA 2.x to 3.x?

Upgrade to 2.11 and clear deprecation warnings; run Ruff AIR3 rules with fixes; replace SubDAGs with task groups and SLAs with deadline alerts; remove direct DB access; validate requirements on the MWAA 3.3.1 image; stand up a new environment (major upgrades aren't in place) with secrets already in Secrets Manager; move DAGs domain by domain by pausing in old and unpausing in new with catchup off; keep the old environment read-only briefly, then delete it.

3. Explain asset partitions and a use case.

Producers attach a partition key to asset events (an hour, a date, a region) and consumers using PartitionedAssetTimetable run once per aligned key, with mappers normalising keys across producers. 3.3 adds rollups: e.g. a daily KPI DAG that waits for all 24 hourly partitions of a day, or fan-out from a weekly model to seven daily inference runs. It replaces brittle sensors in date-partitioned lakehouses.

4. How does the scheduler decide what to run?

In a loop it creates due DAG runs from timetables and asset events, examines task instances whose dependencies are met (trigger rules, depends_on_past), checks concurrency limits (parallelism, pools, DAG max_active_tasks/runs, task limits) and priority weights, and sends ready tasks to the executor. Multiple schedulers coordinate through row-level locks in the database.

5. How does HA work for the scheduler?

Several schedulers run active-active; they use database row locking (SELECT ... FOR UPDATE SKIP LOCKED) so each DAG run and task is handled by one scheduler at a time. If one dies, the others continue. MWAA runs 2–5.

6. When would you write a custom timetable?

When the schedule depends on business logic cron can't express: business days excluding a holiday calendar, fiscal periods, multiple irregular times. It implements next_dagrun_info and infer_manual_data_interval and is registered through a plugin so the scheduler can deserialize it.

7. What are DAG bundles?

The abstraction for where DAG code comes from: local folder, Git, S3. Versioned bundles (Git) let a run keep using the code version it started with and let the UI show each run with its own DAG version.

8. How do you design for exactly-once effects with retries?

You can't stop retries, so make effects idempotent: deterministic inputs, MERGE/overwrite outputs, unique external job names (including run id) to detect duplicates, max concurrent runs on external jobs, deferrable waits, and on 3.3 the state store to remember external ids across tries.

9. How do you multi-tenant one Airflow platform for several teams?

On MWAA: one environment per domain/criticality or a shared one with conventions: folders per team, owners and tags, pools per shared resource, IAM roles mapping to Viewer/User/Op, separate SNS routing. Airflow 3.2 has experimental multi-team mode but MWAA doesn't support it; strong isolation needs separate environments or MWAA Serverless with per-workflow roles.

10. What's in the Task SDK and why separate it?

The public authoring interface: DAG, dag, task, Asset, Variable, Connection, BaseOperator, context. Separating it from core gives DAG authors a stable API that can evolve and be upgraded independently and is the foundation for running tasks remotely and in other languages.

11. What's new in 3.3 and 3.4 you'd actually use?

3.3: task state store (re-attach to running external jobs, cursors), pluggable retry policies (retry throttling, don't retry validation errors), rollup and fan-out partition mappers, bulk actions. 3.4 (not on MWAA yet): task loops for polling/pagination, graceful DAG draining, non-Python DAG importer (experimental), and single-asset schedules now creating one run per event by default.

12. How would you reduce scheduler load for 2,000 DAGs?

Lighten parse time (no top-level I/O, lazy imports, split giant files, .airflowignore), tune processing intervals, stagger schedules, use assets instead of sensors, deferrable operators, more schedulers and a larger environment class, and archive dead DAGs.

13. Airflow vs Dagster vs Prefect?

Airflow: most adopted, huge provider ecosystem, managed on all clouds, task-centric with assets added in 3.x. Dagster: asset-centric from the start with strong typing and local dev. Prefect: dynamic Python flows and a SaaS-first model. On AWS with MWAA and many existing operators, Airflow is the pragmatic default.

14. How do you handle late-arriving data?

Wait with deferrable sensors and timeouts or event-driven watchers; MERGE so late rows update earlier partitions; reprocess a lookback window (e.g. last 3 days) every run; partitions so only affected keys re-run downstream; deadline alerts for the business commitment.

15. How do you observe data freshness across the platform?

Asset event timestamps per gold asset, a freshness DAG comparing them against SLAs, deadline alerts on critical DAGs, CloudWatch dashboards for platform health, OpenLineage for impact analysis when something is late.

Question bank 4: MWAA and AWS

1. Describe MWAA's architecture.

Schedulers, workers and the web/API server run as Fargate containers in two private subnets in my VPC; CeleryExecutor with an SQS broker and an Aurora PostgreSQL metadata DB in an AWS service VPC; DAGs, requirements, plugins and startup script from a versioned S3 bucket; IAM for access; CloudWatch logs and metrics; optional customer KMS key.

2. How do you deploy DAGs and dependencies?

CI syncs dags/ to S3 (picked up in about a minute). requirements.txt, plugins.zip and startup.sh are uploaded and the environment is updated to the new S3 object version, which takes 10–30 minutes and rolls back on failure. I test requirements with the MWAA Docker image first.

3. Execution role vs user access?

The execution role is assumed by the containers (trusted by airflow and airflow-env principals) and used by aws_default; it needs MWAA base permissions plus least-privilege access to orchestrated services and PassRole for job roles. Users get CreateWebLoginToken/InvokeRestApi on role/<env>/<AirflowRole> to map to Admin, Op, User or Viewer.

4. Public vs private web server?

Public exposes the UI endpoint to the internet behind IAM authentication; private keeps it inside the VPC, reached via VPN or proxy. Containers are always private. Production in enterprises is usually private.

5. How does worker autoscaling work and what are the limits?

MWAA adds workers up to max (≤25) when queued plus running tasks exceed capacity and removes them after load drops, down to min. Each worker runs a class-dependent number of tasks (tunable with celery.worker_autoscale). Scale-out takes minutes, so bursty schedules should be staggered.

6. How do you trigger an MWAA DAG from Lambda?

boto3 mwaa.invoke_rest_api with Name, Path /dags/<id>/dagRuns, Method POST and a body with conf; the Lambda role needs airflow:InvokeRestApi on the environment role ARN. On Airflow 3 an SQS asset watcher is an alternative for file-arrival events.

7. Requirements install failed on MWAA. What now?

MWAA rolled back, so prod is fine. Read LastUpdate.Error and the requirements_install log stream; usually a pin conflicts with the constraints file or a package needs internet in a private environment. Fix, test with ./run.sh test-requirements, package wheels into plugins.zip if private, re-upload and update.

8. How do you reduce MWAA cost?

Right-size the class, min workers 1–2, deferrable operators, staggered schedules, consolidate environments, lower log levels and set retention, tear down dev outside hours or use MWAA Serverless/local Docker for dev, and move simple AWS-only workflows to Serverless.

9. MWAA provisioned vs Serverless?

Provisioned: full Airflow UI, any provider, Python DAGs, hourly billing. Serverless: YAML workflows, Amazon operators plus Python/Bash bundles, each task in its own Fargate container, per-workflow IAM role, pay per task-second, no UI. Serverless for AWS-centric infrequent workflows; provisioned for large, custom estates.

10. How do you upgrade MWAA?

Minor versions in place via update-environment (with automatic rollback), dev first, constraints line updated at the same time. Major versions (2→3) need a new environment and blue/green migration.

11. What VPC endpoints does a private MWAA need?

S3 gateway, SQS, CloudWatch Logs and Monitoring, KMS, ECR API and DKR, the airflow api/env/ops endpoints, plus Secrets Manager, STS and every service DAGs call (Glue, Athena, Redshift Data, EMR Serverless, Lambda, SNS…). Without NAT there's no PyPI, so wheels go in plugins.zip or CodeArtifact.

12. Where do you look when a task log is empty on MWAA?

The Worker log group for kills/OOM, the Scheduler log for queueing or heartbeat issues, DAGProcessing for import errors, and environment metrics for capacity. An empty task log usually means the task never really started or the worker died.

13. How do you run dbt on MWAA?

Usually in an ECS Fargate task (EcsRunTaskOperator) with a dbt image, streaming logs into Airflow; this keeps dbt's dependencies out of the environment. Alternatives are dbt Cloud's provider or Cosmos rendering dbt models as Airflow tasks when the dependency set is compatible.

14. Can tasks access the MWAA metadata DB?

No direct access to the Aurora DB is offered, and in Airflow 3 tasks can't query the DB anyway. Use the REST API (invoke-rest-api) for run state, and Airflow's own features for history.

15. How do you do cross-account work from MWAA?

An AWS connection whose extra has role_arn for a role in the target account that trusts the MWAA execution role; operators assume it via the hook. Keep permissions in the target role least-privilege.

Scenario questions with model answers

Senior rounds are mostly scenarios. Structure every answer: clarify → diagnose → fix now → prevent.

1. Every morning at 02:00 tasks queue for 30 minutes on MWAA.

Clarify which DAGs start at 02:00. Diagnose with RunningTasks vs capacity, queued count and max workers; check for poke sensors. Fix now: raise max workers or min workers for that window. Prevent: make waits deferrable, stagger cron minutes, add pools for heavy DAGs, and right-size the class.

2. A downstream team says yesterday's gold table has duplicates.

Check run history: was the task retried or cleared? Read the SQL/job: an append instead of MERGE? Fix now: dedupe the partition (rewrite it with row_number by key, or rerun with an idempotent version after fixing). Prevent: MERGE/overwrite patterns, uniqueness checks as a DQ gate before publishing, code review checklist for idempotency.

3. A new DAG works locally but never appears on MWAA.

Check DAGProcessing logs / import errors: likely a package missing from requirements or a different Python/provider version; maybe a parse timeout from top-level I/O, or the file excluded by .airflowignore or not synced. Fix and test with the MWAA image; add an integrity test in CI.

4. The vendor sometimes sends the file twice with the same name.

Make processing idempotent by key (MERGE on business keys plus file checksum), record processed file ETags in a control table or asset event extras, and skip duplicates with a short-circuit task. With SQS watchers, duplicates can also arrive, so the same idempotency covers them.

5. A Glue job got slower: runtime went from 20 to 90 minutes.

Airflow isn't the cause but shows it: duration chart and deadline alert flagged it. Look at Glue metrics/Spark UI: data volume growth, skew, small files, missing partition pruning. Fix in Spark (compaction, AQE, partition filters, more workers) and add an AVERAGE_RUNTIME deadline so regressions alert early.

6. Leadership wants to cut the MWAA bill by 40%.

Measure utilisation: class, worker hours, log ingestion. Typical wins: drop one class size if scheduler/worker CPU is low, min workers to 1–2, deferrable everywhere, reduce log levels and retention, merge low-use environments, move dev to local Docker or Serverless, move infrequent AWS-only workflows to MWAA Serverless.

7. You must reprocess 18 months of data after a logic change.

Confirm idempotency and estimate compute; do it as a scheduler-managed backfill with limited max active runs and a pool, newest first if recent data matters most, possibly on a separate environment or with a dedicated Glue/EMR capacity, and validate per partition. Or, if it's one big Spark job, run a single reprocessing job instead of 540 daily runs.

8. A teammate wants to load a 3 GB CSV in a PythonOperator with pandas.

Explain the risk: worker memory (OOM kills, other tasks evicted), slow, not scalable. Propose Glue/EMR Serverless/Athena CTAS, or ECS if it must be pandas; Airflow passes the S3 path and waits.

9. A critical report must be ready by 07:00 but upstream sometimes runs late.

Use assets so the report starts as soon as upstream completes; deadline alerts on upstream and report DAGs with escalation; priority weights and pools so the report gets capacity; agree on a fallback (publish with a "stale" banner) and communicate proactively.

10. Someone deleted a connection in the UI and production broke.

Restore from Secrets Manager (if used, UI deletion wouldn't affect it; that's the point). Prevent: secrets backend as source of truth, restrict Admin/Op roles, audit log review, and connections defined as code/IaC.

5. Write a custom operator that counts S3 objects under a templated prefix and fails if below a threshold. 
from airflow.sdk import BaseOperator
from airflow.exceptions import AirflowFailException
from airflow.providers.amazon.aws.hooks.s3 import S3Hook

class S3MinObjectsOperator(BaseOperator):
    template_fields = ("prefix",)

    def __init__(self, *, bucket: str, prefix: str, min_objects: int = 1,
                 aws_conn_id: str = "aws_default", **kwargs):
        super().__init__(**kwargs)
        self.bucket, self.prefix, self.min_objects, self.aws_conn_id = bucket, prefix, min_objects, aws_conn_id

    def execute(self, context):
        n = len(S3Hook(aws_conn_id=self.aws_conn_id).list_keys(self.bucket, prefix=self.prefix) or [])
        self.log.info("Found %s objects under s3://%s/%s", n, self.bucket, self.prefix)
        if n < self.min_objects:
            raise AirflowFailException(f"Expected >= {self.min_objects}, found {n}")
        return n
